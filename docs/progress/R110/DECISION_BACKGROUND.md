# libc++ 运行时迁移：四项待决事项的背景材料

本文供人工裁决者和多方评审使用，只汇编事实、选项后果与证据缺口，不作推荐、
不排列优先级，也不代替发布或 ABI 政策决定。

## 阅读口径

文中的证据标签含义如下：

- **实测**：已在明确架构和环境中运行，并保存命令、输出、退出码与重复结果。
- **静态核查**：来自源码、符号表、包元数据、构建规则或冻结清单。
- **推断**：由已知事实推导，但没有对应产品运行观测；推断会写出前提。
- **未观测**：现有环境或样本中没有实际看到，记为 `NOT_OBSERVED`，不等于不存在。
- **不可得**：完成判断所需材料当前拿不到，记为 `NOT_AVAILABLE`。

这里的“强制展开”（forced unwind）是 POSIX 线程取消驱动的特殊栈展开；它必须
沿调用栈运行清理。“non-throwing 边界”是 C++ 中声明为 `noexcept` 或隐式不得
抛出的函数边界；任何异常或强制展开穿越它都会调用 `std::terminate`。这里的
“C++ ABI 边界”是两个二进制组件之间传递 C++ 对象、异常、所有权或模板语义的
边界，不只是符号能否链接。

## 是否允许条件变量的普通错误作为异常传播

### 要决定的是什么

当前 libc++ 的 `condition_variable::wait` 及相关定时等待虽然在实现内生成
`system_error`，其外层异常规格却会把该异常转成进程终止。待决定的是：保留
这一行为，还是解除相应异常规格，使重新编译的调用方在“未持锁调用”或底层等待
返回普通错误时能够观察到 `system_error`。

这不是只影响线程取消的改动。即使没有任何取消，两个普通错误入口也存在可观察
差异。

### 已查明的事实

- **静态核查**：libc++ 普通等待先检查 `unique_lock::owns_lock()`；未持锁时
  生成错误码 `EPERM` 的 `system_error`。底层 `pthread_cond_wait` 返回非零时，
  也按返回码生成 `system_error`。定时等待有同类检查，正常超时除外。
- **静态核查**：glibc 2.40 的非超时错误包括特定互斥量配置下的 `EPERM`、
  `EOWNERDEAD`、`ENOTRECOVERABLE` 和优先级保护相关错误；定时入口还可能因非法
  纳秒或不支持的时钟得到 `EINVAL`。
- **推断**：标准、未被篡改的 `std::mutex` 和 libc++ 自身生成的时间值没有已知
  合规路径自然触发上述错误。通过 `native_handle()` 重建或篡改互斥量、对象损坏
  和底层故障仍可能触发；产品中的自然发生率为 `NOT_OBSERVED`。
- **静态核查**：在 371 个既有源码包的条件变量专项扫描中，92 处调用可直接
  归属于 `std::condition_variable`；其中生产代码或交付头文件 8 处，源码均表明
  等待时持锁。另有 311 条词法候选不能只凭现有材料确认对象类型，不能据此判断
  锁状态。
- **静态核查**：冻结发布仓中 11,332 个包记录、39,166 个 ELF 均完成符号解析，
  正向对照命中预期符号。普通和 system-clock 等待得到 601 个消费记录，全部映射
  到既定迁移重编计划。头文件内联路径和外部产品/应用不在这个分母内。
- **实测，x86_64**：保留异常规格时，未持锁和受控注入的 `EINVAL` 各 5/5 进入
  `std::terminate`；默认终止处理器下各 5/5 为 `SIGABRT`。
- **实测，x86_64**：移除异常规格并重新编译调用方后，未持锁 5/5 抛出
  `system_error`，code 为 1，消息指向 mutex 未锁；底层 `EINVAL` 5/5 抛出
  `system_error`，code 为 22，消息指向无效参数。
- **实测，x86_64**：旧头文件编译的调用方加载可抛实现后，两类错误仍各 5/5
  终止。符号能绑定不等于旧调用点获得了新语义。
- **实测，x86_64**：持锁且底层成功、以及正常超时的样本没有观察到行为变化。
  这只证明所测成功路径，不证明所有时序和互斥量属性组合均无差异。

### libstdc++ 的对应行为

- **静态核查**：GCC 曾为线程取消解除公开普通等待和内部普通/定时等待的
  `noexcept`；只有公开的 out-of-line `condition_variable::wait` 保留旧、新两个
  符号版本。这一上游改动主要解决强制展开。
- **静态核查**：libstdc++ 对 libc++ 的两条普通错误路径没有对应检查，也不把
  底层错误码转换成 `system_error`。因此 GCC 解除异常规格时没有引入 libc++ 这里
  的“终止变为普通异常”策略变化；平台必须独立决定该策略。
- **实测，x86_64**：libstdc++ 未持锁格 5/5 返回，但返回后
  `unique_lock::owns_lock()==false`，native mutex 的 `try_lock` 仍报告 busy；库层
  和底层所有权状态不一致。底层 `EINVAL` 注入格 5/5 返回且锁对象仍报告持有。
  所以“不检查后返回”不能写成“没有问题”。

### 可选处理及可观察后果

| 选项 | 成功路径 | 普通错误路径 | 取消路径 | 调用方后果 |
|---|---|---|---|---|
| 保留当前 non-throwing 契约 | 所测样本不变 | 在错误现场终止 | 强制展开穿越该边界时终止 | 无需新增错误处理；不能在上层恢复或完成正常展开清理 |
| 解除异常规格 | 所测样本不变 | 重新编译调用方可收到 `system_error` | 强制展开可以继续穿越这些已解除的边界 | 可清理、记录、恢复或降级；也可能被宽泛 `catch (...)` 吞掉，使缺陷延后或被掩盖 |

对解除异常规格的情形，异常最终若逃出线程入口、析构函数或其他 non-throwing
边界，进程仍可能终止，只是位置和清理轨迹不同。某些底层错误返回时 mutex 可能
已经释放，错误处理代码不能统一假定锁仍由调用方持有。

### 仍未查清

- 外部产品、应用、OEM 或伙伴组件中是否存在旧调用方、违规未持锁调用或
  `native_handle()` 篡改，均为 `NOT_AVAILABLE` 或 `NOT_OBSERVED`。
- 311 条复杂别名、模板或跨文件调用候选不能由词法证据闭合。
- 底层普通错误在真实产品负载中的发生率为 `NOT_OBSERVED`。
- aarch64 上的相同行为形态尚未运行；armv7l 也没有这组普通错误矩阵。

## 若改变等待契约，如何处理已经编译的调用方

### 要决定的是什么

如果决定让新调用方接受异常或强制展开，还必须决定如何向已发布对象交付：直接
替换现有共享库实现，还是为可导出的等待入口保留旧、新两个符号版本，并对已经
内联进调用方的实现另行重编或淘汰。这一问题在保留当前等待契约时不产生同样的
交付需求，但头文件内联事实仍然存在。

### 已查明的事实

- **静态核查和最小探针**：顶层 `noexcept` 不进入这里的 Itanium 函数符号名，
  但从 C++17 起属于函数类型的一部分，也会改变调用方是否生成 personality、
  LSDA、清理 landing pad 和 `_Unwind_Resume` 路径。因此“原符号仍能链接”不等于
  “异常展开完全兼容”。
- **实测，x86_64**：旧调用点绑定解除异常规格后的同名实现，两类普通错误仍
  各 5/5 终止。这是混用新旧调用点时可直接观察到的行为差异。
- **静态核查**：普通等待和 system-clock 定时 helper 是共享库中的真实动态
  符号，当前位于同一 LLVM 符号版本节点；库端有承载旧、新入口的技术位置。
- **实测，宿主 GNU 链接器**：独立 `.symver` 探针成功同时导出旧版本和新默认
  版本，证明当前链接器及 version-script 形态能表达双版本。探针使用的版本名不
  是发布方案，真实 libc++ wrapper 尚未实现，也未经过三架构产品构建。
- **静态核查**：steady-clock 定时 helper、generic Clock 模板和
  `wbuffer_convert` 析构是隐藏的头文件实现，没有可由更新共享库替换的统一动态
  符号。它们已经编进消费者；无论选择哪种共享库方案，旧对象都不会被库更新
  修正。
- **静态核查**：C++03 兼容头也有相应镜像，实际变更不能只处理主头文件。
- **静态核查**：冻结发布仓中可见的 601 个普通/system-clock 等待消费记录都在
  迁移重编计划内。这个结论不覆盖隐藏内联实例和外部组件。
- **静态核查**：不重编候选已量化为 5 个确认只复制安装的共享 DSO、另 1,027
  个源码包内共享库候选、8,911 个已发布静态归档和 3,236 个源码包内对象文件；
  这些集合中可见目标符号为零，但内联、LTO、剥离和类型擦除使“符号零命中”不能
  排除旧实现。外部组件分母为 `NOT_AVAILABLE`，各类数量也不能直接相加。

### libstdc++ 的对应行为

- **静态核查**：libstdc++ 只为公开普通等待保留旧 `GLIBCXX_3.4.11` 和新默认
  `GLIBCXX_3.4.30` 两个版本；内部普通和定时等待解除异常规格但没有各自的双符号。
- **静态核查**：libc++ 的 system-clock helper 是导出成员，和 libstdc++ 的内部
  结构不相同。它虽然技术上可版本化，但没有现成 compatibility wrapper，不能把
  GCC 的实现原样视为平台方案。
- **静态核查**：GCC 的 generic Clock wrapper 原本就不带 `noexcept`。libc++ 的
  旧内联 generic Clock 路径仍只能靠消费者重编或淘汰改变。

### 可选处理及可观察后果

| 选项 | 新对象 | 旧 out-of-line 调用点 | 旧头文件内联点 | 代价与混用形态 |
|---|---|---|---|---|
| 直接替换现有实现并重编已知集合 | 取得新契约 | 仍绑定同名符号，但展开元数据和行为不能宣称兼容；实测错误仍终止 | 不受共享库更新影响 | 已知重编集合可趋于一致；漏网旧对象会与新对象表现不同 |
| out-of-line 入口保留旧、新符号版本，内联点另行重编或淘汰 | 新对象可绑定新默认版本 | 可继续绑定旧版本并保留旧契约 | 仍不受库端双版本覆盖 | 有意保留两套可观察行为；需要真实 wrapper、版本命名、回滚与三架构验证 |
| 不改变等待契约 | 保持当前行为 | 保持当前行为 | 保持当前行为 | 不产生这一轮新旧异常语义；现有取消终止边界也保持 |

### 仍未查清

- 真实 compatibility wrapper 的实现、helper 可见性、最终版本节点名称、发布和
  回滚规则均未定。
- `.symver` 只在独立宿主探针验证；三目标架构的 QuickBuild 结果为
  `NOT_OBSERVED`。
- 外部产品/应用的 BOM、最终 ELF、源码和重建策略为 `NOT_AVAILABLE`；因此无法
  证明所有旧内联实例都会被淘汰。
- 5 个确认只复制安装的 DSO 是否实际包含这些调用路径，没有可见符号证据，不能
  由“只复制”属性推断。

## `wbuffer_convert` 析构是否继续自动同步

### 要决定的是什么

`std::wbuffer_convert` 是把宽字符转换套在另一个 stream buffer 上的已弃用头文件
模板。libc++ 当前在析构时自动调用内部 close/sync，写出转换状态和缓冲数据。
待决定的是继续保留析构自动同步，还是改为显式收尾或停止在析构中同步。

### 已查明的事实

- **静态核查**：该析构没有一处可简单删除的显式 `noexcept`；它覆盖
  `basic_streambuf` 的 non-throwing 虚析构，因而隐式 non-throwing。
- **编译探针**：派生析构单独声明 `noexcept(false)` 会因比虚基类更宽松的异常
  规格而被编译器拒绝。若要允许析构传播，必须扩大基类层次契约，或改变析构收尾
  结构；不是单点删标注。
- **静态核查**：输出模式的 `close -> sync` 会调用用户可覆盖的
  `codecvt::do_unshift`，以及 wrapped stream buffer 的 `sputn`、`pubsync`、
  `pubseekoff` 等虚路径。这些开放调用可以抛普通异常，也可能进入输出取消点。
- **推断**：保留自动同步能在正常析构时尝试写出转换尾部和缓冲数据，但异常或
  强制展开穿越析构仍会终止。停止同步会移除该析构边界，却可能丢失调用方未显式
  刷新的尾部或缓冲数据。具体产品是否依赖自动收尾未观测。
- **静态核查**：冻结材料累计覆盖 1,450 个 source RPM（1,424 完整、24 部分、
  2 个仅包装材料不可得）、11,332 个 binary RPM、39,166 个 ELF 和 8,911 个静态
  归档；目标类型零命中，扫描器和独立符号检查均有正向对照命中。
- **限制**：零命中只支持“已覆盖冻结材料内没有发现使用者”。完全内联、LTO
  消除、剥离、宏生成、私有源码和外部产品/应用仍可能漏出；外部 BOM 与源码为
  `NOT_AVAILABLE`，所以不能写成“平台上没有使用者”。
- **未观测**：没有实际平台调用方命中，因而没有真实产品用例可测同步、丢数据、
  普通异常或取消形态；这些产品动态结果均为 `NOT_OBSERVED`。

### libstdc++ 的对应行为

- **静态核查**：libstdc++ 的 `wbuffer_convert` 析构同样隐式 non-throwing，但实现
  为默认析构，不在析构中调用 libc++ 的 `sync()` 路径。
- **推断**：这说明“不在析构中同步”存在实现先例，但不能证明平台调用方没有
  依赖 libc++ 当前的自动收尾语义，也不能替代产品需求决定。

### 可选处理及可观察后果

| 选项 | 正常收尾 | 异常/取消 | 已编译调用方 | 主要待验证内容 |
|---|---|---|---|---|
| 保留析构自动同步 | 继续尝试写出转换尾部和缓冲数据 | 开放虚调用抛出或取消展开时仍可能终止 | 旧、新调用方语义一致 | 真实调用频率、终止暴露和输出正确性 |
| 析构不再同步，要求显式 close/sync 协议 | 遵守新协议者可在可处理异常的位置收尾；遗漏者可能丢数据 | 析构不再进入该同步取消/抛出路径 | 旧头文件实例仍保留自动同步；新协议只约束重编并迁移的调用方 | API 形态、错误报告、调用点迁移和遗漏检测 |
| 析构不再同步，也不新增强制协议 | 析构语义接近 libstdc++；调用方未主动同步时可能丢数据 | 移除这一析构边界 | 新旧对象产生收尾差异 | 产品是否允许改变自动收尾语义 |
| 扩大 `basic_streambuf` 析构契约以允许传播 | 可保留析构内同步并让异常离开 | 改变整个派生层次的异常契约 | 影响范围远超该模板 | 标准契约、ABI、全部派生类和三架构构建/运行 |

### 仍未查清

- 外部产品/应用是否使用该模板、是否依赖析构自动同步、是否可以迁移到显式协议，
  均为 `NOT_AVAILABLE`。
- 私有镜像、应用商店、OEM/供应商和伙伴部署的真实分母为 `NOT_AVAILABLE`。
- 产品能否接受“遗漏显式收尾时丢失输出”或更宽的 streambuf 析构契约，属于待人工
  给定的产品要求。
- aarch64、armv7l 和 x86_64 上的真实模板运行样本均为 `NOT_OBSERVED`。

## 如何处理 Boost 组件之间的跨 C++ 运行库语义边界

### 要决定的是什么

冻结平台中，Boost provider 由 libstdc++ 构建，而拟迁移 consumer 可能由 libc++
构建。待决定的是如何处理仍在组件间传递 C++ 对象、状态和所有权的真实边界：
协调重编为同一运行库、把边界改造成不传递 C++ 语义的接口，或用其他隔离方式
维持两套 ABI 世界。

动态加载器能够同时装入 libc++ 和 libstdc++，只证明“共存”；它不证明两套
`std::string`、容器或嵌入这些成员的 Boost 类型具有相同布局和销毁规则。

### 已查明的事实

- **静态核查**：共有 90 条实际传递 C++ 语义的 Boost 符号边，涉及 13 个
  consumer source package 和 75 个按“架构、consumer ELF 路径”区分的二进制。
  其中 63 条已由签名或 Boost 类型定义确认布局敏感，27 条是 C++ ABI 耦合但现有
  材料没有证明布局；“布局未证明”不是安全证明。这个输入集合中仅 C 接口和无
  交集均为 0。
- **静态核查**：13 个 consumer 中 6 个有已确认布局敏感形态；其中 3 个的标准库
  状态隐藏在 Boost 自有类型内部，链接器不能仅从表面符号名阻止误配。
- **实测汇总**：按“该架构上的边包含实际执行的代表符号组”计，目前测到 49/90；
  布局敏感 33/63、布局未证明 16/27。仍有 41/90 为 `NOT_OBSERVED`：布局敏感 30、
  布局未证明 11。已测边也不是该边全部 C++ 符号逐个动态执行。
- **实测，x86_64 与 armv7l QEMU user**：Boost.Filesystem 混合格各 5/5 具体状态
  和路径值错误，但 consumer 销毁完成。退出或析构没有立即崩溃并不代表值正确，
  也不证明没有潜在堆损坏。
- **实测，x86_64 与 armv7l QEMU user**：Boost.Iostreams 在取得可断言值前分别
  5/5 终止为退出 134 和 139，析构完成标记未到达。
- **实测，x86_64**：Boost.Program Options 5/5 在访问 provider 构造对象期间
  退出 139，销毁完成未到达；armv7l 为 `NOT_OBSERVED`。
- **实测，x86_64**：Boost.Test 5/5 返回静默错值，观察长度 24 而期望 16，随后
  consumer 析构和 `dlclose` 完成。Boost.Thread 单线程 once 状态 5/5 精确为
  `1,1,0`，平凡析构作用域退出完成；该成功不能外推到竞争、其他符号或架构。
- **实测，aarch64 QEMU user**：使用真实平台 provider，并由 `/proc/self/maps`
  逐次确认两套运行库与 provider 同时加载。Boost.Test 5/5 错误长度 56；
  Filesystem 5/5 状态和值错误；Iostreams 5/5 抛 `length_error` 后退出 134；
  Program Options 5/5 值先精确通过、随后在析构阶段退出 139；Boost.Thread 5/5
  精确通过。每格均有同 provider 的 libstdc++ consumer 正向对照，全部 5/5 得到
  预期值和适用的销毁结果。
- **推断**：以上至少证明同一问题可表现为静默错值、取值前终止、值正确后析构
  失败或有限样本精确通过。因此只检查链接、退出码或主路径值中的任一项都不足以
  判断边界安全。

### libstdc++ 的对应行为

- **实测**：所测真实 Boost provider 本身依赖 libstdc++；同一 provider 配同一
  libstdc++ consumer 的所有正向对照均得到预期具体值，并完成结构上适用的销毁。
- **事实边界**：这只证明相同运行库对照和测法有效，不证明所有 Boost API 在
  libstdc++ 下已穷尽，也不提供任何 libc++/libstdc++ 跨对象 ABI 兼容保证。
- **静态核查**：两套运行库可以在同一进程加载；只经 C 接口传递 ICU 等不透明
  状态的既有共存样本与 Boost C++ 语义边的失败不矛盾。

### 可选处理及可观察后果

| 选项 | 边界形态 | 可避免的已知问题 | 新增工作与限制 |
|---|---|---|---|
| provider 与所有 C++ 语义 consumer 协调重编为同一运行库 | 保留现有 C++ API，但边界两侧使用同一标准库 ABI | 避免本次由混合标准库布局和销毁规则造成的误配 | 必须闭合 provider/consumer 构建顺序、插件与外部组件；漏重编对象仍会形成混合边界 |
| provider 保留 libstdc++，边界改为 C ABI、不透明句柄或同侧创建销毁 | 同一 ABI 世界内拥有对象，跨界只传稳定数据 | 避免跨界解释和异侧销毁 C++ 对象 | 需要设计适配层、错误协议、生命周期和性能语义；现有 90 条边不能自动变成 C 接口 |
| 为两套 ABI 提供隔离的并行产物 | 调用方只加载与自身运行库匹配的 provider | 可保留较多 C++ API | 需要符号/SONAME/插件发现隔离，防止同进程错误绑定；发布和更新矩阵扩大 |
| 使用进程边界隔离 | 通过 IPC/序列化交换数据 | 彻底隔离对象布局、异常和分配器 | 引入协议、复制、失败恢复、部署和性能成本；不等同于原调用语义 |
| 接受现有混合边界 | 不改变 | 无 | 已实测的静默错值、终止和析构失败保持；未测 41 条风险仍未知 |

### 仍未查清

- 41 条未测边均保持 `NOT_OBSERVED`；同一代表组以外的符号也没有逐个运行。
- armv7l 尚缺 Boost.Test、Boost.Thread 和 Program Options 的相应覆盖；物理板
  上的 armv7l、aarch64 结果均为 `NOT_OBSERVED`。
- QEMU user 适合确定性布局、值和析构实验，不覆盖真实目标内核调度、设备 provider、
  完整产品插件装载顺序和长期压力。
- 外部产品/应用的 Boost provider、consumer 和重建策略为 `NOT_AVAILABLE`。
- 已完成销毁但没有立即崩溃的样本尚未用 sanitizer 或等价工具证明没有潜在堆
  损坏或泄漏。

## 必须先知道的共同事实

- **三个头文件内联位置无法通过更新共享库修正。** steady-clock 定时 helper、
  generic Clock 模板和 `wbuffer_convert` 析构已经编进消费者；无论选择直接替换
  还是双符号版本，旧对象都必须重编、淘汰或明确保留旧行为。
- **异步取消与已识别的五处 non-throwing 站点正交。** x86_64 独立探针选择五处
  之外的 `std::atomic<int>::wait`；补丁 libc++ 与系统 libstdc++ 各跑 5 轮，正常
  对照均 5/5 通过，异步取消判定均 25/25 进入终止处理器。即使五处全部处理，启用
  异步取消并执行 C++/用户代码的 lightweight web engine 和 OpenMP 条件路径仍不
  会自动获得保护。armv7l 和 aarch64 的该正交实验为 `NOT_OBSERVED`。
- **libstdc++ 的“不检查”并不干净。** 未持锁等待虽然 5/5 返回，但 C++ 锁对象与
  native mutex 的所有权状态不一致；不能把“没崩溃”写成“没有问题”。
- **捕获点修复不等于所有 non-throwing 帧都已消失。** 当前强制展开补丁处理的是
  已识别 catch 路径；任何未改的 `noexcept` 函数、隐式 non-throwing 析构或用户
  代码边界仍可终止展开。
- **同进程共存不等于 C++ ABI 安全。** 动态加载成功只证明 loader 可以解析两套
  运行库；Boost 实测已展示符号匹配后仍会错值或在销毁阶段失败。
- **“值正确”和“销毁正确”必须分别验证。** aarch64 Program Options 的值先精确
  通过、随后析构崩溃；Filesystem 与 Boost.Test 则能在值错误后完成析构。
- **新旧调用点混用会形成真实的语义分裂。** 同一可抛实现，在新调用点可以传播
  `system_error`，在旧 non-throwing 调用点仍终止。
- **零命中结论都有分母。** `wbuffer_convert` 的零命中经过正向对照，但只能约束
  冻结仓、已取得源码和已扫描产物；它不能代替外部产品 BOM。

## 证据覆盖与限制

| 事实主题 | x86_64 | armv7l | aarch64 | 范围限制 |
|---|---|---|---|---|
| 条件变量两条普通错误的终止/异常形态 | 实测，每格至少 5 次 | `NOT_OBSERVED` | `NOT_OBSERVED` | `EINVAL` 为受控注入，不代表自然发生率 |
| 旧调用点加载新实现 | 实测，每格 5 次 | `NOT_OBSERVED` | `NOT_OBSERVED` | 只覆盖最小调用点 |
| 五处之外的异步取消正交性 | 两套运行库实测 | `NOT_OBSERVED` | `NOT_OBSERVED` | 组件只证明条件可达，不证明具体产品必达 |
| `wbuffer_convert` 使用情况 | 源码和多架构产物静态扫描 | 同左 | 同左 | 冻结覆盖范围内零命中；外部组件不可得 |
| Boost Filesystem / Iostreams | 实测 | QEMU user 实测 | QEMU user 实测 | 代表符号组，不是全符号穷举 |
| Boost Program Options | 实测 | `NOT_OBSERVED` | QEMU user 实测 | aarch64 值与析构得到不同阶段结果 |
| Boost.Test | 实测 | `NOT_OBSERVED` | QEMU user 实测 | 已测边只表示代表符号组 |
| Boost.Thread once 状态 | 实测 | `NOT_OBSERVED` | QEMU user 实测 | 单线程状态样本；不覆盖竞争压力 |
| aarch64 两套运行库装载与生命周期 | 不适用 | 不适用 | QEMU user 实测 | 不替代物理目标的取消、信号和设备路径 |

目前能明确写成“已覆盖范围内成立”的结论包括：冻结材料内没有发现
`wbuffer_convert` 使用者；发布仓可见的普通/system-clock 等待消费者都在既定
重编计划；90 条已知 Boost 语义边已全部分类。不能写成“平台上成立”的结论包括：
全平台没有该模板使用者、没有外部旧调用点、全部 Boost 边界都已测或 aarch64
运行时取消行为已验证。

外部产品/应用缺口同时影响等待契约交付、头文件内联实例、模板使用情况和 Boost
边界闭包。当前缺少最终产品 BOM、安装清单、最终 ELF/静态产物、对应源码、组件
来源、重建策略和 OTA/升级保留策略；因此外部分母及可重编比例均为
`NOT_AVAILABLE`。拿不到这些材料时，所有“无使用者”“全部会重编”“边界闭合”
结论都必须保留“已覆盖范围内”限定。
