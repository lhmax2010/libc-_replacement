# 已恢复的技术性错误

以下非零均为命令或校验实现问题，不是业务判据失败：

1. 首次在 `docs progress` 全目录执行宽检索，历史原始输出体量过大；主动发送
   SIGINT，包装器记录退出码 130。随后只检索顶层报告和明确表格。
2. 对全部 Git 已跟踪 `docs` 做正则搜索同样耗时过长，主动 SIGINT，退出码 130；
   改为 `find .../REPORT.md | xargs rg` 后退出 0。
3. 第一次生成表时，把用于 TSV 显示的 `\\t` 转义文本拿去与真实含 tab 行比较，
   触发断言并退出 1。修正为先用原始行做逐字核验、再仅在输出字段中转义 tab；
   扫描表达式和计数逻辑没有改变。
4. 初次严格扫描仍沿用了 R32 已命中文件集合，未覆盖无扩展名头文件。发现后没有
   接受该中间数字，而是把原始阳性源码 RPM 的所有文本文件纳入重扫；最终表来自
   后一次成功运行。
5. 首次直接执行 `progress/R110/run_logged.sh` 时，因文件没有执行位返回 126，
   shell 报 `Permission denied`。这是包装器调用方式错误，校验器尚未运行，不是
   数据判据失败。第二次虽改用 `bash`，但把编号和标签合成了一个参数，包装器因而
   直接执行无执行位的 Python 文件，再次返回 126。随后按包装器要求将编号、标签
   分开，并由 `python3` 显式执行校验器。
6. 校验器首次真正运行时，使用了与表头实际枚举值不同的两个名称，断言退出 1；
   表中实际值为 `ACTUAL_CATCH_CLAUSE` 与 `NON_CLAUSE_TOKEN_LINE`。仅修正校验器的
   枚举名称后重跑，未改任何扫描表或计数。第二次校验因要求方法文档逐字包含
   `CONFIRMED_RETHROW` 而退出 1；该术语已在报告中定义，方法文档实际直接引用
   `guard_status()`。将文档存在性检查改为其实际术语后重跑，同样未改数据。
7. 第一次提交前执行 `git diff --check` 时把逐字保存的历史命令输出也纳入检查，
   因原始日志内本就包含行尾空白而返回 2。原始输出按纪律不得改写；随后仅对本轮
   编写的 Markdown、TSV 与校验代码做格式检查，原始日志继续原样归档。
8. 归档后的校验器第一次从 `docs/progress/R110/code/` 执行时，按原开发目录层级
   推算项目根路径，形成重复的 `docs/progress` 路径并退出 1。改为向上寻找 `.git`
   确定项目根；校验逻辑及数据均未改变。

所有失败原文和退出码均保留在 `raw/`，没有删除或覆盖。
