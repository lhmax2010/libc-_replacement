# 外部组件缺口的性质与所需材料

## 结论边界

本轮把缺口拆成八类，并逐类写明所需材料与职能责任方。外部产品/应用的真实分母仍为 `NOT_AVAILABLE`，但已有两组标准镜像安装清单可作为间接材料：14 份清单共 5,995 条成员记录，另 6 份清单共 4,399 条成员记录。它们来自与当前冻结仓不同的快照身份，不能充当当前外部 BOM，也不能覆盖仓外应用、供应商载荷或现场下发组件。

因此当前能够核实的最强表述仍是：

> 在 Base/Unified 冻结仓的 1,424 个源码完整记录、24 个部分记录的可见内容、39,166 个已发布 ELF 和 8,911 个已发布静态归档中，没有发现 `std::wbuffer_convert` 使用者。

不能写成“平台上没有使用者”。不随迁移重编组件同理：前三类仓内材料已有发现上界，外部一类没有分母，所以不存在全平台有限上界。

## 现有覆盖

### 冻结仓

仓库输入是 Tizen Base Toolchain 与 Unified Toolchain 的 `reference/repos/standard` 二进制仓和源码仓。平台没有跨四仓的单一快照号，身份由四个 `repomd revision + SHA256` 共同冻结：

| 仓 | revision | repomd SHA256 |
|---|---:|---|
| Base binary | 1785866115 | `1789528921ae67d70ba657c787899ec580ab0b17a8368a0245ec09440710cf16` |
| Unified binary | 1785904307 | `e425b6a91a3cfb2f67cbd73160ac48e2bb776e92866de81d5b97bb25e5ab39c3` |
| Base source | 1785866095 | `cf7fca47147304ec114e8e0c19f6f43353dbf973ee623d3eb5188919c509fe72` |
| Unified source | 1785904240 | `f15c6854277fb975d6d5e52d9a33c120eb85bb5cdc726acdf4243026098fde59` |

该复合快照含 1,450 条源码 RPM 记录和 11,332 条二进制 RPM 记录；二进制载荷中读到 39,166 个 ELF，其中 36,829 个是非 debug 路径的运行时 ET_EXEC/ET_DYN。源码专项覆盖为 1,424 完整、24 部分、2 个上游源码不可得；目标可见命中为零。已发布静态归档为 8,911 个路径。

对“不重编组件”的仓内清点还包括：5 个已确认复制安装的 `pen-wave` 共享对象、1,027 个含共享库候选的源码包（发现上界）、8,911 个已发布静态归档、3,236 个源码包内对象候选；其中 21 个对象有生产构建规则引用。这些计数的单位和集合会重叠，不能相加。

### 可得的镜像安装清单

两组历史/相邻快照材料合计 20 份 `.packages` 文件：

| 清单组 | 文件 | 成员行 | 去重 name+arch+version-release | 与当前冻结仓 exact 行 | 当前仓有同 name+arch 的行 |
|---|---:|---:|---:|---:|---:|
| reference standard 组 | 14 | 5,995 | 2,773 | 3,964 | 5,977 |
| toolchain 成对快照组 | 6 | 4,399 | 2,632 | 3,763 | 4,399 |

后一组覆盖 headed/headless/boot 的 armv7l 与 aarch64；前一组还包含若干 HAL、实时和板型 boot profile。版本精确不一致说明这些清单不能与当前冻结仓拼成严格同源 BOM。它们能证明本地存在“按 profile 投影仓库包”的可行输入格式，也能提供历史规模下限，不能证明仓外组件不存在。

把这些清单中与当前仓版本精确一致的成员映射到源码专项缺口，出现 283 条 profile 成员记录，涉及 57 个二进制 name/arch/version 和 14 个部分覆盖源码 RPM；没有映射到两个源码不可得包。这只是对可得 profile 的定位，不会补回缺失源码，更不是外部分母。

## 覆盖不到的类别与规模

逐类结果见 `tables/w1_gap_material_matrix.tsv`。无法估计的根本原因不是缺少推算公式，而是缺少总体定义和身份：产品 profile、架构、版本、地区、时间点及受支持安装来源均未固定。仓库是“可安装集合”，镜像清单才是“某 profile 的选择”，应用商店和现场组件又是独立且随时间变化的集合；三者不能用一个包数互相替代。

外部组件可能使用目标类型的概率不能量化。现有事实只提供方向性依据：该类型属于旧式宽字符编码转换设施；完全内联、静态链接、剥离、LTO、生成源码和类型擦除都可能令最终符号不可见。没有组件清单、源码和构建身份时，既不能因类型已弃用而推断无人使用，也不能为外部使用给出数值概率。

## 需要索取的材料

最小可执行请求应按“产品 profile + 架构 + 版本”发给产品镜像集成/发布团队，要求：

1. 与冻结 Base/Unified 身份同源的最终镜像 BOM，至少含包名、架构、NEVRA、载荷 SHA256 和来源；
2. 系统仓以外的预装、供应商、HAL、应用、插件及运行时下载组件清单；
3. 对应最终 ELF、静态归档和可加载模块，优先同时提供未剥离文件、DWARF、link map 或符号清单；
4. 组件源码、生成源码、依赖锁文件和编译数据库；
5. 逐组件“随迁移重编/保留旧二进制”的声明，以及 OTA、回滚和旧版本支持窗口。

材料责任方及每项材料能闭合的结论见矩阵。若只能取得 BOM 和最终二进制，可以量化外部分母并做符号/载荷扫描，但仍不能把模板零符号提升为源码级零使用；若再取得源码与构建材料，才能核实内联和生成路径；若再取得重建策略，才能量化不重编组件。

## 替代手段实测

- **安装清单反推：部分有效。** 对 20 份本地清单逐行解析并与当前冻结仓 11,332 条记录对照，结果见三个 `w1_image_manifest_*.tsv` 表。它能缩小特定历史 profile 的仓内选择，不能覆盖仓外载荷，也不能跨快照拼接。
- **依赖声明反推：只适合定位，不能证明目标类型使用。** RPM Requires/BuildRequires、ELF `DT_NEEDED` 和 UND/DEF 可说明包或动态库依赖；`wbuffer_convert` 是头文件模板，依赖边不携带“是否实例化该类型”的完备信息。既有源码、ELF 和归档专项扫描比依赖名称更直接，但仍受内联/剥离等边界限制。
- **许可证/SBOM 反推：当前不可用。** 对 git 跟踪文件名搜索 SBOM、Bill of Materials、CycloneDX 和 SPDX，结果为零、退出码 1；同一 `git ls-files | rg` 管线以 `manifest` 为正向对照取得命中，排除了空文件集和失效规则。较宽的 license/notice 搜索只找到发布通知、镜像清单和一份评审备忘，不是机器可关联的产品组件许可证清单。
- **VCS 字段反推：只能识别来源。** `.packages` 行带项目路径和提交标识，可协助向源码 owner 索取材料；它不包含最终载荷 SHA、运行时下载项或重编策略。

没有任何替代手段把外部分母闭合。缺口已被分解为可索取的具体输入，但结论强度没有越过“已覆盖范围内成立”。
