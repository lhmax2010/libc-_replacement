  `codex/runtime-validation`**(那是运行时验证线);

  是本地准备的源码树与配置;**`codes/` 为只读**,
  需修改时复制到 `tmp/` 下操作;

**当前状态**

Base 层需要适配的 11 个包中,**8 个已完成并推送**
(`abseil-cpp`、`boost`、`icu`、`jsoncpp`、`libsigc++`、`pcre`、
`taglib`、`tensorflow2`),各自位于
`sandbox/lhmax2025/libcxx-migration` 分支。

与 libc++ 编译的新代码符号不匹配(`std::__cxx11` 对 `std::__1`),
链接 `libLLVM.so.22.1` 时失败。

# W1:重新生成基于 libc++ 的 MLGO / XLA AOT 资产

**时间上限**:8 小时　**构建**:需要

## 背景

LLVM 包中捆绑的 MLGO / XLA AOT 预编译对象按 libstdc++ ABI 生成。
当 LLVM 改用 libc++ 构建时,新编代码与这些对象的符号不匹配 ——
前者 `std::__1`,后者 `std::__cxx11`,在符号名层面是不同的实体。
链接 `libLLVM.so.22.1` 失败。

此前评估认为这些资产"无法可靠重生成",因为缺少 SavedModel、
准确的 TensorFlow revision、生成脚本与构建环境。
**这些材料现已定位。**

**材料位置**(Gerrit `platform/upstream/tensorflow2` 仓):

| 分支 | 内容 |
|---|---|
| `sandbox/lhmax2025/mlgo_aot_v3` | 编译 AOT 所用的代码 |
| `sandbox/lhmax2025/mlgo_aot_temp` | 模型、脚本与操作指南 |

## 执行

1. **先读指南,再动手**:
   a. 拉取上述两个分支到 `codes/` 下;
   b. **完整阅读 `mlgo_aot_temp` 中的操作指南**;
   c. **申报你的理解**:生成流程是什么、需要哪些输入、
      产出什么、耗时与资源需求如何;
   d. **若指南与实际材料不符,或缺少必要输入,停下报告**,
      不要自行推断补全;

>> 第 1 步完成后停,报告你的理解与计划,等待确认再动手生成。

2. **生成资产**(经确认后):
   a. 按指南生成,**目标是使用 libc++ 的版本**;
   b. 三架构分别生成还是一次生成,按指南实际情况执行并申报;
   c. 记录完整命令、耗时、产出文件及其校验值;

3. **核验产物**:
   a. 新生成的对象**是否使用 `std::__1`**(而非 `std::__cxx11`)?
      给出符号证据;
   b. 与原有资产逐项对照:文件数、接口符号是否齐全;
   c. **缺失或多出的部分逐项说明**;

4. **若生成失败或结果不符预期**:
   **停下报告,不要用旧资产凑合,也不要修改 LLVM 侧代码去迁就**;

## 输出

指南理解与计划、生成过程与产物、符号核验结果;
结论三选一:`ASSETS_REGENERATED`(附核验证据)/
`PARTIAL`(附完成部分与阻断点)/ `BLOCKED`(附原因与所缺材料)。

# W2:完成 llvm / bcc-tools / bpftrace 的适配

**时间上限**:6 小时　**构建**:需要
**前置**:W1 产出可用的资产

## 背景

这三个包必须按顺序处理,不能分开:

```
libcxx-runtimes → llvm → bcc-tools → bpftrace
```

依据是实测符号数:`bcc-tools → llvm` 584 个、
`bpftrace → llvm` 201 个 C++ 符号,均已证明布局敏感;
LLVM 自身不同子包间另有 17,589 个。
**只切换链条一端,这些边界会从"两侧一致"变成"两侧不一致",
部分迁移的风险高于不迁移。**

改法设计已定(见 `docs/progress/R104/IMPLEMENTATION_DESIGN.md`):

- 启用判据:仅当 `_toolchain` 已定义且 `toolchain_is clang` 时启用;
- `llvm` 用原生 `LLVM_ENABLE_LIBCXX=ON`,
  **不设置 `CLANG_DEFAULT_CXX_STDLIB`** ——
  只改变 LLVM 工具自身的运行时,不改变产出 Clang 的默认标准库;

## 执行

5. **若 W1 未产出可用资产**:
   本任务记 `NOT_AVAILABLE` 并说明,**直接进入 W3**;

6. **按顺序实施**,每个包完成后再动下一个:
   a. `llvm` —— 用 W1 的新资产;
   b. `bcc-tools`;
   c. `bpftrace`;

7. **`llvm` 的验证必须包含一项专门检查**:
   用新构建的 clang 执行 `-###`,分别测试
   **不指定 `-stdlib`** 与 **显式指定** 两种调用,
   确认**产出的编译器默认标准库未被改变**。
   这是设计阶段就承诺要实测的一格,**不能只凭设计推断**;

8. **每个包的验证**:
   a. 三架构 × libc++/GCC 六格;
   b. libc++ 路径下产物依赖 `libc++.so.1`;
   c. GCC 路径下构建不受影响 —— **实际跑,不能只看设计**;
   d. 四个补丁相关的既有行为未被破坏(若适用);

9. **推送**:
   a. 验证全部通过才推;
   b. **任一包验证失败,该包不推并报告** ——
      不要因为其他包过了就一起推;
   c. **若 `llvm` 那格出问题,后两个不要继续**;
   d. 推送前后各记录一次分支状态;

## 输出

逐包的改动、六格验证结果、`llvm` 的 `-###` 专项检查结果、
推送记录;结论:`THREE_PACKAGES_COMPLETE` /
`PARTIAL`(附完成与未完成)/ `BLOCKED`(附原因)。

# W3:Unified 侧编译失败的初步归类

**时间上限**:3 小时　**构建**:不需要(只读分析)

## 背景

总部近期的 Unified armv7l 全量构建中,**17 个包失败**:

```
lapack, tidl, noise-suppression, openblas, onnxruntime,
tensorflow2, openusd, protobuf, lottie-player, yaca,
libcynara-commons, rive-tizen, glog, c-mock,
docker-launcher, hdf5, hailo-rt
```

**已知一条线索**:其中 `lapack`、`openblas`、`onnxruntime`、`yaca`
四个包在 LLVM Toolchain 仓中设有 `_toolchain_override gcc`,
即以 GCC 构建;而 Unified 的 project_config 全局注入了
`-stdlib=libc++`,**该选项 GCC 明确拒绝**。

**待验证的假设**:这四个包的失败源于全局注入的选项打到了
GCC 构建路径上。

**注意**:该轮构建只跑到 449/1034 即因调度器异常退出而中止,
**其余 585 个包从未构建**,因此这不是全平台的完整结论。

## 执行

10. **本任务只做归类,不修复**:
    a. 若能取得那 17 个包的失败日志,逐个查明失败原因;
    b. **若日志不可得,如实说明**,并基于现有信息给出可能的分类;
    c. **不要用旧快照的日志冒充本轮证据**;

11. **归类**:
    a. 因全局注入的 Clang 选项打到 GCC 路径而失败的;
    b. 属既有的 45 个需改源码的包;
    c. 环境或基础设施原因;
    d. 其他 —— 逐个说明;

12. **一项可现在做的验证**(不需要本轮日志):
    直接用 GCC 与 Clang 分别试 Unified project_config 注入的那组选项,
    确认哪些被接受、哪些报错、**哪些被静默忽略**;
    **「静默忽略」这一类要专门标出** ——
    那种情况会编过但产物不对,比直接失败危险;

13. **不做修复、不做处置建议**;

## 输出

失败原因归类(或说明日志不可得)、选项探针结果、
静默忽略项的专门说明;
结论:`CLASSIFIED`(附分类)/ `PARTIAL`(附缺失材料)。
