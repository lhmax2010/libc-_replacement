【任务】R43b:上游测试套件基线 + 标准库层防护缺失实测

本任务合并两部分:
- **A 部** 跑 libc++abi 自带的回归测试(此前从未跑过,零成本、
  上游认可的判据),同时作为 B1 缺陷的判定实验;
- **B 部** 即原 R43,验证 libc++ 标准库自身缺失 forced-unwind
  防护(原 R43 因资源门禁红停,未执行任何步骤)。

【资源门禁(参数按构建量分档,本任务为"轻档")】
═══════════════════════════════════════
原 R43 因 `MemAvailable=7,934,588 KiB` 低于 8 GiB 硬阈值而红停,
差 0.7%。8 GiB 是为 runtimes-only 完整构建设定的;本任务复用 R42
已有产物、**不重建 libc++abi**,峰值仅为若干测试件的编译,故按
轻档执行:

1. 门禁须为**独立可执行脚本**,先经 `bash -n` 与一次干跑验证;
2. **轻档阈值**:可用内存低于 **2 GiB** 返回非零;1 分钟负载高于
   CPU 核数的 **1.5 倍**返回非零;两项用不同退出码区分;

   误执行了一次只读板端 preflight,本次须避免;

6. 执行期间每 5 分钟采样 `free -h`/`uptime` 落盘;
   **可用内存低于 1 GiB 立即终止**,记 `RED_STOP_RESOURCE`;
7. 开工前落盘 `top -bn1 | head -20`。

A 部:上游自带回归测试
═══════════════════════════════════════
【背景】libc++abi 自带 `test/forced_unwind{1,2,3,4}.pass.cpp` 与
`test/unwind_0{1..6}.pass.cpp`,是上游认可的回归判据,**本项目此前
从未运行过**。其中 `forced_unwind1.pass.cpp` 的 `test()` 正是
`catch (...) { bits |= 2; throw; }` 形态——即评审方指出的 B1 缺陷
(catch-all 重抛在 armv7l 上会 terminate)的现成判定实验。

**已知障碍**:`forced_unwind1/2.pass.cpp` 在 ARM 上编译失败,因其
使用 `struct _Unwind_Exception*` 而 ARM 上该名为 typedef
(LLVM #53849,仍 open)。**允许修改上游测试文件的这一处以使其可编译**
——这是修被测试的适配,不是修被测代码,须逐处 diff 申报。

A1. 测试清单与适配:
   a. 列出 `codes/llvm/libcxxabi/test/` 下与展开/强制展开相关的
      全部测试文件;
   b. 对 ARM 编译失败者,给出最小适配 diff(仅改 `struct
      _Unwind_Exception*` → `_Unwind_Exception*` 之类的类型写法),
      **不得改变测试逻辑与判据**;逐处申报;
   c. 若某测试因其他原因无法在本环境运行,如实申报 NOT_AVAILABLE;

A2. 运行矩阵(每格记录完整输出与退出码):
   | 维度 | 取值 |
   | 架构 | x86_64 宿主原生 / armv7l 板上(**不用模拟器**) |
   | libc++abi | **未打 R42 补丁** / 打 R42 补丁 |
   | 测试 | forced_unwind1-4、unwind_01-06 |
   a. 四种组合逐一运行,逐测试记录 pass/fail 与完整输出;
   b. **重点关注 `forced_unwind1`**:其 catch-all 重抛形态是否在
      armv7l + 打补丁的组合下失败?失败信息是什么?
   c. 与 libstdc++ 的行为对照(若该测试可在 libstdc++ 下构建运行;
      不可则说明原因);

A3. A 部结论:

B 部:libc++ 标准库层防护缺失实测
═══════════════════════════════════════
【背景】libstdc++ 在其自身头文件与库中有约 65 处 `__forced_unwind`
防护(评审方给出,须本任务复核),典型形态
(`bits/ostream.tcc:81-87`):

    __catch(__cxxabiv1::__forced_unwind&)
      { this->_M_setstate(ios_base::badbit); __throw_exception_again; }
    __catch(...)
      { this->_M_setstate(ios_base::badbit); }

libc++ 侧对应位置为裸 catch-all(评审方 grep 为零命中)。**这些位置
内联进每一个消费者**,因此 R32 的"10 包 50 处 / 90 包 3364 处"是
应用代码口径,完全覆盖不到标准库这一层。

B1. 静态复核(只读):
   a. 在 `codes/gcc/libstdc++-v3/` 下检索 `__forced_unwind` 全部
      出现位置,逐条 file:line 与上下文;区分**防护子句**
      (catch 该类型并重抛)与其他用途(类型定义、声明、注释);
      给出防护子句的实测计数与文件分布,与"65 处 / 16 文件"对照;
   b. 在 `codes/llvm/libcxx/include/` 与 `src/` 下检索
      `forced_unwind`,给出命中数(预期零,须实测);
   c. 对第 a 步每一处防护,**定位 libc++ 中的对应代码位置**,
      给出 file:line 与实际写法;无对应者标注说明;
   d. 逐处判定该位置在 libc++ 下是否会吞掉强制展开,判据须明确;
   e. 特别核查 `ios_base::__set_badbit_and_consider_rethrow()`:
      其 `throw;` 的触发条件、默认配置下是否触发;

B2. 运行时实测(**本部核心**):
   用例形态硬性要求(逐条遵守):
   - 线程函数**非 noexcept**,调用链上无 noexcept 帧;
   - 用**裸 `pthread_create`**,不用 `std::thread`;
   - 取消点明确(依赖 I/O 调用自身的取消点,或显式
     `pthread_testcancel()`);
   - **应用代码中不得有任何 catch**——本部测的是标准库内部的
     catch-all,应用层加 catch 会掩盖现象;
   - 每格 **libstdc++ 与 libc++ 各跑一遍**。

   a. **核心格(优先级最高)**:一个线程循环
      `std::cout << i << std::endl;`,另一线程反复 `pthread_cancel`;
      记录退出码、完整 stderr、join 返回值;
      **明确回答**:libc++ 下是否出现 `FATAL: exception not
      rethrown` 并 abort?libstdc++ 下是否正常取消
      (join 返回 `PTHREAD_CANCELED`)?
   b. `std::cin >> x` 或 `std::getline` 阻塞时被取消
      (用管道或文件保证 read(2) 实际阻塞);
   c. `std::packaged_task` / `std::async` 内部被取消;
   d. `std::string::shrink_to_fit` 等含裸 catch-all 的路径
      (难以构造取消时机则如实申报 NOT_OBSERVED);
   e. **对照格**:不经标准库 I/O 的纯计算循环 +
      `pthread_testcancel()` —— 确认取消本身正常;
   f. 架构:x86_64 原生(必做)+ **armv7l 板上(必做)**;
      每格申报执行方式,**不用模拟器**;
   g. **与 R42 补丁的关系**:上述用例在**打了 R42 补丁**的
      libc++abi 下同样跑一遍。明确回答:补丁是否改变这些场景的
      结果?(预期不改变——补丁提供的是识别类型,而 libc++ 头文件
      根本没有使用它的 catch 子句;须实测确认)

B3. 影响面估算(只读,基于既有数据):
   a. 371 个源码包中,有多少包使用了第 B1 步识别出的防护所在的
      标准库设施(iostream / future / basic_string 等)?给出判定
      方法与计数;
   b. 其中有多少同时具有线程/取消迹象(沿用 R32 判据);
   c. **申报该估算的局限**:头文件代码内联进消费者,源码扫描无法
      精确定位,本项为近似;
