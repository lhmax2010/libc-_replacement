# W1 源码与已发布文件核查

## 结论

`PARTIAL`。在可得平台源码、39,166 个已发布 ELF，以及既有 8,911 个静态归档证据中，未发现平台调用方使用 `std::wbuffer_convert`。这证明“已覆盖材料内为零”，但材料缺口使其不能升级为“全平台不存在”。

## 方法与分母

源码侧使用保留全部上下文的词法检索。它覆盖直接限定名、`using` 声明、类型别名、`typedef` 和模板参数中仍保留该标识符的写法；逐条分类表用于区分标准库实现、自测、文档和潜在平台调用方。

- 本轮对 360 个低体量源码根重新执行：命中 0。
- R87 已覆盖冻结语料的 371 个源码包；R92 对 C++ ELF 缺口补充了 136 个完整源码包和 2 个部分源码包，另有 2 个仅包装材料不可得。
- 另有 965 个源码 RPM 因没有 C++ ELF 指标而未纳入源码深扫。它们不能被当作已证明无调用。

已发布文件侧直接解析冻结 R11 清单中 ELF 的 `SYMTAB` 和 `DYNSYM`，对 Itanium 符号名检索目标类型，再统一解码。本轮分母为 11,332 个包记录、39,166 个 ELF；命中 0，解析失败 0。既有 R87 静态归档分母为 8,911，目标命中同样为 0。

## 正向对照

正向对照源码通过别名实例化目标类型，并生成共享库：

- 同一源码扫描器得到 1 条命中；
- 同一 ELF 扫描器得到 34 条符号表记录；
- 独立的 `nm` 与解码检查也确认目标类型存在。

因此，零命中不是空规则、错误根目录或解码器失效造成的。

## 边界与误差方向

源码方法会漏掉由宏在外部生成、仅存在于未获取依赖、私有产品源码、加密材料或运行时生成代码中的使用。二进制方法会漏掉完全内联且未发射符号、完全剥离、LTO 消除、类型擦除、非 Itanium ABI 或 JIT 生成的使用。因此二进制零命中只能与源码覆盖合并解读。

本轮最初两次全根读取因范围过宽而技术性中止，退出码均为 130；扩展名过滤并按既有覆盖证据拆分后，最终读取成功。技术中止不计为验收失败，原始记录均保留。

由于实际平台调用命中为零，没有可供逐项分析的同步行为或异常传播路径。
