# W3 异步取消路径与正交行为验证

## 结论

`CONFIRMED_ON_X86_64`。两个指定组件都存在“启用异步取消的线程可条件进入 C++/用户代码”的静态路径；独立探针进一步确认，即使完全避开本补丁修改的五个位置，仅由另一个标准库 `noexcept` 等待接口形成的库帧，也会在异步取消展开时进入 `std::terminate`。因此该性质不是四补丁引入的特例。

armv7l 本轮为 `NOT_OBSERVED`，属于可选架构，未影响 x86_64 验收。

## 两个组件的静态可达性

### lightweight-web-engine 1.4.0-1

`WorkerThread` 创建 `std::promise`/future 和 `std::thread`，线程入口初始化后进入 `WorkerHost::run`；初始化设置异步取消模式，销毁路径请求取消。`WorkerHost::run` 随后执行事件循环并调度 worker 工作。

结论是“条件可达”而非“固定必达”：固定框架路径本身已经操作 C++ 共享状态，而事件循环回调还能进入任意 worker 功能；是否恰好进入某个 libc++ 等待/析构点取决于当时调度的任务和取消时机。

### llvm/openmp 22.1.8-18.1

在 `KMP_CANCEL_THREADS` 路径下，worker 与 monitor 入口设置异步取消模式，终止路径请求取消。worker 随后进入 `__kmp_launch_thread`，该循环最终通过 `t_invoke` 调用应用 microtask；因此应用的 C++ 代码可在该可取消线程上运行。

这里同样是条件可达：OpenMP 固定调度与 monitor 等待主要使用 pthread 原语，本身没有证明必经本补丁的五个位置；可达性来自应用 microtask。静态证据没有把“可能进入”提升为“每次必然进入”。

## 正交探针设计

探针选择 C++20 `std::atomic<int>::wait`，它不属于 D01–D05，补丁头文件中仍声明为 `noexcept`。线程入口是普通的、可抛出 C++ 函数，没有用户添加的 `noexcept` 调用链帧；线程由 pthread 直接创建。

每次测试同时检查：

1. 正常路径修改原子值并通知，线程必须正常返回；
2. 取消路径在子进程中等待线程真正进入阻塞点，再发出异步取消；
3. 自定义 terminate handler 只写固定管道标记并以 86 退出；
4. 父进程必须同时观察到精确标记与退出码 86，意外正常返回使用不同标记和退出码。

子进程隔离使一次 terminate 不会终止测试控制器。`-O0 -fno-inline` 以及二进制符号复核用于避免只依赖源码推断。

## 证明范围

本实验确认 x86_64 上的行为性质，并确认两个组件的源码可达形状。它不证明某个具体产品工作负载一定在取消瞬间位于该接口，也不替代 armv7l 实机观测。
