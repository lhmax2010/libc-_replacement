# 应用与平台跨 C++ 标准库边界：事实、方案与未决条件

**待人工审阅；部分目标实测未完成，不作为兼容性验收。**

平台准备使用 libc++，部分应用/插件可能仍用 libstdc++。二者都是 C++ 标准库，但“同一种源码类型”不保证对象的内存结构、异常或销毁方式相同。ABI（应用二进制接口）指这些编译后仍须一致的约定。本文区分应用直接接触的边界和平台组件内部边界，不把所有 C++ 接口或所有应用一概判为不能支持。

本轮四组目标均为 **PARTIAL**。取得了 Native 代表包装的 8 个最终 ELF（可执行格式）及独立双库转换桥的实测；EWK、引擎插件回调和 binder/Dali 尚没有有效的双方向接口值矩阵。最关键的环境疑问是产品应使用 `elementary` 还是 `elementary-tizen` 依赖，以及匹配的完整运行环境。没有为跑完而选择产品变体，也没有用模拟组件填补结果。

## 已实测的转换桥机制

shim 指中间的适配代码。两个编译单元（分别编译的源文件）各使用一套标准库，中间只传 C 可表达的指针、长度和状态，不传 std 对象。

本轮用**真实平台 Boost.Program_options** 的原函数 `to_internal(const std::wstring&) -> std::string` 验证该机制，而非自写解析 provider（被调用的实际组件）。两个方向各 5 次，同侧正向控制各 5 次，共 **4 格/20 次运行**；每次 5 项具体内容比较，共 **100 项**。空串、ASCII、中文/补充平面字符、内嵌 NUL、长串的返回字节数为 **0、9、11、3、257**，逐字节相等。每次 maps 核实两套库及准确 provider；真实 callee 路径与退出作用域后的检查点也保留。

结论仅为 **SHIM_VIABLE（固定普通输入、x86_64 原生）**。它没有证明三个目标的适配完成，也没有验证异常、取消、所有权转交、泄漏或任意部署环境。样本通过复制后在各自一侧销毁 std 对象，**不是把提供方 std 对象交给另一库直接 delete 的成功试验**。[逐次矩阵](../W2/matrix.json)、[代码与完整解释](../W2/REPORT.md)、[库与产物身份](../W2/identity.json)。

## ewk_parse_cookie

### 事实链

1. **静态核查**：真实公开候选头的参数为 `const std::string&`，输出结构含 domain、name、path、value 四个 string，整个声明位于 `extern "C"` 中。[原始声明](../../P7_0909/stage2/snapshots/evidence/chromium-efl/55f75e1f273b_ewk_cookie_parser.h)。
2. **静态 ELF 核查**：真实 libchromium-ewk.so 导出 `ewk_parse_cookie`，并有 GNU string 的导入。C 链接名称没有把上述 string 的具体布局编码进去。[符号原文](../W1/raw/009_ewk_symbols.stdout)。
3. **独立样本实测，非此 provider 的尺寸测量**：本轮应用 string 的 sizeof 为 GNU 32、libc++ 24 字节。这说明不能用名字“std::string”推断本轮两种类型布局相同；不能把这个尺寸直接当成所有产品/编译宏的尺寸。[GNU 样本](../W2/raw/gnu_to_cxx_shim_1.stdout)、[libc++ 样本](../W2/raw/cxx_to_gnu_shim_1.stdout)。
4. **推断**：只按 C 名称链接，不会替调用者检查对象内部哪一段是指针、长度或缓冲区。若真实两端按不同布局解释同一对象，可能读错值或破坏内存；“链接成功”本来就不足以排除它。
5. **未观测**：本接口实际消费方的跨库链接/调用、四字段错值或正确值、销毁、两个方向与同侧控制均尚未完成。已解包真实实现，但加载止于产品依赖选择。[诊断及停止点](../W1/load_results.json)。因此链条不能续写成“实测错值 5/5”。

### 已排除与尚不能排除的形态

以自定义结构强制冒充原签名的 std::string，不会建立真实类型的不变量与生命周期，不能据此承诺兼容。只改 `extern "C"` 或只加符号版本也不会转换四个对象。单 TU 用同一种 std 定义直接解释两个布局不能完成转换；但单进程链接两库并非不可能。

双 TU 桥尚未排除；这里还要证明同名 C 入口如何找到真实 provider 而不递归或错误绑定。不能用本轮靠不同 C++ 修饰名分流的 Boost 样本跳过这一步。两个项目的实现也不构成“任何双版本导出都不可能”的证明。[机制与源码依据](../W2/REPORT.md)。

### 什么证据能改变判断

若证明实际产品两端没有跨标准库边界，或对其确切布局、生命周期及调用路径建立兼容证明并以真实双向/同侧/销毁矩阵验证，则当前不作兼容承诺的依据可以改变。**仅 sizeof 相等不足以证明兼容**。若能证明该 API 不在应用 SDK 中，应调整应用直接影响范围，而不是抹掉接口内部的类型事实。

## SetSyncBinaryReply

### 事实链

1. **静态核查**：实际接口表的槽是 `void (*)(XW_Instance, const std::vector<uint8_t>&)`；不是只传原始字节。[声明](../../P7_0909/stage2/snapshots/evidence/webapi-plugins/353da9cbd3a2_XW_Extension_SyncMessage.h)。
2. **静态核查**：插件 `Instance::SendSyncBinaryReply` 调用 `g_sync_messaging->SetSyncBinaryReply(xw_instance_, reply)`；方向是**插件调用引擎提供的函数指针**，不可倒置。[真实调用点](../../P7_0909/stage2/snapshots/evidence/webapi-plugins/e4597e6f32ca_extension.cc)。
3. **独立样本实测**：本轮两种 vector<uint8_t> 的 sizeof 都为 24 字节。这既不能证明其全部不变量/编译模式兼容，也不能支持“大小必不同所以已坏”的说法。[尺寸原文](../W2/raw/cxx_to_gnu_shim_1.stdout)。
4. **推断**：函数指针槽不会因为两侧 std 定义不同自动插入转换；实际是否错读需要正确注册方向及真实实例的运行结果。
5. **未观测**：真实引擎回调上下文、两方向长度/字节/销毁与同侧控制尚未建立。未用自写回调替代引擎，故当前没有实际错值/正确值结论。[范围记录](../W1/REPORT.md)。

### 已排除与尚不能排除的形态

把回调表包在 `extern "C"` 中不会消除 vector 参数；把旧表槽强制转成 `(data,length)` 类型不保持旧 ABI。只测模拟接收函数或反向回调也不能验证真实边。新版本 C 数据表或真正插入注册路径的双 TU 桥尚未排除；需要引擎和插件共同定义版本、数据有效期及错误契约。

### 什么证据能改变判断

真实两端精确版本在正确回调方向下完成双向内容、长度、生命周期与控制矩阵，可提升固定组合的结论。若证明生产不使用这个槽、或两端本来使用同一套 std，应相应缩小影响。不能因一次未崩溃或 vector 大小一致，就宣称全部插件安全。

## binder 与 Dali

### 事实链

1. **静态核查**：C# 应用通过 C 名称/句柄进入 binder；这不等于 C# 应用直接传入 Dali C++ 类。[托管与原生证据索引](../../P7_0909/stage2/DALI_NUI.md)。
2. **静态核查**：`CSharp_Dali_View_New` 内部调用 `Control::New`，复制构造并分配 Control；`CSharp_Dali_delete_View` 做删除。binder 导入 core/adaptor/toolkit，并从其原生 C++ 接口取得对象。[完整 wrapper](../../P7_0909/stage2/snapshots/evidence/dali2-csharp-binder/b0487e765ad5_control-wrap.cpp)、[ELF 依赖原文](../../P7_0909/stage2/raw/elf_dali2-csharp-binder_libdali2-csharp-binder.so.2.0.0_dynamic.stdout)。
3. **推断**：内部对象操作依赖匹配的类、虚调用、引用计数和生命周期约定；应用外侧的 C 包装不能自动证明内部一致。但“内部是 C++”也不能自动证明它传标准库对象或混库必失败。
4. **未观测**：加载依赖诊断批次未到有效 Control::New 对照；混用后具体值与销毁未测。**目前不能判定必须同批迁移，也不能判定分批迁移安全。**

### 已排除与尚不能排除的形态

只改/只测 C# 应用入口，没有验证真正的 binder/Dali 边；只让创建函数返回另一种对象，再让其余 wrapper 按原 Control* 解释，不是完整适配。单纯 string/vector 复制桥也不覆盖该对象图。

内部 C 句柄加操作协议、原生组件协调迁库以及对象级适配尚未排除，代价须包括所有继续解释句柄的 wrapper，而非只改 New。应用直接链接 Dali C++ 的 Native 路径是另一条边，不能自动享有 NUI C 绑定的隔离。

### 什么证据能改变判断

真实 binder/Dali 两方向在有效初始化上下文中完成代表对象操作、精确状态及销毁，或证明相关生产组合根本不异构，可改变当前限制。完整类/对象关系证明与更广操作覆盖会增强结论；单看 C# P/Invoke 或一个导出名不足以证明内部安全。

## Native 四族：所选边为什么不同

**静态核查 → 实际编译/链接**：app_control.hpp 的 Set/GetOperation 在头内转换 string 与 C 字节；AppBase::GetId 从 C char** 得到数据后在调用侧建 string；UiAppBase/ServiceAppBase 用 C 回调表与 void* 调平台入口。两个标准库各编译四个代表用例，共 8 个最终 ELF；平台导入为对应 C 函数，本地 C++ 符号有正向控制可见。[逐个最终 ELF 结果](../W1/native_final_results.json)、[完整限制](../W1/REPORT.md)。

所选平台边可以归 C 数据类别，但**不是四族所有成员、任意用户回调或真实运行均已安全**。链接允许 provider 的传递未定义符号，尚未建立有效应用上下文；不把这 8 个编译成功写成“8 个运行样本通过”。C ABI、内存配对、回调不得把未处理 C++ 异常带到不匹配边界等条件仍需核查。

## 方案代价：由谁做什么

| 方案 | 平台/组件维护方 | 应用/插件维护方 | 当前能量化到哪里 |
| --- | --- | --- | --- |
| C 数据/句柄接口 | 定义字节/长度/容量/状态、创建释放与接口表版本；维护旧路径 | 直接 Native 使用者改调用；JS/C# 若上层契约不变，未必需改源码 | EWK 1 个头/1 声明；回调 2 个已定位文件/1 方法/1 槽；Dali 1 代表文件/3 函数。均是下界，不是全量工时 |
| 双 TU/object shim | 控制符号路由、每侧对象创建销毁、转换、异常与版本回归，承担复制开销 | 核对实际加载组合；是否不改源码取决于完整契约能否保留 | 固定 Boost 样本可行；目标专用改动量、复制时间/峰值内存未测 |
| 原生消费方迁 libc++ | 提供匹配的构建与发布组合 | 有源码且依赖可迁者重编/回归；无源码者不能凭此完成 | 未取得业务应用/插件清单，不能估比例或总人时 |
| 声明不支持的组合 | 明确同库/ABI 配置、旧接口支持范围与期限 | 确认是否满足限制及功能影响 | 声明不修复不匹配二进制；期限与功能取舍须业务确定 |

[逐接口四方案、候选 C 签名及计数出处](../W3/OPTIONS.md)。保留旧名字不等于保护旧 std 布局；两个标准库同时加载也不证明 C++ ABI 支持库/异常可任意混用。[Clang 官方说明](https://clang.llvm.org/docs/Toolchain.html#c-standard-library)。

## 本材料未覆盖与待确认

- 真实目标的两方向 5 次/格行为矩阵，以及有效引擎、Dali、Native 应用上下文；目标 libc++ provider 未取得。加载失败不是不兼容证据。
