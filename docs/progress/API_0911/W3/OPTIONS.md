# 四方案条件性评估：待业务裁决

## 前置限制

W1 四组均为 PARTIAL：没有目标接口的完整跨库运行矩阵。W2 仅在真实 Boost 的普通字符串转换上证明双 TU 桥可行。故下文对三组需要关注的非 C 数据/原生 C++ 边界作**条件性方案评估**，不冒称已找出三组“实测不能支持”的接口，也不替业务选择方案。Native 所选边是 C 数据形态，单列限制，不强行提出改造需求。

这里“接口不变”分两层：函数声明/导出可保持，不代表异常类型、别名关系、内存所有权、回调时序也保持。完整生产改造量、外部应用分母、迁移意愿与产品 SDK 最终白名单为 `NOT_AVAILABLE`；已试方法是 P7 冻结源码/头、SDK 配方及本轮真实 ELF 核查，它们不包含业务应用清单或部署策略。

## 1. ewk_parse_cookie

| 方案 | 平台侧要做什么 | 应用侧要做什么 | 条件、成本与未决项 |
| --- | --- | --- | --- |
| 改 C 数据接口 | 增加下面的字节接口；内部仍由真实 parser 解析；输出字段转换为调用方缓冲区。处理长度、容量、编码与日期范围错误 | 直接调用此 API 的原生应用改传 buffer/length，按状态取四字段；仅二进制且无源码的应用无法直接采用新声明 | 新入口可避免 std 对象交叉解释，但语义/错误路径未实现与验证；外部调用方数未知 |
| shim | 两侧 TU 在各自 std 定义下构造对象，中间传四字段字节和日期；必须解决 ewk_parse_cookie 同名 C 符号路由及避免递归 | 若完整保留导出与契约，可不改源码；仍需部署 shim/修改链接或加载安排，不能承诺所有旧二进制零操作 | W2 的不同 C++ 修饰名样本不能证明这里的同名寻址；复制与异常转换有额外成本，SHIM_UNCERTAIN |
| 应用改 libc++ | 平台交付匹配头、库、构建约束与可复核版本 | 应用方重编本身及所有跨 C++ 边界依赖并回归 | 有源码、工具链、依赖可迁者技术上可尝试；无源码/依赖供应商不配合者不能据此完成。没有逐应用清单，不能报比例 |
| 接受限制并声明 | 声明该 std-bearing 接口只在匹配标准库/ABI 设置下承诺，并说明旧入口与部署边界 | 应用确认实际绑定与 std 实现；不匹配时不能依赖该层承诺，可选择不使用该功能 | “同一套库”仍需 ABI 宏、版本、类型/生命周期一致；不是全面兼容保证 |

**设计签名（未实施）**：

```c
#include <stddef.h>
#include <stdint.h>
struct ewk_text_out { char *data; size_t capacity; size_t length; };
struct ewk_cookie_text_out {
    int64_t expiry_utc_seconds;
    struct ewk_text_out domain, name, path, value;
};
int ewk_parse_cookie_bytes(const char *input, size_t input_length,
                           struct ewk_cookie_text_out *output);
```

需写入契约：长度单位为字节；是否加 NUL、不足容量是否只返回所需长度、失败时各字段状态、输入输出能否重叠及会话 cookie 日期含义。输出内存由调用方持有，平台只按容量写入；这些是方案待定义事项，**不是已经具有的安全保证**。

**可定位改动点**：1 个已取得的头文件、1 个既有函数声明；真实实现位于组件中，但本轮没有展开其完整源码调用图。设计增加 1 个入口及 2 个 C 数据结构，是设计项数，**不是“平台只改 1 个文件/函数”**。完整平台文件/函数数 `NOT_AVAILABLE`。

**旧入口与期限**：若继续支持仍调用旧入口的二进制，就需要保留其可用路径或提供经验证的适配；保留一个同名导出本身不能转换旧 std 布局。是否放弃这批调用方、并存多久，需应用清单与支持周期裁决，本任务不指定期限。

## 2. SetSyncBinaryReply：插件调用引擎的函数指针

| 方案 | 平台/组件侧要做什么 | 应用侧要做什么 | 条件与成本 |
| --- | --- | --- | --- |
| 改 C 数据接口 | 引擎提供新版本接口表，插件取到后用 data/size 调用；保持真实实例映射和同步生命周期 | 普通 JS 应用若 JS 契约保持，可以不接触此 C++ 改动；原生第三方插件若使用此表，需要更新并重编 | 必须协同接口表生产方与消费方；不能在旧表中直接改函数指针类型后称兼容 |
| shim | 在真实 GetInterface/注册路径放入调用方匹配的适配表；接收其 vector 后转字节，另侧构造引擎匹配的 vector | JS 层通常无源码改动；原生插件的部署/加载依赖仍需核对 | W2 证明复制桥机制，不证明真实回调方向、实例、长度/所有权/时序；SHIM_UNCERTAIN |
| 应用/插件改 libc++ | 提供匹配引擎开发环境；协同插件及其依赖重编 | 这里主要是**原生插件维护方**，不是要求 JS 重编标准库 | 无原生插件源码或固定二进制依赖时不可直接完成；未知插件分母 |
| 接受限制并声明 | 声明原生引擎插件接口必须使用匹配 std/ABI 的构建组合 | JS 使用者不因此直接承担 C++ ABI；原生插件提供方遵守构建/版本约束 | 限制针对原生边，不泛化成“Web 应用不兼容” |

**设计签名（未实施，V2 新接口槽）**：

```c
/* XW_Instance 沿用已定义的整型实例标识。 */
void (*SetSyncBinaryReplyBytes)(XW_Instance instance,
                               const uint8_t *data, size_t length);
```

新接口必须明确数据仅在调用期间借用、还是接收方需复制保存；若异步留存，需要另一种生命周期协议。保留旧 V1 表能否继续工作取决于其 provider 是否仍理解旧 vector，不能只保留表名。V1/V2 并存期由引擎/插件版本清单决定，当前 `NOT_AVAILABLE`。

**可定位改动点**：`XW_Extension_SyncMessage.h` 1 个回调槽；`extension.cc` 1 个 `Instance::SendSyncBinaryReply` 方法内的引擎调用点，共 2 个已核文件。引擎表初始化/接收实现及其他消费者尚缺，不报告全量文件/函数数。“2 文件、1 方法、1 槽”是已定位点，不是完成估算。原文行及 SHA 见 [known_points.json](known_points.json)。

## 3. dali2-csharp-binder → Dali 原生边

应用 C# 经 C 名称/句柄进入 binder；binder 再调用 Dali C++。**不能从内部风险推导应用正在直接传 std 对象，也不能从应用经 C 边界推导内部已安全。** W1 尚未测到混用不同标准库的故障，因此“必须同批迁移”仍是待验证判断，不是本轮事实。

| 方案 | 平台/组件侧要做什么 | 应用侧要做什么 | 条件与成本 |
| --- | --- | --- | --- |
| 内部改 C/不透明句柄 | 把 Dali 对象创建、操作、引用计数与销毁集中到与 Dali 匹配的一侧；binder 改用新 C 适配层 | NUI C# 若现有导出名、参数与行为契约不变，可以不改应用源码；直连 Dali C++ 的 Native 应用是另一条路径，不能自动受保护 | 不只是给 Control::New 套函数：所有仍把指针当 Control* 解释的方法都必须审计，虚调用、事件、属性与派生对象难度较高 |
| shim | 对可序列化的值可做双 TU 转换；对 handle/虚对象/引用计数需要对象级操作协议和身份映射 | C# 层可能保持；原生直连使用者未必能透明保留 | 不是每类型两次复制就覆盖；W2 不涉及 Dali 对象图，SHIM_UNCERTAIN |
| 消费方改 libc++ | binder、Dali 组件及跨 C++ 依赖协调构建和回归 | C# 应用本身没有“改用 libc++”这一步；需改的是其 native binder。Native 直连应用若有源码则另行重编 | 匹配构建减少异构 std 边界，但是否需要同批发布取决于实测与实际安装原子性，未证明 |
| 接受限制并声明 | 约束 native binder/Dali 的受支持构建组合，明确应用侧 C 边界与内部 C++ 边界不同 | C# 业务确认使用的绑定组件版本；原生 Dali 使用方确认自己的工具链 | 不宜将组件约束写成所有 NUI 应用需源码迁移；允许/禁止过渡组合由业务裁决 |

**对象级设计示例（未实施）**：

```c
struct dali_control_handle;
int dali_control_create(uint32_t behaviour, struct dali_control_handle **out);
void dali_control_release(struct dali_control_handle *handle);
/* 对象操作也需相应 C 入口，不能在 binder 中再转回另一侧 Control*。 */
```

**可定位改动点**：同一个 `control-wrap.cpp` 中 `CSharp_Dali_View_New`、`CSharp_Dali_View_NewWithBehaviour`、`CSharp_Dali_delete_View` 3 个函数。它们调用 New、复制构造/分配、销毁的原文已取得；**1 文件/3 函数是代表下界，不能当整套 binder 改造量**。其他 wrapper、生成模板与 Dali provider 全量改动计数 `NOT_AVAILABLE`。例中的 2 个新 C 操作亦只是设计起点。

旧 C# 导出若保留，可保持应用接入层；但内部句柄解释须完整替换，不能只替换创建函数。旧 Native C++ ABI 是否另保留、期限多长仍需消费方清单和发布契约。

## 4. Native 四族所选内联包装

没有证据表明当前选择的 GetId、Set/GetOperation、Run 平台边必须套上述改造。8 个最终 ELF 支持“所选边为 C 数据”而非四族全量安全。它们仍需真实应用上下文、C ABI/编码、分配释放契约与用户回调不泄漏异常等前提；未验证部分继续 PARTIAL。不能把应用本地 string 符号当成平台跨库传 string。

## 哪些情形四种方案都无法在当前约束下保证目标

**条件性推论，不是已找到具体应用的事实**：若某应用/插件仅有固定二进制，不能重编、不能改变接口或加载安排，依赖又跨标准库传不透明 C++ 对象且缺少可用生命周期协议，则前 3 方案不能据本轮证据完成；第 4 项只是声明限制，不会恢复该功能。当前无这类应用的实际清单，不能声称有多少应用“无解”。

本阶段未实施任何设计，未排优先级。待业务决定：产品/profile、实际应用/原生插件列表、支持旧二进制的承诺与期限、可接受复制/发布/回归成本、是否投入补齐目标接口矩阵。
