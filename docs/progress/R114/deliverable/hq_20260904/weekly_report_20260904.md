## 三、问题三的进展：四项待决事项已查清

问题三尚未处置。本周完成了处置方案的事实调查，确认需要决定四件事，
并查清了 libstdc++ 在对应位置的做法。

### 3-1 新发现：错误路径行为将发生变化

**这一项上周报告中未提及，需要总部知晓。**

移除相关标注之后，`condition_variable::wait` 在**锁未被调用方持有**或
**底层等待返回错误**时，行为将从**终止进程**变为**抛出 `system_error`**。

这是**无取消路径上的可观察变化** —— 不涉及线程取消时也会发生。

**GCC 的先例在这一点上不适用。** 经核对源码，libstdc++ 对应实现为：

```cpp
condition_variable::wait(unique_lock<mutex>& __lock)
{
  _M_cond.wait(*__lock.mutex());
}
```

**函数体不做任何检查、也无抛出路径** —— 锁未持有属未定义行为。
因此 GCC 移除标注时并未引入错误传播变化，**而 libc++ 会**。

libc++ 的对应实现有两处显式抛出：锁未持有时抛 `EPERM`，底层返回错误时
抛对应错误码。

**这是本平台独有的取舍**，无上游先例可援引。

**待裁决**：是否保留现有异常规格与错误处理行为；作出选择前需先补齐正文所列影响面。

理由是这一变化发生在**无取消的正常路径**上，且我们尚未评估它对既有代码的
实际影响面 —— 哪些调用方会因此从"进程终止"转为需要处理异常，目前没有数据。

**该项需在完成全面验证后再作最终决定**，本周不下结论。验证内容至少包括：
现有调用方在锁未持有或底层返回错误时的实际路径、这些路径在产品中是否可达、
以及行为改变后对上层错误处理的影响。

### 3-2 状态更新：兼容措施的做法已确认

上周报告已说明 GCC 的双版本符号做法，以及它只适用于编译在库文件中的函数。
本周进一步确认了实现形态。

libstdc++ 在 `compatibility-condvar.cc` 中：

- 建立旧契约的 wrapper，用 `.symver` 绑定回旧版本符号；
- 私有成员的访问通过显式模板实例化取得；
- 并记录了一个已知问题（PR105730）：直接调用基类版本在特定 C 库上会绑回
  旧符号，需绕开。

该形态可作为 libc++ 设计时的参考。libc++ 当前没有现成的 condition-variable
兼容 wrapper 框架，移植可行性、旧调用点展开兼容性和具体实现仍需验证，不能
据此认定实现障碍已经消失。

**可行选项，尚未裁决**：参考 libstdc++ 的双版本符号和 wrapper 形态；尚未在
libc++ 中实施验证，也尚未由人工选定。

### 3-3 新发现：一处析构语义的取舍

**这一项上周报告中未提及。**

五处站点中的 `wbuffer_convert::~wbuffer_convert`，其析构过程会调用
`sync()` —— 该调用会写出缓冲区剩余内容并执行编码转换器的收尾（unshift）。
这正是取消可以送达的位置。

**libstdc++ 的对应析构为 `= default`，不执行同步。** 因此这条暴露路径在
libstdc++ 侧不存在。

若改为不同步，该处问题消除，但**未显式同步过的使用方可能丢失尾部数据与
编码收尾序列**。这是无取消路径上的可见变化。

**待裁决**：保留现有同步语义，或改为不同步并接受尾部数据/编码收尾语义变化。

**待查**：平台上 `wbuffer_convert` 的实际使用情况。使用者为零时，
两种选择的代价差消失；存在使用者时，数据完整性风险需要实际评估。

### 3-4 状态更新：头文件内联实现的限制与第三方应用

上周报告已说明：五处中有三处的实现位于头文件，随使用方编译内联进其产物，
库端没有可重定向的符号，因此**已编译且不重编的对象无法通过更新库来修正**。

**本周补充一个此前未展开的方面：第三方应用。**

Tizen 平台上存在第三方应用，它们不会随平台迁移而重新编译。若其产物中内联了
这三处实现，**平台侧无法通过任何库更新修正它们的行为** —— 只能由应用重新
编译发布。

这不是技术实现上的欠缺，而是结构性限制。因此该项最终需要形成一份
**支持范围声明**，明确说明哪些对象在本次迁移后行为改变、哪些保持原状。

**该声明涉及应用兼容政策，需要相应的 owner 参与确认。**

### 3-5 四项待决事项汇总

| # | 待决事项 | libstdc++ 的做法 | 待裁决选项 |
|---|---|---|---|
| 1 | 错误路径从终止变为抛异常，是否接受 | **不适用**（本身不检查、不抛） | 是否保留现有异常规格与错误处理行为；需先补齐影响面 |
| 2 | 是否为未重编的旧对象保留原有契约 | 双版本符号 + `.symver` | 可参考该形态；libc++ 实施与兼容性仍需验证 |
| 3 | 析构是否继续执行同步 | 不同步（`= default`） | 保留同步，或不同步并接受尾部语义变化 |
| 4 | 支持范围如何界定 | 无对应问题 | 需形成声明 |

第 1 项为前置条件：若最终不接受该变化，第 2、3 项失去意义，问题三只能维持
「记录风险、不处置」。因此该项的验证优先于其余各项。

## 四、问题六的进展：产品使用情况已查清

上周报告中该项标注为「该模式在产品中的使用情况尚未检索」。本周完成检索。

对平台 371 个源码包做全量静态扫描，结果：

**3 个生产源码包直接设置异步取消模式，其中 2 个具备完整风险形态** ——
即同时具备「异步模式」「C++ 线程」「存在取消发起路径」三项：

| 组件 | 情况 |
|---|---|
| `lightweight-web-engine` | 工作线程初始化时先启用取消、再设为异步模式；同类的销毁方法对该线程调用取消。该线程走 C++ 线程路径 |
| LLVM OpenMP 运行时（`libomp`） | 工作线程与监控线程在 `KMP_CANCEL_THREADS` 下设为异步模式并启用取消；**该开关默认打开，Tizen 不在源码的排除条件内**；平台构建配置确实启用并打包该项目 |

以上均为**源码层面的确认，尚未观察到运行时的实际落点**。

**一项需要指出的关系**：异步取消可以落在五处已知边界之外的其他不抛异常帧中，
因此问题三的五处定点修正不能作为这两个组件的完整处置。当前只完成源码形态
确认，尚未观察到两个组件运行时的实际取消落点；不能据此断言五处修正对其
“完全不产生帮助”，该风险需要作为独立条目验证和处理。

## 五、问题七的进展：跨库对象布局差异已取得实证

上周报告中该项为「已识别、影响范围待确认」。本周为其中一项取得可复现实例。

**构造**：一个动态库由 libstdc++ 构建，返回 `std::deque<int>*`；调用方由
libc++ 构建，直接读取该对象。

**结果**：

| 项 | 值 |
|---|---|
| 库侧对象大小 | 80 字节 |
| 调用方侧对象大小 | 48 字节 |
| 库侧报告的元素个数 | 4 |
| **调用方读到的元素个数** | **106884723786536** |
| 进程结束情况 | **正常退出，无崩溃** |

**链接器不设防的原因**：C++ 名字修饰不将返回类型编入函数名，因此调用方
所需符号与库提供的符号完全匹配，编译与链接阶段均无从发现两侧对同一类型的
理解不一致。

**需要强调**：该用例仍是较轻的表现形式 —— 对象的销毁交回了库侧。若调用方
自行销毁，即为用一套布局析构另一套构造的对象，后果通常更严重。

另对 33 个常用类型做了布局比对，**其中 10 个明确不同**：`any`、`function`、
`deque`、`map`、`set`、`unordered_map`、`unordered_set`、`string`、`future`、
`promise`。

**平台上的规模**：仅 Boost 一处边界即涉及 13 个 consumer 源码包、75 个去重
`(架构, consumer ELF 路径)` 记录和 90 条真实 C++ 符号边。其中已实测的部分确认存在布局敏感传递；
**其余边尚未逐条实测**。

## 六、对上周报告中一处数据的更正

总部对接人询问上周报告「问题一」影响面表格中「50 处独立站点」的含义。
我们在整理逐条清单时重新核算，**确认该数字不准确，现予更正**。
以下为完整说明，不再另行答复。

### 6-1 定义与计数单位

**识别子句**：源码中捕获 `abi::__forced_unwind` 或
`__cxxabiv1::__forced_unwind` 的 `catch`（或 libstdc++ 的 `__catch`）子句。

**传播子句**：在上述基础上，handler 还通过下列任一形式继续向上传播：

```cpp
throw;                      // 裸重抛
__throw_exception_again;    // libstdc++ 的宏形式
```

**本次使用两种计数单位，二者不可互相比较**：

| 单位 | 标识键 |
|---|---|
| **源码出现次数** | 源码 RPM 实例 + 包内规范化路径 + 行号 |
| **逻辑站点** | 合并同一包的不同 Release 变体后，以包名 + 规范化路径 + 行号 + 子句与重抛形态为键 |

### 6-2 更正内容

原扫描筛出的 50 行存在两类缺陷：

| 缺陷 | 数量 | 说明 |
|---|---:|---|
| 误计 | 4 | `key-manager` 中位于真实 handler 内、介于识别子句与 `throw;` 之间的日志字符串，被启发式规则误匹配。旧规则未要求命中行本身是 catch 子句 |
| 漏计 | 126 | 旧规则只承认裸 `throw;`，**未识别 `__throw_exception_again` 宏形式**；文件后缀白名单也未包含无扩展名的 C++ 头文件（如 `future`、`ostream`、`condition_variable`），该项在本次范围内涉及 32 处出现、16 个逻辑站点，属宏形式的子集，不另行累加 |

对同一份冻结源码重新严格核算：

| 度量 | 源码出现次数 | 去重后逻辑站点 |
|---|---:|---:|
| 旧规则选出的行 | 50 | 45 |
| 其中确为识别子句的 | **46** | **41** |
| 严格核算后的传播子句 | **172** | **104** |

172 处传播子句由 46 处裸 `throw;` 与 126 处宏形式构成，去重后分别为
41 与 63 个逻辑站点。识别子句总数为 175，其中 `dali2-csharp-binder`
的 3 处不重新传播，故传播数为 172。

传播集合涉及 10 个源码 RPM 实例、8 个包名（重复项为 GCC 与 TensorFlow2
的不同 Release 变体）；识别集合涉及 11 个实例、9 个包名，多出的是
`dali2-csharp-binder`。

### 6-3 本次核算的范围

**这不是对全平台的重新扫描。**

原扫描覆盖 371 个成功解包的源码 RPM。本次严格核算**没有对全部 371 个
重跑**，而是先选出原位置表中已确认含目标识别子句的 **11 个源码 RPM
实例**，再对这些实例的全部文本文件重新核对（不再限定文件后缀）。

冻结输入的校验值：

```text
extraction_results.tsv  5498c430baecd81e689a44d8266d5597a92779680105ede0c320f9b1ea013031
corpus_hits.tsv         cd2a91832f5a548b4e762c9cc42c4349c50d4f82e559058760f1cf6f83a6c7c2
scan_status.tsv         5c15fe0097f5dc6b37a755ce25cb6d01846050fa653a4ca5fe8e74803ed85723
```

文档路径已排除；源码、测试、示例与构建文件保留。这是源码出现次数的计数，
因此条件编译下不生效的源码同样计入。

**当前平台源码全集尚未做同样的严格扫描**，历史阳性包之外的当前新增内容
不在本次核算范围内。

### 6-4 复现步骤

1. 取用同一份冻结源码 RPM 与上述 11 个实例的审计子集；
2. 检索两种写法：`abi::__forced_unwind` 与 `__cxxabiv1::__forced_unwind`；
3. **搜索全部文本文件**，不限于常规扩展名；
4. 对每处命中打开文件，确认它是**实际的 catch 子句**，而非字符串或注释中
   的提及；
5. 定位该 handler 的完整函数体，确认是否包含两种传播形式之一；
6. 排除文档路径；规范化主源码归档前缀；嵌套架构资产内的不同路径予以保留；
7. 按「源码 RPM 实例 + 路径 + 行号」计源码出现次数；
8. 按 6-1 所述的逻辑站点键合并 Release 变体，得到 104。

### 6-5 若对方核算结果不同，可能的原因

- 源码快照或源码包全集不同；
- 扫描全部包 与 仅扫描本次的历史阳性子集；
- 是否包含 `__throw_exception_again` 形式；
- 是否搜索无扩展名的 C++ 头文件；
- 对字符串、注释、文档、测试、示例、构建文件、以及条件编译下不生效的
  源码的处理方式；
- 主归档与嵌套架构资产内路径的规范化方式；
- 是否合并同一包的不同 Release 变体；
- 别名、由宏生成的 catch、或项目自有的间接传播方式 —— 这些不以上述两种
  显式写法出现，本次方法无法识别。
