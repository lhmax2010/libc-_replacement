## 七项建议改

七项均采纳，但不是“默认全改”；逐项理由如下。

| 项 | 是否采纳 | 理由与处理 |
|---|---|---|
| S1 补丁提交关系 | 采纳 | 原文容易把 `8dfebafe` 读成四层改动的一部分。按已核实拓扑明确四层改动在 `6771dbc4`，`8dfebafe` 是更早的独立 ARM EHABI 编译修正，当前 `2d23367d` 位于二者之上。该修改只澄清关系。 |
| S2 Boost 的 75 | 采纳 | 单位直接影响对外理解。改为 75 个去重 `(架构, consumer ELF 路径)` 记录，不称为 75 个二进制 RPM。 |
| S3 共同失败 213 | 采纳 | 基线/补丁对照只能支持“基线既有”分类，不能支持逐项根因均已查明；补上该限定以防扩大证据。 |
| S4 全局注入后果表 | 采纳 | 原表两格读起来像 61 包逐包构建结果。改成条件句，并保留 aarch64 GCC 未观测及逐包传播未验证。 |
| S5 缺失证据索引 | 采纳第二种方案 | 当前交付包没有可外发的证据索引，直接附内部索引会泄露内部路径。因此删除“随附”承诺，改为原始材料、脚本和 SHA256 可按需提供。 |
| S6 “修复完成”与稳定性 | 采纳 | 用“代码修复及两架构官方测试对照已完成；产品级稳定性验证仍待进行”区分两个阶段，不改变完成状态。 |
| S7 问题六状态范围 | 采纳 | 静态源码形态与运行时落点是不同证据。状态改为冻结 371 个源码 RPM 的静态形态已查清，2 个风险形态运行时落点未观测。 |
