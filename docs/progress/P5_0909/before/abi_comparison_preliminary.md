# libstdc++ 与 libc++ 的 ABI 差异（初步版）

- 日期：2026-09-09
- 状态：**初步版** —— 成员级的内部实现比对尚未完成，见第五节
- 测量环境：x86_64；libstdc++ (GCC 14.2)、libc++ 22.1.8

---

## 一、哪些层一致、哪些层不同

这一点是理解全部差异的前提。

| 层 | 两套库 | 后果 |
|---|---|---|
| 名字修饰规则 | **一致**（同为 Itanium C++ ABI） | **链接器认为符号匹配** |
| 函数调用约定 | **一致**（由平台 ABI 决定） | 参数传递正常 |
| 内置类型与 POD 的布局 | **一致** | 跨边界安全 |
| **标准库类型的内存布局** | **不同** | **传对象会静默出错** |
| 内联命名空间 | 不同（`__cxx11` / `__1`） | 部分符号名不同，链接会失败 |
| 异常与 RTTI 的类型信息 | **各自独立** | 跨边界接不住类型化异常 |
| 分配器与内部状态 | 各自独立 | 跨边界释放会破坏堆 |

**危险恰恰来自前三行一致。** 若连名字修饰都不同，链接会当场失败，问题反而
暴露；正因为符号能对上，问题被推迟到运行时才显现，而且不崩溃。

## 二、对象布局的差异

比对了 33 个常用类型，**10 个布局不同**。

### 2.1 布局不同的类型

| 类型 | libstdc++ | libc++ | 差值 |
|---|---:|---:|---:|
| `std::any` | 16 | **32** | +16 |
| `std::function<void()>` | 32 | **48** | +16 |
| `std::deque<int>` | **80** | 48 | −32 |
| `std::map<int,int>` | **48** | 24 | −24 |
| `std::set<int>` | **48** | 24 | −24 |
| `std::unordered_map<int,int>` | **56** | 40 | −16 |
| `std::unordered_set<int>` | **56** | 40 | −16 |
| `std::string` | **32** | 24 | −8 |
| `std::future<int>` | **16** | 8 | −8 |
| `std::promise<int>` | **24** | 8 | −16 |

**注意方向不一致** —— 有的 libc++ 更大，有的更小。这说明两套库的设计取舍
不同，不是简单的"新版本更紧凑"。

### 2.2 布局一致的类型

其余 23 个（`std::array`、`std::pair`、`std::vector`、`std::unique_ptr`、
`std::shared_ptr` 等）大小与对齐相同。

**但大小相同不等于可以跨边界传递** —— 内部字段的含义与不变式仍可能不同。
本轮只比对了大小与对齐，**成员级比对未做**（见第五节）。

### 2.3 实测的后果

```cpp
// 提供方（libstdc++ 构建）
std::deque<int>* make_data() {
    return new std::deque<int>{1, 2, 3, 4};   // 报告长度 4
}

// 消费方（libc++ 构建）
auto* d = make_data();
printf("%zu\n", d->size());                   // 读到 106884723786536
```

**链接成功、加载成功、进程正常退出，不崩溃，但数据是错的。**

**为什么链接器发现不了**：C++ 的名字修饰不把返回类型编进符号名，
两侧的 `make_data` 都修饰成 `_Z9make_datav`。

## 三、导出符号的差异

| 项 | libstdc++ | libc++ |
|---|---:|---:|
| 导出的 C++ 符号数 | 6,057 | 1,969 |
| **名称完全相同的** | **17** | |

**同名的 17 个尚未逐个核实语义是否等价。**

**差异的来源**：

1. **内联命名空间** —— libstdc++ 用 `std::__cxx11`、libc++ 用 `std::__1`，
   因此大量同名类型的修饰名不同；
2. **实现策略** —— libc++ 大量使用头文件内联（`_LIBCPP_HIDE_FROM_ABI`），
   代码编进使用方而非导出；libstdc++ 更多编在库中；

**第 2 点的后果**：libc++ 的很多实现**随使用方编译进其二进制**，
更新库改变不了已编译的那些副本。

## 四、线程取消相关的差异

这一项是本次迁移中实际撞上的，单列。

| 项 | libstdc++ | libc++ |
|---|---|---|
| 识别强制展开的标记类型 | **提供**（`abi::__forced_unwind`） | **不提供** |
| 标准库内部的识别子句 | 约 50 处 | **0 处** |
| `condition_variable::wait` 的异常规格 | **无**（GCC 为支持取消移除过） | **有 `noexcept`** |
| `wbuffer_convert` 析构 | `= default`，不同步 | 调用同步 |
| `shared_mutex` 的实现 | x86_64 用 `pthread_rwlock` | **自己的状态机** |

**最后一行的后果**：libc++ 的状态机在写者被取消时没有回滚，
锁会永久不可用；libstdc++ 因为用系统原语，状态由内核管理，不存在该问题。

## 五、本版未覆盖的内容

**以下需要另行安排，预计数日：**

1. **成员级的布局比对** —— 本版只比对了大小与对齐。要说清"内部实现差距"
   需要逐个类型比对：
   - 数据成员的类型、顺序、填充；
   - 虚表结构与虚函数顺序；
   - 内部辅助类型（节点、控制块、迭代器表示）；
   - 分配策略与增长策略；

2. **大小相同的 23 个类型是否真的等价** —— 大小相同不代表字段含义相同；

3. **同名 17 个符号的语义等价性** —— 尚未逐个核实；

4. **异常与 RTTI 的具体机制差异** —— 本版只说明"类型信息独立"，
   未展开两套实现的具体做法；

5. **架构覆盖** —— 本版数据取自 x86_64；armv7l 与 aarch64 未比对，
   而指针宽度与对齐规则不同，**部分结论可能不适用**。

## 六、哪些差异需要保持一致

**按我们目前的处理原则：凡有 libstdc++ 参照之处一律对齐。**

| 差异 | 是否需要一致 | 我们的处理 |
|---|---|---|
| 线程取消的识别机制 | **需要** | 已补齐标记类型与 50 处防护 |
| `condition_variable` 的异常规格 | **需要** | 解除，与 libstdc++ 一致 |
| `wbuffer_convert` 析构行为 | **需要** | 改为不同步，与 libstdc++ 一致 |
| `shared_mutex` 的取消安全性 | **需要** | 加状态回滚（libstdc++ 因用系统原语而无此问题） |
| **对象布局** | **不需要，也做不到** | 两套独立实现，标准不要求一致；靠边界管理规避 |
| 导出符号集合 | 不需要 | 实现策略不同，属正常差异 |
| 内联命名空间 | 不需要 | 它反而提供了部分保护（符号不撞名） |

**判断标准**：凡是**行为差异**（同一段代码在两套库下表现不同）都要对齐；
**实现差异**（布局、符号集合）不追求一致，靠接口边界管理。
