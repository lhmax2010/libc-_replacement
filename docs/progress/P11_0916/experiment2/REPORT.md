# 旧 EWK 符号引用与版本路由核查

状态：`PARTIAL`。只完成本阶段的静态产物核查并交审；不据此启动后续实验或修改方案文档。

## 一、先给结论：旧引用、方案 B 与“零改动”

1. **已核查的三架构真实 `chromium-efl` 产物，其 `ewk_parse_cookie` 导出均无命名版本节点。** 转发库与实现库共六个 ELF 均为动态符号版本索引 `1`（`*global*`），不是 `ewk_parse_cookie@某版本`。这是静态核查结果，不是运行时调用结果。
2. **实际找到的间接调用路径是 `libchromium-ewk.so` 内部的 `dlsym(handle, "ewk_parse_cookie")`，不是 `UND ewk_parse_cookie@版本`。** 三架构的指令与目标字符串均已核对。这条查找没有指定版本，不能利用一个不存在的、由调用方明确请求的旧 EWK 版本节点分流。
3. 冻结清单对应的本地提取物中，**普通 `UND ewk_parse_cookie` 导入零命中**，有真实版本化导入正向对照。但是**未取得至少三个独立的已发布应用调用方**：其具体引用有无版本为 `NOT_OBSERVED`；满足该要求的材料为 `NOT_AVAILABLE`。不能把转发库的定义行或 SDK 中的重复文件冒充应用导入样本，也不能外推全部历史版本、全部第三方应用。
4. **方案 B 若专指“依靠旧引用已有的 EWK VERNEED 节点来选旧接口”，当前已找到的路径不具备这个前提。** 若指“同 DSO 内保留旧兼容入口，另给新接口一个可区分的入口”，则本轮未证明它不存在，也未验证它可部署，记 `NOT_OBSERVED`。两种含义必须分开。
5. **零改动对已发布 ELF 是否可能：现有材料不足以作全体肯定或全体否定。** 保留旧名称的 GNU 薄接口层、把新实现置于另一个明确入口，在机制上仍是条件性可能；不是本轮实测结论。若要求两种 ABI 的调用都使用不可区分的同一名称、同一路由上下文，单靠该名称无法判定传入对象布局。

**业务问题需要重新定义**：不能只问“旧引用有没有版本，因此所有零改动方案是否存在”；需要明确要兼容哪些已发布 ELF、它们走普通重定位还是 `dlsym`、允许平台保留什么兼容入口，以及“零改动”是否同时禁止应用重编、重链和启动方式变化。本轮没有替业务方作这些选择。Chromium 整体迁移及允许薄 GNU 接口层的人工前提不变。

## 三、真实组件的来源、导出与查找链

六个生产 ELF 来自 `chromium-efl-1.1.144-1` 的 x86_64、armv7l、aarch64 三份 RPM；SDK 产物来自 `app-rootstrap-devel-10.0.0-1` 的三份 RPM。完整来源 RPM 路径、RPM SHA256、ELF SHA256、18 条 `readelf -Ws` 原文以及每份完整 `-V` 链接集中在 [SAMPLES.md](SAMPLES.md)，机器可读版见 [SAMPLES.tsv](SAMPLES.tsv)。这满足三架构组件对照，不满足三个独立业务调用方的要求。

### 3.1 导出不带命名版本，不等于整个 ELF 没有 VERNEED

例如 x86_64 转发库的实际 `readelf -Ws` 输出：

```text
   409: 000000000002bd78    77 FUNC    GLOBAL DEFAULT   14 ewk_parse_cookie
```

它是 **定义**（`Ndx=14`），不是 `UND`。同文件 `readelf -V` 却包含：

```text
Version needs section '.gnu.version_r' contains 2 entries:
 Addr: 0x000000000000593c  Offset: 0x0000593c  Link: 6 (.dynstr)
  000000: Version: 1  File: libstdc++.so.6  Cnt: 6
```

另外一个条目属于 `libc.so.6`；这些 GLIBCXX、CXXABI、GLIBC 需求不等于 EWK 的版本需求。目标符号索引 409 对应 `.gnu.version` 索引值为 1。完整 [符号表](raw/elf_07_r1_Ws.stdout)、[版本表](raw/elf_07_r1_V.stdout) 和 [逐轮断言](MEASUREMENTS.json) 可逐项对照。反汇编工具显示的 `@@Base` 也不能替代这个判定。

### 3.2 已找到的间接调用不是普通符号交集边

事实链（以下全部为静态核查）：

**真实转发库定义旧 C 名称 → 函数体取一个库句柄 → 将 `ewk_parse_cookie` 字符串传给 `dlsym` → 保存并恢复原始两个参数 → 跳转到返回地址。** 此处未调用带版本参数的 `dlvsym`。没有执行该路径，不能据此声称某业务已经调用它或实际加载了哪个实现。

| 架构 | 目标字符串地址 | 查找与转发指令 | 原始记录 |
| --- | --- | --- | --- |
| x86_64 | `0xf9ce` | `0x2bda6` 调 `dlsym@plt`，`0x2bdbb` 间接跳转 | [反汇编](raw/elf_07_forwarder.stdout) |
| aarch64 | `0xf992` | `0x341cc` 调 `dlsym@plt`，`0x341e8` 间接跳转 | [反汇编](raw/elf_01_forwarder.stdout) |
| armv7l | `0xeece` | Thumb 的 `0x29c6c` 调 `0x31240`，`0x29c7c` 间接跳转 | [Thumb 反汇编](raw/021_arm_thumb_forwarder.stdout) |

armv7l 的 PLT 入口最终读取 GOT 地址 `0x41494`；[重定位表](raw/022_arm_relocations.stdout) 的实际对应行为：

```text
00041494  00000516 R_ARM_JUMP_SLOT        00000000   dlsym@GLIBC_2.34
```

三处虚拟地址的 ELF 文件字节均断言为目标名称及 NUL 终止符，见 [字符串校验](FORWARDER_STRING_CHECKS.json)。初次普通 ARM 解码模式不适用于此 Thumb 函数，故保留初次记录，改用显式 Thumb 模式复查；没有将 `<unknown>` 指令当成正常证据。

**排除的解释**：不能把这个函数自身的导出行说成“调用方未定义引用”；不能把 SDK 的同内容别名文件说成不同应用。**反驳这条链需要的证据**：指出上述 RPM 身份、指令解码、字符串地址或重定位对应有误，或给出实际发布调用方证明另有带版本的调用路径。后者会扩展范围，不会抹掉本轮已经查到的间接路径。

## 四、正向对照与重复的分量

扫描器按目标名字精确匹配动态符号条目，区分 `SHN_UNDEF` 和定义，并读取关联版本索引；不是扫描二进制中的字符串命中数。源代码见 [scan_elf.py](scan_elf.py)。18 个目标定义由独立 `readelf` 交叉确认；六个真实组件 ELF 的 `dlsym@GLIBC_2.34` 为“UND + 命名版本”的正向对照，覆盖三架构及转发/实现两层，见 [POSITIVE_CONTROLS.json](POSITIVE_CONTROLS.json)。

例如 x86_64 转发库正向对照原文：

```text
     5: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND dlsym@GLIBC_2.34 (3)
```

18 条产物记录各重复 5 轮，每轮同时保存完整 `readelf -Ws` 与 `readelf -V`，共 **90 轮静态读取、180 次 readelf 命令**，具体符号角色与版本值断言全部通过。18 条产物的读取前后 SHA256 均一致，且与所属 RPM 载荷摘要一致。脚本见 [measure.py](measure.py)。

这五次重复证明固定输入的解析与断言可复现，**不是五次 EWK 运行，不是跨库数据正确性或路由可部署性实测**。没有加载目标库、没有 `/proc/self/maps` 运行证据，没有板上任务。整个发行版负向扫描执行一次，不把它写成全清单五次扫描。

## 五、无版本引用对可选路由的实际影响

### 5.1 不能从一个 ELF 倒推出全部历史，也不能直接推出方案 B 不存在

GNU ld 允许版本脚本只控制导出可见性而不分配命名版本。因此“当前目标导出无版本”不能证明“历史上没有版本脚本”。[GNU ld VERSION 文档](https://sourceware.org/binutils/docs/ld/VERSION.html)

上游 glibc 2.40 的查找实现明确区分旧无版本引用和 `dlsym` 的无版本查找，其兼容选择规则不同。因此“没有旧 VERNEED”并不从机制上排除任何旧入口兼容策略。这里引用的是上游源码，不是本轮对 Tizen 加载器补丁及运行效果的确认。[glibc 2.40 查找源码](https://raw.githubusercontent.com/bminor/glibc/glibc-2.40/elf/dl-lookup.c)

**事实链**：本轮旧转发路径按名称查找 → 没有携带 EWK 版本选择信息 → 不能假定新旧调用自然分流。**已排除**：仅增加两个版本定义，便宣称所有旧调用会自动选旧布局。**反驳需要什么**：在真实旧调用链、真实加载器上证明一个具体入口和版本布局能将旧调用与新调用稳定分流，并同时保持数据、复用状态、销毁及异常契约。普通重定位的样例不能替代已查到的显式句柄 `dlsym` 路径。

### 5.2 各路由与已发布 ELF 的关系

以下是基于已查结构与加载机制的条件分析，**不是新增实验或部署结论**。

| 手段 | 对已发布 ELF 的条件性适用范围 | 本轮结论与限制 |
| --- | --- | --- |
| 根据旧 VERNEED 精确选旧版本 | 要求目标调用已经携带可用的旧版本需求 | 已找到的名称查找不具备此条件；外部应用样本不足 |
| 保留旧名称/默认 GNU 兼容入口；新 libc++ 入口使用不同名称、私有入口或明确版本 | 可能保持旧 ELF 字节与应用启动不变，但需要平台接口部署和新侧明确路由 | `NOT_OBSERVED`；是允许的薄接口层/同 DSO 部署候选，不等于保留整个 GNU Chromium |
| `LD_PRELOAD` | 某些普通全局符号查找可受影响，但需改变加载环境；安全执行模式有限制 | 不符合“启动方式也零改动”的严格口径；仅覆盖全局同名函数不能保证截住当前显式句柄查找 |
| 拦截 `dlsym` | 需要先让拦截器进入有效查找范围，再识别句柄、名称与调用上下文 | `NOT_OBSERVED`；需要处理递归、并发、初始化与真实查找语义，不能仅按函数名自动辨别两套对象布局 |
| 改 SONAME 或库文件名 | 单独改名不改写旧 ELF 的 DT_NEEDED，也不改写旧代码传给 dlopen 的名字 | 单独改名不能维持原查找；保留旧名门面并转调新名库是另一项有条件的兼容部署设计，未测 |
| 显式 `dlvsym` 选择 | 新侧可以明确请求一个版本，但旧 `dlsym` 不会凭空多出版本参数 | 若要改旧调用代码/重链，已不属于既有应用严格零改动；若修改平台转发层，需要单独验证全部使用者 |

加载范围与环境约束依据：[ld.so](https://man7.org/linux/man-pages/man8/ld.so.8.html)；句柄查找、`RTLD_DEFAULT`/`RTLD_NEXT` 与版本查找的区别依据：[dlsym / dlvsym](https://man7.org/linux/man-pages/man3/dlsym.3.html)。这些来源不证明任一候选方案已经适配 Tizen。

## 六、未覆盖、执行判断与交审事项

- **应用材料缺口**：已试全冻结清单动态符号交集、全部命中的独立 readelf、SDK/生产包身份分组和真实转发层反汇编；仍没有三个独立业务应用的普通目标导入样本。需要发布方提供实际调用该接口的应用 ELF/RPM、对应发布版本和加载方式，才能补齐应用侧 VERNEED 判定。
- **历史范围**：只有所列冻结版本；不覆盖全部旧发行版、外部产品、自带运行库应用、静态链接副本、名称经计算产生的动态查找或所有回调路径。零普通导入不等于没有使用者。
- **架构范围**：三架构都是文件静态核查，在 x86_64 主机上读文件；没有 ARM 物理板/QEMU 执行，没有任何新版 libc++ provider 路由实测。
- **自行判断**：把“旧 VERNEED 精确路由”与“旧无版本入口兼容部署”拆开；把转发库作为间接调用证据而不是应用导入；只把 SDK 数据用于导出形态核查；不采用任务书中两个过强的逻辑蕴含。这些判断的依据均列在上文，等待人工确认方案 B 的口径。
- **执行异常**：GNU ld 网页 shell 下载 HTTP 403（退出 22），网页工具可读取；没有伪造下载成功。汇总脚本首次使用当前 Python 不支持的 `hashlib.file_digest` 失败（退出 1），改为分块 SHA256 后重跑通过。早期路径探查中的缺文件信息与初次 ARM 解码均保留；详见 [自检](SELF_CHECK.md)。这些不改变已完成的 ELF 原始读取记录。
