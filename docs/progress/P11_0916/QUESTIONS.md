# 需人工确认的事项

## 方案 B 的定义及二值推论

已在核查期间提问：是否把“按旧 ELF 中已有 VERNEED 精确选择版本”与“无版本旧入口的兼容路由”分开报告？

原因：GNU ld 文档明确存在不分配命名版本的版本脚本；glibc 的符号查找代码明确区分旧无版本引用和 dlsym 查找。因此“目标导出无版本 → 历史上没有版本脚本”和“旧引用无版本 → 所有同 DSO 双接口方案都不存在”都不能仅凭这一项二进制事实推出。

当前处理：实验 2 已单独停止交审，人工审阅通过并授权继续。仍按二进制事实与成立范围分别报告；未实测路由记 NOT_OBSERVED，未将方案 B 判为已可部署，也未把没有旧 VERNEED 判为一切零改动均不可能。人工新增的转发层小节已经落入两稿 5.3，严格标为推论与待验设计。

依据与具体样本见 [实验 2 报告](experiment2/REPORT.md)；不改变 Chromium 整体迁移、允许薄 GNU 接口层的既定前提。

## 真实已发布应用与零改动的边界

全冻结清单普通 UND 交集未找到目标导入，有六个真实组件 ELF 的版本化导入正向对照。三架构转发库是按名称 dlsym 的间接调用证据，不是三个独立应用样本。后者仍缺实际调用该接口的应用 ELF/RPM、发布版本和加载方式，不能推断补齐。

请人工明确：需兼容的已发布应用范围，以及“零改动”是否同时要求不改应用源码、不重编、不重链、不改应用启动方式；允许平台保留旧默认入口、为新实现提供另一个明确入口是否属于方案 B 的讨论范围。本轮只是按这些可能定义分开列证据，不作部署选择。

## 实验续测后的未决事实

- 原 BoundaryError 的两架构观测已区分原因：类型身份/匹配失败，不是 foreign；不再将两原因对这个固定样本都标未知。其他加载条件不作全称判断。
- ARM QEMU 用户态的 libsupc++＋LLVM 预加载组合五次 SIGABRT，诊断未知 personality 结果 5；内部根因尚未定位。不能以 x86_64 通过宣称整个异常契约消失，也未授权本轮修展开器。
- 真实 libc++ EWK 产物 NOT_AVAILABLE，仍缺完整生成头/依赖闭包或可验证的组件产物；本轮按要求继续文档，没有伪造反方向结果。
- `dlsym` 原句柄最终解析到哪一个生产实现、能否保留旧入口同时路由转换，尚未实测。候选位置不是部署结论。
- 哨兵允许哪些 ABI 标签、属于哪些正式 SDK 头，须由接口维护者/业务明确；本轮只评估，未改任何头文件。
- 开头补充评审的作者身份沿用旧缺口；不推定归属，不影响具名建议与事实核对。
