# 需人工确认的事项

## 方案 B 的定义及二值推论

已在核查期间提问：是否把“按旧 ELF 中已有 VERNEED 精确选择版本”与“无版本旧入口的兼容路由”分开报告？

原因：GNU ld 文档明确存在不分配命名版本的版本脚本；glibc 的符号查找代码明确区分旧无版本引用和 dlsym 查找。因此“目标导出无版本 → 历史上没有版本脚本”和“旧引用无版本 → 所有同 DSO 双接口方案都不存在”都不能仅凭这一项二进制事实推出。

当前处理：只给出各个二进制事实及其成立范围；未实测的路由记 NOT_OBSERVED，不擅自把方案 B 判为已可部署，也不把没有旧 VERNEED 判为一切零改动方案均不可能。完成实验 2 后停止，交人工裁决后续口径。

依据与具体样本见 [实验 2 报告](experiment2/REPORT.md)；不改变 Chromium 整体迁移、允许薄 GNU 接口层的既定前提。

## 真实已发布应用与零改动的边界

全冻结清单普通 UND 交集未找到目标导入，有六个真实组件 ELF 的版本化导入正向对照。三架构转发库是按名称 dlsym 的间接调用证据，不是三个独立应用样本。后者仍缺实际调用该接口的应用 ELF/RPM、发布版本和加载方式，不能推断补齐。

请人工明确：需兼容的已发布应用范围，以及“零改动”是否同时要求不改应用源码、不重编、不重链、不改应用启动方式；允许平台保留旧默认入口、为新实现提供另一个明确入口是否属于方案 B 的讨论范围。本轮只是按这些可能定义分开列证据，不作部署选择。
