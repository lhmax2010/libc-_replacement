    28	## 问题一：线程取消会被 `catch (...)` 吞掉，导致进程终止
    29	
    30	### 先说明一个背景机制
    31	
    32	程序里有一种操作叫「终止一个正在运行的线程」（`pthread_cancel`）。它不是粗暴地把线程杀掉，而是让线程**有序退出**：从线程当前位置开始，一层层往回退，沿途执行每一层的清理代码（析构对象、释放资源），最后线程干净地结束。
    33	
    34	这个「一层层往回退并清理」的过程，在 Linux/glibc 上叫**强制展开**（forced unwind），它和 C++ 抛出异常时发生的事情**用的是同一套底层机制**。
    35	
    36	### 问题是什么
    37	
    38	因为机制相同，下面这种非常常见的写法：
    39	
    40	```cpp
    41	try {
    42	    // 这里可能有取消点，例如读写、等待
    43	} catch (...) {
    44	    // 捕获所有异常并处理
    45	}
    46	```
    47	
    48	**会把「线程终止」也一并捕获**。捕获之后如果不重新放行，终止流程就走不完，glibc 判定出错并**终止整个进程**，打印：
    49	
    50	```
    51	FATAL: exception not rethrown
    52	```
    53	
    54	### 两套标准库为何不同
    55	
    56	**libstdc++ 提供了一个专门的标记类型**，让代码能识别出「这是线程终止，不是普通异常」：
    57	
    58	```
    59	codes/gcc/libstdc++-v3/libsupc++/cxxabi_forced.h:48-54
    60	
    61	  class __forced_unwind
    62	  {
    63	    virtual ~__forced_unwind() throw();
    64	    virtual void __pure_dummy() = 0;   // 纯虚函数，使该类不可实例化
    65	  };
    66	```
    67	
    68	光有这个类型还不够，还需要让它在运行时真的能被匹配到。libstdc++ 的异常处理例程在判断「当前这个异常是什么类型」时，做了一步特殊处理：
    69	
    70	```cpp
    71	// codes/gcc/libstdc++-v3/libsupc++/eh_personality.cc:563-573
    72	
    73	#if __cpp_rtti
    74	      // During forced unwinding, match a magic exception type.
    75	      if (actions & _UA_FORCE_UNWIND)
    76	        {
    77	          throw_type = &typeid(abi::__forced_unwind);
    78	        }
    79	      // With a foreign exception class, there's no exception type.
    80	      else if (foreign_exception)
    81	        {
    82	          throw_type = &typeid(abi::__foreign_exception);
    83	        }
    84	      else
    85	```
    86	
    87	关键是第 565–568 行：**当发现这次展开是「强制展开」（也就是线程终止）时，就把「当前异常的类型」直接指定为 `abi::__forced_unwind`。**
    88	
    89	线程终止本身并不是一个真正的 C++ 对象，它来自 glibc，没有类型信息。这段代码相当于给它**临时贴上一个标签**，于是后续的类型匹配就能认出它——代码里写的 `catch (abi::__forced_unwind&)` 才会命中。
    90	
    91	于是代码可以这样写：
    92	
    93	```cpp
    94	try { ... }
    95	catch (abi::__forced_unwind&) { throw; }   // 识别出来，原样放行
    96	catch (...) { ... }                         // 处理真正的异常
    97	```
    98	
    99	**libc++ 没有这个类型**。迁移后，写了上面那行的代码编译不过；把那行删掉，线程终止就被吞掉，进程崩溃。
   100	
   101	### 复现步骤
   102	
   103	复现逻辑：让一个线程阻塞在取消点上，另一个线程终止它；线程的调用栈里有一个 `catch (...)`。
   104	
   105	**关键在于对照怎么设**：同一份源码，在 libstdc++ 下**带有识别子句**，在 libc++ 下那段代码被条件编译排除掉（因为该类型不存在，写了也编译不过）。这正是迁移后代码的真实处境——所以用 `#if defined(__GLIBCXX__)` 把它分开。
   106	
   107	```cpp
   108	#include <pthread.h>
   109	#include <unistd.h>
   110	#include <atomic>
   111	#include <cstdio>
   112	
   113	#if defined(__GLIBCXX__)
   114	#include <cxxabi.h>          // libstdc++ 才有识别类型
   115	#endif
   116	
   117	static std::atomic<int> started{0};
   118	
   119	struct Cleanup {
   120	    ~Cleanup() { std::puts("EVENT destructor"); }
   121	};
   122	
   123	static void *worker(void *) {      // 注意：不加 noexcept
   124	    Cleanup cleanup;               // 用于确认清理代码确实执行了
   125	    try {
   126	        started.store(1);
   127	        for (;;) {
   128	            pthread_testcancel();  // 明确的取消点
   129	            usleep(1000);
   130	        }
   131	#if defined(__GLIBCXX__)
   132	    } catch (const __cxxabiv1::__forced_unwind &) {
   133	        std::puts("EVENT forced_guard_rethrow");
   134	        throw;                     // 识别出来，原样放行
   135	#endif
   136	    } catch (...) {
   137	        std::puts("EVENT catch_all");   // 吞掉——问题就出在这里
   138	    }
   139	    std::puts("EVENT worker_returned");
   140	    return nullptr;
   141	}
   142	
   143	int main() {
   144	    pthread_t thread{};
   145	    void *result = nullptr;
   146	    pthread_create(&thread, nullptr, worker, nullptr);   // 用裸 pthread，不用 std::thread
   147	    while (started.load() == 0) usleep(1000);
   148	    pthread_cancel(thread);
   149	    pthread_join(thread, &result);
   150	    std::printf("RESULT joined=%s\n",
   151	                result == PTHREAD_CANCELED ? "PTHREAD_CANCELED" : "other");
   152	    return result == PTHREAD_CANCELED ? 0 : 1;
   153	}
   154	```
   155	
   156	编译与运行：
   157	
   158	```
   159	# libstdc++
   160	g++ -std=c++17 -pthread probe.cpp -o probe_gnu && ./probe_gnu; echo "exit=$?"
   161	
   162	# libc++
   163	clang++ -std=c++17 -stdlib=libc++ -pthread probe.cpp -o probe_llvm && ./probe_llvm; echo "exit=$?"
   164	```
   165	
   166	**实测结果**：
   167	
   168	| 标准库 | 输出 | 退出码 |
   169	|---|---|---|
   170	| libstdc++ | `EVENT forced_guard_rethrow` → `EVENT destructor` → `RESULT joined=PTHREAD_CANCELED` | **0** |
   171	| libc++ | `EVENT catch_all` → `EVENT destructor` → `FATAL: exception not rethrown` | **134** |
   172	
   173	两种架构一致。
   174	
   175	**如果把 libstdc++ 那侧的识别子句也去掉**（即两边都只剩裸的 `catch (...)`），**libstdc++ 同样会退出 134**——这说明差异不在于哪套库更宽容，而在于**libc++ 根本没有提供能写出那句识别子句的类型**。
   176	
   177	### 根因
   178	
   179	崩溃来自 glibc，不是 C++ 运行时。具体链条是：`catch` 块结束 → 运行时判定该外来异常「未被重新放行」→ 调用 glibc 注册的清理回调 → glibc 打印上述信息并终止进程。
   180	
   181	### 影响面
   182	
   183	平台上 371 个已解包源码包中：
   184	
   185	| 情况 | 包数 | 站点数 |
   186	|---|---|---|
   187	| 已写有识别子句的包 | **10 个源码包**（去重后 8 个包名） | 45 处独立站点 |
   188	| 有 `catch (...)` 且有线程操作、但无识别子句 | 90 个 | 3,364 处 |
   189	
   190	需要说明的是，第二类**在当前的 libstdc++ 下就已经没有防护**——这些包如果今天在 libstdc++ 上被终止，同样会崩溃，不是迁移带来的。
   191	
   192	**我们的处理方式是：维持与 libstdc++ 一致，不额外处理这 90 个包。**
   193	
   194	原因有两点。一是这属于那些包自身的写法问题，与用哪套标准库无关；如果我们单方面为它们兜底，同一份代码在两套标准库下的行为就不一样了，反而给这些包的开发者制造困惑。二是真要处理，只能逐包修改源码，而我们逐处检查过 45 处已有识别子句的站点，**没有一处能确认改动之后还能保持原来的行为**——第二类的 3,364 处只会更难。
   195	
   196	因此我们的目标是**让迁移不引入新的问题**，而不是顺带修复 libstdc++ 下本来就存在的问题。这 90 个包在迁移前后的表现是一样的。
   197	
   198	### 状态
   199	
   200	**已解决。** 解决方案见后文第三节。

   204	## 问题二：libc++ 标准库自身的内部代码没有防护
   205	
   206	### 问题是什么
   207	
   208	问题一说的是应用代码。但我们随后发现了更大的一块：**libc++ 自己的实现内部，也大量存在「捕获所有异常」的写法**，而 libstdc++ 在同样位置是有识别子句的。
   209	
   210	这意味着：**应用代码一行不改、里面一个 `catch` 都没有，只要它用到标准库的常见功能，线程在其中被终止时同样会崩溃。**
   211	
   212	以输出流为例，libstdc++ 的写法是：
   213	
   214	```
   215	codes/gcc/libstdc++-v3/include/bits/ostream.tcc:81-87
   216	
   217	  __catch(__cxxabiv1::__forced_unwind&)
   218	    { this->_M_setstate(ios_base::badbit); __throw_exception_again; }
   219	  __catch(...)
   220	    { this->_M_setstate(ios_base::badbit); }
   221	```
   222	
   223	先设置状态位，然后**把线程终止原样放行**。
   224	
   225	libc++ 在对应位置的写法是这样（以输出流为例，其内部把出错处理收拢到一个函数里）：
   226	
   227	```cpp
   228	// codes/llvm/libcxx/src/ios.cpp
   229	
   230	void ios_base::__set_badbit_and_consider_rethrow() {
   231	    __rdstate_ |= badbit;
   232	    if (__exceptions_ & badbit)
   233	        throw;
   234	}
   235	```
   236	
   237	**注意这里没有任何识别线程终止的地方。** 调用它的位置是一个裸的 `catch (...)`：捕获之后设一下状态位就结束了，线程终止被吞在这里，再也没有机会继续。
   238	
   239	只有当使用方事先设置过「出错时抛异常」这个开关时，末尾那个 `throw;` 才会执行——而**默认是不设的**，所以绝大多数情况下就是直接吞掉。
   240	
   241	### 复现步骤
   242	
   243	复现逻辑：让线程在标准库内部（而非应用代码中）被终止。**应用代码里不写任何 `catch`**，以证明问题出在标准库内部。
   244	
   245	```cpp
   246	static void *worker(void *) {          // 同样不是 noexcept
   247	    for (int i = 0; ; ++i) {
   248	        std::cout << i << std::endl;   // 底层的写操作本身就是取消点
   249	    }
   250	    return nullptr;
   251	}
   252	
   253	int main() {
   254	    pthread_t t;
   255	    pthread_create(&t, nullptr, worker, nullptr);
   256	    usleep(50 * 1000);
   257	    pthread_cancel(t);
   258	    void *result = nullptr;
   259	    pthread_join(t, &result);
   260	    return result == PTHREAD_CANCELED ? 0 : 1;
   261	}
   262	```
   263	
   264	**实测结果**（两种架构一致）：
   265	
   266	| 场景 | libstdc++ | libc++ |
   267	|---|---|---|
   268	| 线程正在 `std::cout` 输出时被终止 | 正常结束 | **进程崩溃** |
   269	| 线程阻塞在 `std::getline` 时被终止 | 正常结束 | **进程崩溃** |
   270	| 线程在 `std::packaged_task` / `std::async` 中被终止 | 正常结束 | **进程崩溃** |
   271	
   272	我们同时验证了：**只做问题一的修复对这三个场景毫无作用**，因为那只是提供了「可识别的类型」，而 libc++ 的内部代码里根本没有使用它的地方。
   273	
   274	### 影响面
   275	
   276	libc++ 内部共 **50 处**这样的位置。使用相关功能的包共 **329 个**，其中 **147 个**同时存在线程操作。
   277	
   278	需要说明这两个数的性质：它们来自源码特征扫描，是**候选上界**。扫描能看出「这个包用了相关功能、也有线程操作」，但**不能证明运行时真的会在那里被终止**。实际受影响的包数只会少于这个数，具体多少取决于运行期的实际情况。
   279	
   280	与问题一的 10 个包相比，**差了一个数量级**。
   281	
   282	### 一个关键点
   283	
   284	**应用侧无法自行规避。** 崩溃发生在标准库内部，应用代码里没有任何相关语句，开发者即使想改也无从下手。
   285	
   286	### 状态
   287	
   288	**已解决。** 解决方案见后文第三节。

   292	## 问题三：libc++ 的 `noexcept` 标注使线程终止变成进程终止
   293	
   294	这一项**已经查清，但尚未处置**，因此描述得详细一些。
   295	
   296	### 问题是什么
   297	
   298	C++ 里可以给函数标注 `noexcept`，表示「这个函数不会抛出异常」。如果异常真的试图穿过这样的函数，程序**立即终止**——这是语言规定的行为。
   299	
   300	而线程终止走的是异常的同一套机制。因此：**如果一个函数被标注了 `noexcept`，而线程恰好在它内部被终止，那么终止流程一穿到这个边界就会让进程死掉。**
   301	
   302	libc++ 给 `std::condition_variable::wait` 加了这个标注。声明处：
   303	
   304	```cpp
   305	// codes/llvm/libcxx/include/__condition_variable/condition_variable.h:104-107
   306	
   307	  void notify_one() _NOEXCEPT;
   308	  void notify_all() _NOEXCEPT;
   309	
   310	  void wait(unique_lock<mutex>& __lk) _NOEXCEPT;      // ← 就是这一行
   311	```
   312	
   313	定义处：
   314	
   315	```cpp
   316	// codes/llvm/libcxx/src/condition_variable.cpp:33-37
   317	
   318	void condition_variable::wait(unique_lock<mutex>& lk) noexcept {
   319	  if (!lk.owns_lock())
   320	    std::__throw_system_error(EPERM, "condition_variable::wait: mutex not locked");
   321	  int ec = __libcpp_condvar_wait(&__cv_, lk.mutex()->native_handle());
   322	  ...
   323	}
   324	```
   325	
   326	第 36 行的 `__libcpp_condvar_wait` 最终调用的是 `pthread_cond_wait`——**那是一个取消点**。也就是说，线程可以在这个函数内部被终止，**而这个函数本身被标注为不会抛异常**。两件事撞在一起，结果就是进程终止。
   327	
   328	同一个头文件里，三个带超时的等待函数（第 177、180、184 行）也都带着同样的标注，因此是同一类问题的另外三个入口。
   329	
   330	### 两家的政策正好相反
   331	
   332	标准对这个函数的规定是「不抛出」。
   333	
   334	- **libc++ 的政策是据此追加 `noexcept`**，其政策文档见
   335	  <https://libcxx.llvm.org/DesignDocs/NoexceptPolicy.html>
   336	- **GCC 则专门把这个标注移除了**，理由正是为了支持线程终止的强制展开。
   337	  讨论见 <https://gcc.gnu.org/pipermail/libstdc++/2021-December/053608.html>，
   338	  最终提交见 <https://gcc.gnu.org/pipermail/libstdc++/2021-December/053631.html>
   339	
   340	**两家在同一个点上做了相反的选择，而我们的平台恰好落在中间。**
   341	
   342	### 复现步骤
   343	
   344	复现逻辑：让一个线程阻塞在「等待另一个线程的结果」上，然后终止**这个等待的线程**。注意被终止的是等待方，不是干活的那一方——这是此前一直没有测过的方向。
   345	
   346	```cpp
   347	std::shared_future<int> *waiting_future;
   348	
   349	static void *waiting_side(void *) {    // 不是 noexcept
   350	    waiter_started.store(1);
   351	    waiting_future->wait();            // 阻塞在这里
   352	    return (void *)1;
   353	}
   354	
   355	int main() {
   356	    auto f = std::async(std::launch::async, some_work).share();
   357	    waiting_future = &f;
   358	    // 等 some_work 真正开始
   359	    pthread_t waiter;
   360	    pthread_create(&waiter, nullptr, waiting_side, nullptr);
   361	    while (!waiter_started.load()) usleep(1000);
   362	    pthread_cancel(waiter);            // 终止等待方
   363	    void *joined = nullptr;
   364	    pthread_join(waiter, &joined);
   365	    // 期望：等待方干净退出，主线程仍能取到结果
   366	    return (joined == PTHREAD_CANCELED && f.get() == 42) ? 0 : 1;
   367	}
   368	```
   369	
   370	**实测结果**（两种架构完全一致，各运行 20 次）：
   371	
   372	| 标准库 | 结果 |
   373	|---|---|
   374	| libc++ | **0/20 通过，全部退出 134** |
   375	| libstdc++ | **20/20 通过** |
   376	
   377	两套标准库在同一份代码上表现完全相反。
   378	
   379	### 根因：调用栈直接可见
   380	
   381	我们用调试器抓到了终止现场的调用栈：
   382	
   383	```
   384	#14  waiting_side()                     ← 我们的测试线程
   385	#13  shared_future<int>::wait()
   386	#12  __assoc_sub_state::wait()          libcxx/src/future.cpp:110
   387	#11  __assoc_sub_state::__sub_wait()    libcxx/src/future.cpp:121
   388	#10  condition_variable::wait()         libcxx/src/condition_variable.cpp:35
   389	#9   __clang_call_terminate()           ← 编译器为 noexcept 生成的终止桩
   390	#8   std::terminate()
   391	```
   392	
   393	第 9 帧的 `__clang_call_terminate` 是编译器专门为 `noexcept` 函数生成的。**强制展开撞上 `noexcept` 边界，当场终止**——这不是推断，是栈上直接可见的。
   394	
   395	### 为什么 libstdc++ 不会
   396	
   397	我们对照了两侧的完整调用路径，差异有两处：
   398	
   399	1. **结构不同**：libstdc++ 的 `future::wait()` 对这类任务是直接等待线程结束（`pthread_join`），而 libc++ 走的是条件变量等待（`pthread_cond_wait`）；
   400	2. **路径上有无 `noexcept` 边界**：libstdc++ 那条路径上**没有**，libc++ 那条路径上**有**。
   401	
   402	所以这不是「libstdc++ 多写了一个防护」，**而是两边的实现结构和标注政策共同造成的**。
   403	
   404	### 我们把同类位置全部枚举了
   405	
   406	用「被标注为不抛异常」× 「调用路径上有取消点」这两个条件做交集，逐一核对：
   407	
   408	**构成两套库实际差异的，共 5 处，全部可达：**
   409	
   410	| 编号 | 函数 | 位置 |
   411	|---|---|---|
   412	| D01 | `condition_variable::wait` | `libcxx/src/condition_variable.cpp:33-39` + `include/__condition_variable/condition_variable.h:107` |
   413	| D02 | `condition_variable::__do_timed_wait`（系统时钟） | `libcxx/src/condition_variable.cpp:41-63` + 头文件 `:175-177` |
   414	| D03 | `condition_variable::__do_timed_wait`（稳定时钟） | `include/__condition_variable/condition_variable.h:197-217` |
   415	| D04 | `condition_variable::__do_timed_wait`（自定义时钟） | `include/__condition_variable/condition_variable.h:220-224` |
   416	| D05 | `wbuffer_convert::~wbuffer_convert` | `include/__locale_dir/wbuffer_convert.h:119-126` |
   417	
   418	其中 D01、D03、D04 已动态确认；D02、D05 只取得了源码可达性证据，动态行为标注为未观测。
   419	
   420	**另有 8 处两侧共有**（libstdc++ 同样如此，因此不是迁移引入的）：`jthread` 的析构与移动赋值、`random_device` 析构、文件系统内部的文件描述符析构、输出流哨兵对象析构、同步流缓冲析构、文件缓冲析构、以及流初始化对象的析构。
   421	
   422	### 影响面
   423	
   424	按显式使用相关功能统计：**11 个源码 RPM / 9 个去重包名**。其中 5 个是工具链自身（`binutils` 的四个架构变体与 `gcc`），真正的平台运行时组件是 `angle`、`boost`、`libzypp`、`nnstreamer`。
   425	
   426	**需要说明的一处盲区**：源码扫描只能查「这个包自己有没有发起终止」，**查不到「别的组件终止了它的线程」**。在扫描范围内，我们没有找到能够闭合证明「相关等待线程确实会被终止」的包。
   427	
   428	### 触发需要同时满足的条件
   429	
   430	1. 有线程阻塞在条件变量等待中（`future.wait()`、`cv.wait()`、共享锁等待等）；
   431	2. 另一个线程对它发起终止；
   432	3. 终止恰好在它阻塞期间到达；
   433	4. 该线程的终止响应是启用的（默认启用）。
   434	
   435	**一旦触发，表现是进程直接终止，调用栈落在标准库内部，应用代码里找不到任何相关语句** —— 现场很容易被当成另一个问题排查很久。
   436	
   437	### 业界如何处理
   438	
   439	我们检索了公开资料：
   440	
   441	- **LLVM 官方**：其政策文档允许但不强制追加该标注；**我们没有找到关于这一冲突的公开议题或被拒记录**，说明 LLVM 社区可能没有讨论过这个组合；
   442	- **GCC**：正面处置，移除标注并用新的符号版本兼顾旧的二进制兼容性（出处见前）；
   443	- **Chromium**：采用协作式退出后等待线程结束的做法，不使用 `pthread_cancel`。
   444	  见 <https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/base/threading/thread.cc>
   445	- **Android**：其 C 库根本不提供 `pthread_cancel`。
   446	  见 <https://android.googlesource.com/platform/bionic/+/refs/heads/android11-dev/docs/status.md>
   447	
   448	**换句话说，除 GCC 外，其他项目都是回避而非解决。**
   449	
   450	### 状态
   451	
   452	**已查清，尚未处置。** 我们会继续跟进，寻找合适的处理方式。

   456	## 问题四：libstdc++ 有防护但 libc++ 没有对应位置的 8 处
   457	
   458	在比对两套库的防护位置时，有 8 处在 libc++ 中找不到对应的地方。逐处说明如下：
   459	
   460	| 编号 | libstdc++ 位置 | 是什么 | libc++ 的情况 |
   461	|---|---|---|---|
   462	| E1 | `include/experimental/executor:1734` | 实验性执行器的 `use_future` 完成处理 | **libc++ 22.1.8 不提供这个实验性扩展** |
   463	| E2 | `include/experimental/executor:1794` | 同上，执行器的 dispatch 路径 | 同上 |
   464	| E3 | `include/experimental/executor:1812` | 同上，执行器的 post 路径 | 同上 |
   465	| E4 | `include/experimental/executor:1830` | 同上，执行器的 defer 路径 | 同上 |
   466	| E5 | `include/ext/vstring.tcc:605` | GNU 自有字符串扩展的流提取 | **libc++ 不提供这个 GNU 扩展** |
   467	| E6 | `include/ext/vstring.tcc:681` | 同上的 `getline` | 同上 |
   468	| E7 | `include/std/condition_variable:268` | `condition_variable_any` 的作用域解锁守卫：活动异常期间重新加锁，重加锁若遇强制展开则放行 | **libc++ 有结构等价的位置**，但其析构函数是 `noexcept`，且直接调用用户提供的加锁操作 |
   469	| E8 | `include/tr2/dynamic_bitset.tcc:255` | TR2 动态位集扩展的流提取 | **libc++ 不提供这个扩展** |
   470	
   471	**结论**：8 处中有 7 处（E1–E6、E8）是 libstdc++ 独有的扩展功能，libc++ 根本不提供这些设施，因此「没有对应位置」是字面意义上的，不是遗漏。**只有 E7 在 libc++ 中有结构等价的位置。**
   472	
   473	### 我们的处理方式
   474	
   475	**那 7 处：不做处理。**
   476	
   477	这些是 libstdc++ 的自有扩展，不属于标准。代码如果用了它们，迁移到 libc++ 时**在编译阶段就会报错**——因为设施本身不存在，而不是「能编过但行为不对」。也就是说，这类问题不会藏到运行时才暴露，而是迁移时立刻可见，届时由使用方改用标准设施即可。
   478	
   479	平台上是否有软件包在使用这三个扩展，我们尚未专门统计——但由于它们在迁移时会直接编译失败，不存在遗漏到运行时的风险，因此我们把它留给迁移过程自然暴露。
   480	
   481	**E7：并入问题三一起看。**
   482	
   483	libc++ 里对应的位置是 `condition_variable_any` 的一个内部辅助结构，它的析构函数被标注为不会抛异常，而析构过程中会调用使用方提供的加锁操作——**这正是问题三所说的那种情形**，只是入口不同。
   484	
   485	因此我们不把它当作单独一项，而是并入问题三，随那 5 处一起跟进。

   489	## 问题五：有两处防护补上也不会生效（两套库皆然）
   490	
   491	这一项**不是两套库的差异**——libstdc++ 在对应位置的情况完全相同。我们把它列出来，是因为它解释了一个容易让人困惑的现象：**有些位置即使写了防护，线程终止时也永远走不到那里。**
   492	
   493	| 位置 | 原因 |
   494	|---|---|
   495	| `basic_string::shrink_to_fit` | 该函数标注为不抛异常。线程终止穿过这个边界时，按语言规定当场终止进程，根本到不了函数内部的防护 |
   496	| `basic_ostream<char>::sentry::~sentry()` | 析构函数隐式带有同样的标注，同理 |
   497	
   498	这与问题三是同一个机制——**不抛异常的标注挡在了前面**，只不过这两处在 libstdc++ 上也一样，所以不构成迁移带来的变化。
   499	
   500	### 如何自行确认
   501	
   502	**复现逻辑**：要观察这个现象，必须让取消**恰好在那个函数内部**被送达。普通写法做不到——`shrink_to_fit` 内部没有取消点，延迟取消送不进去。因此我们用一个自定义分配器，在它的 `allocate()` 里放一个取消点：字符串重新分配时会调到那里，取消就落在了 `shrink_to_fit` 这个不抛异常的边界之内。
   503	
   504	```cpp
   505	#include <pthread.h>
   506	#include <unistd.h>
   507	#include <atomic>
   508	#include <cstdio>
   509	#include <string>
   510	
   511	static std::atomic<int> cancel_ready{0};
   512	
   513	template <class T> struct CancelAllocator {
   514	    using value_type = T;
   515	    CancelAllocator() = default;
   516	    template <class U> CancelAllocator(const CancelAllocator<U>&) {}
   517	
   518	    T *allocate(std::size_t n) {
   519	        cancel_ready.store(1);
   520	        for (;;) pthread_testcancel();   // 取消在这里被送达——位于 shrink_to_fit 内部
   521	        return nullptr;
   522	    }
   523	    void deallocate(T *p, std::size_t) noexcept { ::operator delete(p); }
   524	};
   525	
   526	using CancelString =
   527	    std::basic_string<char, std::char_traits<char>, CancelAllocator<char>>;
   528	
   529	static void *worker(void *) {            // 不加 noexcept
   530	    CancelString s(1024, 'x');
   531	    s.reserve(65536);
   532	    s.shrink_to_fit();                   // 触发重新分配 → 进入 allocate()
   533	    return nullptr;
   534	}
   535	
   536	int main() {
   537	    pthread_t thread{};
   538	    void *result = nullptr;
   539	    pthread_create(&thread, nullptr, worker, nullptr);
   540	    while (cancel_ready.load() == 0) usleep(1000);
   541	    pthread_cancel(thread);
   542	    pthread_join(thread, &result);
   543	    std::printf("RESULT joined=%s\n",
   544	                result == PTHREAD_CANCELED ? "PTHREAD_CANCELED" : "other");
   545	    return result == PTHREAD_CANCELED ? 0 : 1;
   546	}
   547	```
   548	
   549	**实测结果**（x86_64）：**两套标准库都得到进程终止**，而不是线程干净退出。终止发生在 `shrink_to_fit` 这个边界上，函数内部写没写防护都一样。
   550	
   551	需要说明的是：这个用例证明的是**「终止确实发生在这个边界上」**；至于「补上防护之后会不会生效」，由于终止在到达防护之前就发生了，**我们没有观察到防护被执行**，这一点如实记录为未观测。
   552	
   553	`basic_ostream<char>::sentry` 的析构同理，它是隐式带有同样标注的。
   554	
   555	## 问题六：有一种线程终止模式会绕过全部防护（两套库皆然）
   556	
   557	前面几项讨论的都是默认的终止模式——终止请求送到线程后，会等到线程执行到一个「取消点」才真正生效。
   558	
   559	还有另一种模式（异步取消）：终止请求可以在**任意一条指令处**生效，不必等到取消点。
   560	
   561	**在这种模式下，上述全部防护都不起作用。** 我们用调试器确认过：该模式下的终止流程根本不会进入 C++ 的异常处理例程，因此无论 libc++ 还是 libstdc++，写在那里的防护代码都不会被执行。
   562	
   563	这**不是迁移带来的差异**——两套标准库表现一致。但它意味着：**如果产品中有组件使用这种模式，它不在本方案的保护范围内。**
   564	
   565	我们会检索这种模式在产品中的实际使用情况。

   656	| D-21 | 标准允许实现自行决定的行为两侧不同，涉及容器的分块策略、文件与字符串缓冲、区域设置与时区数据 |
   657	| D-22 | armv7l 的异常展开路径与 64 位完全独立 —— **问题一的一处缺陷正是只在 armv7l 上出现**，因此这一项已有实例 |
   658	| D-23 | 动态加载的插件边界上的标准库、类型信息、异常对象所有权，以及卸载时的生命周期 |
   659	| D-24 | LLVM 官方随 libc++ / libc++abi 发布的测试套件，尚未在本平台配置下全量运行 —— armv7l 实机上单一构建可运行 10,320 项，两种构建合计 20,640 次执行；x86_64 另有一套。目前只运行过约 80 项 |
   660	
   661	---
   662	
   663	## 我们的解决方案
   664	
   665	针对问题一与问题二，方案分三个部分。
   666	
   667	### 第一部分：修复运行时的两处缺陷
   668	
   669	**（一）重新放行时用错了接口。**
   670	
   671	C++ 里的 `throw;`（不带参数的重新抛出）在运行时会走到一个内部函数。libc++ 的实现在处理外来异常时，调用的是 `_Unwind_RaiseException`——**这是「发起一次全新的异常传播」的接口**。
   672	
   673	而正确的做法是 `_Unwind_Resume_or_Rethrow`——**它会先检查「当前是不是正处在一次强制展开当中」，如果是就继续那次展开，而不是另起一次**。
   674	
   675	libstdc++ 在同样位置用的正是后者：
   676	
   677	```cpp
   678	// codes/gcc/libstdc++-v3/libsupc++/eh_throw.cc:123-131
   679	
   680	#ifdef __USING_SJLJ_EXCEPTIONS__
   681	      _Unwind_SjLj_Resume_or_Rethrow (&header->unwindHeader);
   682	#else
   683	#if defined(_LIBUNWIND_STD_ABI)
   684	      _Unwind_RaiseException (&header->unwindHeader);
   685	#else
   686	      _Unwind_Resume_or_Rethrow (&header->unwindHeader);    // ← 我们平台走的是这一支
   687	#endif
   688	#endif
   689	```
   690	
   691	**两者的差别在后果上很直接**：线程终止流程是由 glibc 发起的，它在发起时登记了一个「收尾回调」。用「继续原有展开」的接口，那个回调会在展开走完时被正常调用，线程干净结束；而用「发起新异常」的接口，等于把线程终止当成了一个普通异常重新抛出去——**glibc 那个收尾回调再也不会被调用**，异常一路上抛没人接手，最终终止进程。
   692	
   693	**（二）ARM 架构上的一处处理错误。**
   694	
   695	32 位 ARM 的异常展开是一套与 64 位完全独立的实现。libc++ 的运行时在那条路径上，把「捕获处理」误当作「清理处理」登记，导致内部记录无法配对，后续遇到真正的清理点时终止。
   696	
   697	这处缺陷源自 LLVM 官方 2021 年的一次改动：那次改动给 ARM 路径加上了强制展开的支持，但没有同步更新相关的调用点。
   698	
   699	**这两处属于纯粹的缺陷修复**，其价值不依赖方案的其余部分。修复后，应用代码中常见的「捕获后重新放行」写法在 libc++ 下也能正常工作。
   700	
   701	**验证**：LLVM 官方随 libc++abi 发布的相关测试，两种架构各 20 项全部通过（armv7l 在开发板上实际运行，不使用模拟器）。
   702	
   703	### 第二部分：补齐缺失的识别类型
   704	
   705	在 libc++ 的运行时中提供与 libstdc++ 对应的识别类型，形态完全一致——同样是不可实例化的抽象类，因此只能按引用捕获、不能按值捕获。
   706	
   707	我们验证了七种写法在两套库下的行为**逐项一致**：按常量引用捕获、按非常量引用捕获（均可编译）；按值捕获、继承该类型、对其使用 `new` 与 `delete`（均编译失败）。
   708	
   709	这样做的目的是：**应用代码在两套标准库下可以使用同一份写法**，不需要为迁移而分叉。
   710	
   711	### 第三部分：为 libc++ 自身补上防护
   712	
   713	在 libc++ 内部那 50 处位置，补上与 libstdc++ 对应的识别与放行逻辑。
   714	
   715	这 50 处按**是否需要重新编译使用它的软件包**分为两批：
   716	
   717	| 批次 | 数量 | 影响 |
   718	|---|---|---|
   719	| 只需更新标准库本身 | **30 处** | 不影响任何软件包，随标准库更新发布即可 |
   720	| 需要使用方重新编译 | **20 处** | **必须赶在软件包开始迁移编译之前就位** |
   721	
   722	**两批的区别在于这些代码存放的位置。** 第一批那 30 处，其代码编译在标准库的库文件里，软件包运行时才去调用它——所以更新库文件，所有软件包立刻都能用上新的行为。第二批那 20 处位于头文件中，而头文件里的代码是在**每个软件包自己编译的时候被复制进该包的二进制里**的；库文件再怎么更新，也改变不了已经复制出去的那些副本，所以只能由软件包重新编译一次才能带上。
   723	
   724	第二批的时序要求需要特别说明：它一旦晚于软件包的迁移编译，那些包就要再编译一次。**但如果赶在迁移开始之前就位，则不产生任何额外成本**——因为迁移本身就要求全部重新编译。
   725	
   726	### 贯穿方案的一条原则
   727	
   728	**改实现，不改行为。** 凡是 libstdc++ 有对应处理的地方，我们一律与其保持一致。
   729	
   730	原因是：如果行为出现差异，483 个软件包的开发者就需要重新理解一套 Tizen 特有的行为——**那等于把迁移的成本转嫁给了所有人**。
   731

   733	
   734	## 对产品的影响
   735	
   736	### 已经消除的
   737	
   738	问题一与问题二所述的崩溃，在应用了上述方案后不再发生。我们在 x86_64 与 armv7l 两种架构上验证了：线程终止、线程主动退出、真实异常不被误判、非终止的外来异常行为不变、多线程同时终止、终止与异常并发、重复终止等场景，均与 libstdc++ 表现一致。
   739	
   740	### 仍然存在的
   741	
   742	**问题三所述的 5 处，加上问题四并入的 1 处（E7），共 6 处。** 触发需要同时满足四个条件，且在源码扫描范围内我们没有找到能够闭合证明其会发生的包。但**外部组件发起的终止是扫描的盲区**，因此不能断言它不会发生。
   743	
   744	一旦发生，表现是进程直接终止，调用栈落在标准库内部，**归因困难**。
   745	
   746	我们建议在产品验证阶段专门覆盖这一场景，即构造「终止一个正在等待的线程」的用例实际运行一遍。
   747	
   748	### 尚未验证的
   749	
   750	- **aarch64 架构上的全部验证** —— 本报告中的所有实测都在 x86_64 与 armv7l 上完成；
   751	- LLVM 官方测试套件的全量运行（armv7l 单一构建 10,320 项，两种构建合计 20,640 次执行；x86_64 另有一套。目前已运行约 80 项）；
   752	- 问题七所列各项的实际影响范围。

   756	## 附：关于复现用例
   757	
   758	本材料中列出的用例都是完整可编译的，可以直接复制运行。为便于对照，各用例都遵循同样的形态要求：
   759	
   760	- **线程函数不加 `noexcept`** —— 否则线程终止穿过这个边界本身就会终止进程，那是另一回事，会掩盖真正要测的现象；
   761	- **使用裸的 `pthread_create`，不用 `std::thread`** —— 后者有自己的包装层，会引入额外变量；
   762	- **取消点明确** —— 或者依赖 I/O 调用自身的取消点，或者显式调用 `pthread_testcancel()`；
   763	- **测标准库内部问题时，应用代码里不写任何 `catch`** —— 否则就分不清是应用层拦下的还是标准库拦下的；
   764	- **判定不只看进程退出码** —— 还要断言真正关心的东西，例如线程的结束状态、流对象的状态位、任务的实际执行次数。
   765	
   766	最后一条是我们中途补上的：早期只看退出码，因而漏掉了一处「状态位没有正确写入」的问题——进程没崩，但状态是错的。
