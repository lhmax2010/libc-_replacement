As of O there were exactly two exceptions, but there are likely to be more in future because of Project Treble.</p><h3><a class="h" name="Invalid-handling-targetSdkVersion-O" href="#Invalid-handling-targetSdkVersion-O"><span></span></a><a class="h" name="invalid-handling-targetsdkversion-o" href="#invalid-handling-targetsdkversion-o"><span></span></a>Invalid <code class="code">pthread_t</code> handling (targetSdkVersion &gt;= O)</h3><p>As part of a long-term goal to remove the global thread list, and in an attempt to flush out racy code, we changed how an invalid <code class="code">pthread_t</code> is handled. For <code class="code">pthread_detach</code>, <code class="code">pthread_getcpuclockid</code>, <code class="code">pthread_getschedparam</code>/<code class="code">pthread_setschedparam</code>, <code class="code">pthread_join</code>, and <code class="code">pthread_kill</code>, instead of returning ESRCH when passed an invalid <code class="code">pthread_t</code>, if you&lsquo;re targeting O or above, they&rsquo;ll abort with the message &ldquo;attempt to use invalid pthread_t&rdquo;.</p><p>Note that this doesn&#39;t change behavior as much as you might think: the old lookup only held the global thread list lock for the duration of the lookup, so there was still a race between that and the dereference in the caller, given that callers actually need the tid to pass to some syscall or other, and sometimes update fields in the <code class="code">pthread_internal_t</code> struct too.</p><p>We can&lsquo;t check a thread&rsquo;s tid against 0 to see whether a <code class="code">pthread_t</code> is still valid because a dead thread gets its thread struct unmapped along with its stack, so the dereference isn&#39;t safe.</p><p>To fix your code, taking the affected functions one by one:</p><ul><li><p><code class="code">pthread_getcpuclockid</code> and <code class="code">pthread_getschedparam</code>/<code class="code">pthread_setschedparam</code> should be fine. Unsafe calls to those seem highly unlikely.</p></li><li><p>Unsafe <code class="code">pthread_detach</code> callers probably want to switch to <code class="code">pthread_attr_setdetachstate</code> instead, or use <code class="code">pthread_detach(pthread_self());</code> from the new thread&#39;s start routine rather than calling detach in the parent.</p></li><li><p><code class="code">pthread_join</code> calls should be safe anyway, because a joinable thread won&lsquo;t actually exit and unmap until it&rsquo;s joined. If you&lsquo;re joining an unjoinable thread, the fix is to stop marking it detached. If you&rsquo;re joining an already-joined thread, you need to rethink your design!</p></li><li><p>Unsafe <code class="code">pthread_kill</code> calls aren&lsquo;t portably fixable. (And are obviously inherently non-portable as-is.) The best alternative on Android is to use <code class="code">pthread_gettid_np</code> at some point that you know the thread to be alive, and then call <code class="code">kill</code>/<code class="code">tgkill</code> with signal 0 (which checks whether a process exists rather than actually sending a signal). That&rsquo;s still not completely safe because if you&#39;re too late the tid may have been reused, but your code is inherently unsafe without a redesign anyway.</p></li></ul><h3><a class="h" name="Interruptable-targetSdkVersion-N" href="#Interruptable-targetSdkVersion-N"><span></span></a><a class="h" name="interruptable-targetsdkversion-n" href="#interruptable-targetsdkversion-n"><span></span></a>Interruptable <code class="code">sem_wait</code> (targetSdkVersion &gt;= N)</h3><p>POSIX says that <code class="code">sem_wait</code> can be interrupted by delivery of a signal. This wasn&#39;t historically true in Android, and when we fixed this bug we found that existing code relied on the old behavior. To preserve compatibility, <code class="code">sem_wait</code> can only return EINTR on Android if the app targets N or later.</p><h2><a class="h" name="FORTIFY" href="#FORTIFY"><span></span></a><a class="h" name="fortify" href="#fortify"><span></span></a>FORTIFY</h2><p>The <code class="code">_FORTIFY_SOURCE</code> macro can be used to enable extra automatic bounds checking for common libc functions. If a buffer overrun is detected, the program is safely aborted as in this <a href="https://source.android.com/devices/tech/debug/native-crash#fortify">example</a>.</p><p>Note that in recent releases Android&#39;s FORTIFY has been extended to cover other issues. It can now detect, for example, passing <code class="code">O_CREAT</code> to open(2) without specifying a mode. It also performs some checking regardless of whether the caller was built with FORTIFY enabled. In P, for example, calling a <code class="code">pthread_mutex_</code> function on a destroyed mutex, calling a <code class="code">&lt;dirent.h&gt;</code> function on a null pointer, using <code class="code">%n</code> with the printf(3) family, or using the scanf(3) <code class="code">m</code> modifier incorrectly will all result in FORTIFY failures even for code not built with FORTIFY.</p><p>More background information is available in our <a href="https://android-developers.googleblog.com/2017/04/fortify-in-android.html">FORTIFY in Android</a> blog post.</p><p>The Android platform is built with <code class="code">-D_FORTIFY_SOURCE=2</code>, but NDK users need to manually enable FORTIFY by setting that themselves in whatever build system they&lsquo;re using. The exact subset of FORTIFY available to NDK users will depend on their target ABI level, because when a FORTIFY check can&rsquo;t be guaranteed at compile-time, a call to a run-time <code class="code">_chk</code> function is added.</p></div></div></div><!-- default customFooter --><footer class="Site-footer"><div class="Footer"><span class="Footer-poweredBy">Powered by <a href="https://gerrit.googlesource.com/gitiles/">Gitiles</a>| <a href="https://policies.google.com/privacy">Privacy</a>| <a href="https://policies.google.com/terms">Terms</a></span><div class="Footer-links"><a class="Footer-link" href="/platform/bionic/+show/refs/heads/android11-dev/docs/status.md">source</a></div></div></footer></body></html>
