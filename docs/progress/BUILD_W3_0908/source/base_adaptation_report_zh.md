# Tizen Base 层 libc++ 适配报告

- 日期：2026-09-04
- 范围：`Tizen-Base-Toolchain` 全部源码包
- 架构：armv7l、aarch64、x86_64

---

## 一、本周要解决的问题

Tizen-Base-Toolchain 的 project_config 中，**是否应统一注入 libc++ 编译
选项**。

这取决于需要适配的包有多少：

- **数量少** → 在各包的 spec 中单独启用，全局配置不动；
- **数量多** → 全局注入，再在少数不适用的包中规避。

为得出结论，我们对该范围内的全部 **254 个源码包**逐个做了判定。

---

## 二、判定结果

**需要适配的仅 11 个，因此采用逐包启用。**

| 判定 | 数量 |
|---|---:|
| 需要适配 | **11** |
| 不需要适配 | 237 |
| 当前不可迁移 | 6 |
| 未定 | 0 |
| **合计** | **254** |

需要适配的 11 个包：

```
abseil-cpp   bcc-tools   boost      bpftrace    icu
jsoncpp      libsigc++   llvm       pcre        taglib
tensorflow2
```

### 判定依据

254 个包中，按成功构建日志、C++ runtime 依赖、静态归档外部 C++ 符号和
C++ 头文件载体四类机械证据识别出的候选并集为 73 个。这个数字是已声明口径
下的候选数，不是“绝对完整的 C++ 源码包全集”；普通 `.h`、未覆盖 ELF 符号、
动态加载及预编译私有代码等仍是方法边界。**含 C++ 并不等于需要适配** —— 两套标准库在
同一系统中共存本身不构成问题，风险来自**跨标准库边界传递 C++ 语义**：
容器、字符串、智能指针、异常、RTTI、内存所有权。

因此以下情形判定为不需要适配：

| 情形 | 依据 |
|---|---|
| 仅构建期使用，产物不进入设备 | 不存在运行时边界 |
| 对外仅暴露 C 接口 | 跨边界只传 C 类型，两侧标准库不同不受影响 |
| 仅提供头文件，由消费方编译 | 该代码继承消费方的标准库 |
| 经链接核查，C++ 静态代码未进入消费方产物 | 边界实际不存在 |

每个包的具体依据见随附清单。

### 逐包启用与全局注入的对比

全局注入**需要适配的仍是这 11 个**，但会额外波及：

| 影响面 | 数量 | 后果 |
|---|---:|---|
| 显式走 GCC 路径的包 | 6 | 若选项实际到达 GCC driver：已测 armv7l/x86_64 会直接失败；aarch64 未观测 |
| 已判定不需要适配的 C++ 包 | 55 | 若选项实际到达 Clang++ driver：三架构会实际切换到 libc++；逐包传播未验证 |

**证据与其边界**：上述影响面基于编译器 driver 探针，**不是对这 61 个包的
逐包完整构建**。已测得：

| 项 | 结果 |
|---|---|
| armv7l / x86_64 的 GCC 14.2.0 | **明确拒绝 `-stdlib=libc++`**，不静默忽略 |
| aarch64 的 GCC | `--version` 即异常退出，**该选项的行为未观测** |
| 三架构的 Clang++ 22.1.8 | 接受该选项，`-###` 确认实际选择了 libc++ |

因此准确的表述是：**全局注入会把 6 个当前走 GCC 路径的包与 55 个无迁移
需求的 C++ 包置于影响范围；在选项实际到达编译器 driver 时，已测的 GCC 会
报错，Clang++ 会切换到 libc++。各包构建系统是否都会将该选项传递到最终
命令，尚未逐包实测。**

> 「当前不可迁移」描述的是这些包现有的工具链配置与产品角色，**不是永久性
> 技术结论**。

### 三个包未完成的原因

**LLVM 捆绑的 MLGO / XLA AOT 预编译对象按 libstdc++ ABI 生成**，与 libc++
编译的新代码链接时符号不匹配：前者使用 `std::__cxx11`，后者使用 `std::__1`，
两者在符号名层面是不同的实体。链接 `libLLVM.so.22.1` 时失败。

另两个包必须与 LLVM 协同处理：

| 依赖边 | 已证明布局敏感的 C++ 符号数 |
|---|---:|
| `bcc-tools` → `llvm` | 584 |
| `bpftrace` → `llvm` | 201 |

若只切换链条一端，这些边界将从"两侧标准库一致"变为"两侧不一致"——
**部分迁移的风险高于不迁移**。

**下周计划**：重新生成基于 libc++ 的 MLGO / XLA AOT 资产，所需的模型、
脚本与构建代码已定位（`sandbox/lhmax2025/mlgo_aot_v3` 与
`sandbox/lhmax2025/mlgo_aot_temp`）。资产就绪后按
`libcxx-runtimes → llvm → bcc-tools → bpftrace` 的顺序完成三包适配与验证。

## 四、与总部 step0 数据的关系

step0 分析给出：Tizen-Base 共 639 个二进制包，其中 91 个依赖 libstdc++。

**该数据与本轮结果不构成直接对比关系**，原因有三：

### 1. 仓库范围不同

| | 范围 |
|---|---|
| step0 | `Tizen-Base` |
| 本轮 | `Tizen-Base-Toolchain` |

### 2. 统计单位不同

| | 单位 |
|---|---|
| step0 的 639 / 91 | **二进制包** |
| 本轮的 254 / 73 / 11 | **源码包** |

一个源码包可以产出多个二进制 RPM。以本轮 armv7l/x86_64 的 Boost 验证构建
为例，每个架构生成 33 个 RPM；这些 RPM 中合计包含 39 个 ELF。RPM 数与 ELF
数是不同单位，不能混用。

### 3. step0 的数字无法严格复现

step0 统计取自**未记录 revision、未固定时间点**的滚动仓库，事后无法恢复同一
输入。以固定快照重新统计 `Tizen-Base`：

| 指标 | step0 | 固定快照重算 |
|---|---:|---:|
| 二进制包总数 | 639 | **646** |
| 依赖 libstdc++ | 91 | **83** |

> 另有一种统计方式（扫描 RPM payload 内 ELF 的 `DT_NEEDED`、排除
> noarch 与 riscv64）可得到 91，但方法与原口径不同，不能替代原数字。

### 4. 两仓包集合基本一致

| | 源码包数 |
|---|---:|
| 两仓共有 | 250 |
| 仅 `Tizen-Base` 有 | 1（`toybox`） |
| 仅 `Tizen-Base-Toolchain` 有 | 4 |

`toybox` 无 C++ runtime ELF，依赖元数据亦不要求 libstdc++，**不构成遗漏的
迁移对象**。

**结论**：两组数据描述不同仓库与不同统计单位，不能直接比较；step0 的 639/91 因原始
输入未固定，现不能严格复现。就本次比较的两个固定快照及已声明的 C++ 候选与
边界判定口径而言，未发现因两个 Base 仓集合差异而漏掉的 libc++ 迁移对象；
这不是对未来快照或其他仓库的永久断言。

## 五、本轮判定的适用边界

以下几点说明本次结论在什么条件下成立，以及哪些内容不在本轮范围。

**1. 判定基于一个固定时间点的代码与构建数据**

我们把仓库、构建记录、镜像清单都固定在某一版本上分析，以保证结论可复核。
因此如果之后有新包加入、现有包的代码更新、或出现新的动态加载关系，
**这些新增部分需要重新核对**，本轮结论不自动覆盖。

**2. 设备镜像的判断基于六份已有清单**

判断一个包是否进入设备，我们用的是已经取得的六份镜像清单
（boot / headed / headless，各对应 aarch64 与 armv7l）。
**其他产品配置的镜像我们没有取到**，若某个包只出现在那些配置中，
本轮不会发现。

**3. 三个未完成的包尚未验证**

`llvm`、`bcc-tools`、`bpftrace` 的适配依赖 MLGO / XLA AOT 资产重建，
资产未就绪之前，这三个包的协同验证无法进行。

**4. 以下两项属于其他工作线，不在本轮范围**

- **Unified 侧的包适配** —— 本轮只处理 Base 层；
- **运行时行为验证** —— 本轮只回答「能否正确编译与链接」，
  不回答「运行起来行为是否正确」。后者由专门的工作线负责。
