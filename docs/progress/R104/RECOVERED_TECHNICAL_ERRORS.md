# 恢复记录：未进入日志包装器的技术性错误

## LLVM 首次启动尝试（编号 088）

本条是会话恢复记录，不是日志包装器自动生成的原始文件。

首次从 `codes/R104/llvm` 作为工作目录启动构建时，调用了相对于项目根的
日志包装器路径：

```text
bash progress/R104/code/run_logged.sh 088 build_llvm_armv7l_libcxx ...
```

因为该相对路径在 LLVM 子仓工作目录下不存在，shell 返回 `127`；GBS
没有启动，也没有产生编号 088 的 `command/stdout/stderr/exitcode` 四件套。
随后改用日志包装器的绝对路径重新执行，形成编号 089 的完整记录。该次
技术性错误没有修改源码、没有创建构建根，也不影响编号 089 的失败判定。

限制：压缩后的会话摘要保留了错误性质、退出码和路径原因，但未保留那次
工具调用的完整参数序列；因此本记录不把省略号冒充原始命令。可审计的实际
构建命令以 `raw/089_build_llvm_armv7l_libcxx.command.txt` 为准。

## 本轮新增的技术性记录

- 编号 337：直接执行没有执行位的 `run_logged.sh`，shell 返回 126，命令未
  进入包装器；编号 338 又把“编号/标签”参数错位，返回 127。编号 339 使用
  正确调用形式后完成同一只读检索。
- 编号 342：引用了并不存在的简写文件名，返回 2；编号 343 使用实际的
  `*_retry` 文件名后完成同一只读核对。
- 编号 344、345：循环变量被错误转义为字面量 `$p`，返回 128；编号 346
  完成同一仓库状态核对。
- 编号 347：对 Boost 构建进程组发送 SIGINT，命令本身返回 0，但目标未停止；
  编号 348 发送 SIGTERM 后，外层矩阵状态为 143。SIGTERM 同时结束了编号
  324 的日志包装器，所以没有自动生成的 324 exitcode；该事实单列在
  `raw/324_build_boost_aarch64_libcxx.recovery_note.txt`，没有伪造退出码。
- 编号 349：清理 root 所有的残留日志转发进程时权限不足，返回 1；编号 350
  尝试 sudo，但当前环境无法交互提供凭据，也返回 1。该零 CPU 进程随后随
  构建管道关闭自然退出，最终进程审计未再发现残留。
- 编号 370：10 个普通仓的远端分支核对通过，`tensorflow2` 因其分支快照存放
  在不同子目录而在最后一步返回 2；编号 371 的修正命令仍有字面变量路径
  错误，返回 128；编号 372 使用明确路径后确认 tensorflow2 的目标 SHA 与
  其他既有分支均未变化。

以上均是命令路径、包装或恢复记录问题，不是构建判据失败。真正的判据失败
分别是 LLVM/MLGO 链接、Boost 最终产物仍为 libstdc++、libsigc++ 严格
`DT_NEEDED` 判据、TensorFlow libc++ 源码编译错误，均在阶段报告中单列。

## 恢复期间未经过包装器的只读监控

恢复会话中若干次 `ps`、`tail`、`free`、`find`、`git status` 与 `du` 是为确认
唯一活动构建、进度、内存和材料规模而直接执行，未生成逐条四件套；另有多次
重复 `rsync` 用于把刚生成的归档审计记录补入 `docs/`。这些命令没有改包仓
内容，`rsync` 的唯一目标是本项目的 `docs/progress/R104/`。其瞬时进程/内存
输出不能事后逐字恢复，记为 `NOT_AVAILABLE`；最终等价审计已由编号 346、
370–373、380–383 落盘。所有构建、验证、包提交和外部推送命令均经过包装器，
不在这一缺口内。
