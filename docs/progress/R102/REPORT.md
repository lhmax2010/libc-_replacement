# R102：Base 层 libc++ 判定理由的对外说明版

## 1. 结论

已把 R101 清单中 254 个包的“理由”逐项改写成可独立阅读的说明。每条理由均包含：

1. 包的用途；
2. 它与 C++ 标准库的实测关系；
3. 为什么该关系支持原有的“需要改 / 不需要改 / 当前不能改 / 未定”判定。

一致性校验结果：254 个包的顺序不变，除“理由”外的七列逐字段相同，四类判定仍为：

| 判定 | 数量 |
|---|---:|
| 需要改 | 10 |
| 不需要改 | 236 |
| 当前不能改 | 6 |
| 未定 | 2 |

没有发现 R100/R101 的既有判定有问题；本任务未重新分类任何包。

## 2. 输入与改写边界

- 原表：`docs/progress/R101/tables/base_all_source_packages.tsv`。
- 判定证据：R100 的 73 个 C++ 候选判定、armv7l 的 Unified→Base 与 Base
  内部精确 ELF/符号边、三架构构建与 RPM 元数据、六份标准镜像清单。
- 包用途：沿用原表证据列保存的仓库 `Summary`；254/254 都有该字段。
- 为避免把翻译或常识当成新证据，普通包的用途直接引用仓库原始英文摘要；10 个
  需要改的包、两个未定包、`bison`、`cereal` 和 `libcxx-runtimes` 在中文概括后
  仍保留原始摘要供核对。
- 精确运行时符号边只覆盖 armv7l，因此凡依赖该证据的理由都明确写出架构，不将
  其表述成三架构实测。

“不含 C++”不是用泛泛的“没查到”作安全结论，而是复述已完成的四项候选门禁：
实际构建日志、动态 C++ 运行时依赖、静态归档全局 C++ 符号、C++ 头文件载体均为
否。其余“不需要改”包则引用正面的拓扑或接口分类证据。

## 3. 10 个“需要改”包的改写重点

| 包 | 已实测的 C++ 交互 | 不改的后果如何表述 |
|---|---|---|
| `abseil-cpp` | 8 个 Unified runtime consumer 有 C++ ABI 边，其中 7 个 consumer 的边含布局敏感类型 | 会保留已证明的跨标准库对象布局边 |
| `bcc-tools` | Base 内部以布局敏感 C++ 接口调用 `llvm` | 与需迁移的 LLVM 形成混合运行时边界 |
| `boost` | 12 个 Unified consumer 有 C++ ABI 边，其中 6 个含布局敏感类型 | 容器/所有权/析构可能被另一套实现解释 |
| `bpftrace` | Base 内部以布局敏感 C++ 接口调用 `llvm` | 与需迁移的 LLVM 形成混合运行时边界 |
| `icu` | 8 个 Unified consumer 有 C++ ABI 边，其中 2 个含布局敏感类型 | 会保留实测 C++ ABI 和布局边；另有纯 C consumer 不作为迁移理由 |
| `jsoncpp` | 13 个 Unified consumer 有 C++ ABI 边，其中 11 个含布局敏感类型 | JSON C++ 对象边可能静默错读或错误析构 |
| `libsigc++` | `glibmm`、`libzypp` 有已确认 C++ ABI 耦合 | 即使现有符号不足以证明具体布局，也不能保证跨库 ABI 语义 |
| `llvm` | Unified 的 `rpi4-linux-kernel` 有 C++ ABI 边；Base 内 BCC、bpftrace 和 LLVM 自身存在布局敏感边 | 迁移集合内部会分裂为两套 C++ 运行时 |
| `pcre` | `cert-svc`、`webapi-plugins` 的边含布局敏感类型 | 会保留已证明的跨标准库对象布局边 |
| `taglib` | `capi-media-metadata-editor` 有已确认 C++ ABI 耦合 | 会保留已实测但布局细节尚不能从符号完全展开的 C++ ABI 边 |

完整理由列出了相应 consumer 名称，并区分“已经证明布局敏感”与“已经证明 C++
ABI 耦合、但不能进一步证明布局”两类证据，没有把后一类写成已证明的数据错读。

## 4. 236 个“不需要改”包的分组

| 分组 | 数量 | 可对外说明的共同依据 |
|---|---:|---|
| 不含 C++ 载体 | 181 | 三架构四项候选门禁结果均为否，没有可选择标准库的 C++ 构建或交付边界 |
| C++ 只出现在构建或非运行时载体 | 29 | 有构建动作或少量随 consumer 编译的头文件，但没有本包固定实现的跨包 C++ runtime 边 |
| 独立工具或仅在 Base 拓扑中运行 | 17 | 自身直接链接 libstdc++，但 armv7l 精确图中 Unified runtime 边为 0；Base 内部无 C++ 语义边或仅为 C 接口 |
| 跨包边界只有 C 接口 | 4 | `db4`、`ncurses`、`nghttp2`、`tiff` 的实际符号交集只经过 C 接口 |
| 含 C++ 静态归档但无消费边 | 2 | `golang`、`icecream` 的归档有 C++ 符号，但精确图中迁移侧/Base 内部 runtime consumer 均为 0 |
| 头文件由使用方编译 | 2 | `bison`、`cereal` 的 C++ 载体由使用方按自己的标准库实例化，本包不提供 C++ runtime |
| 已是 libc++ 运行时 | 1 | `libcxx-runtimes` 就是目标 libc++/libc++abi 提供方，不是待切换 consumer |

逐包用途、镜像归属、工具属性和各组内差异见 `NO_CHANGE_GROUPS.md`。特别是 22 个
“直接链接 libstdc++ 但不需要改”的包，没有用“看起来无风险”解释，而是分别引用
完整 runtime 图为 0、Base 内纯 C 边或明确的 C 接口符号交集。

29 个“构建或非运行时载体”中有些包确实进入设备镜像，因此没有一概写成“不进
设备”。理由按每包实际镜像列分别写明；决定性依据是交付物不形成 C++ runtime
边界，而不是安装位置。

## 5. 6 个“当前不能改”包

`gcc`、`gcc-aarch64`、`gcc-armv7hl`、`gcc-armv7l`、`gcc-riscv64`、`glibc`
当前承担 GCC 编译器、目标工具链或 GNU C 运行库构建角色，现有 spec/产品角色要求
使用 GCC。本轮理由明确写成“当前配置和产品职责限制，不是永久技术结论”。

其中只有 `gcc` 的已发布 C++ ELF 直接依赖 libstdc++；另五包的 C++ 仅出现在构建
动作，已发布产物没有直接 C++ runtime 依赖。armv7l 精确图中，这六包通向 Unified
的 C++ runtime 边与 Base 内部 C++ 语义边均为 0。因而覆盖范围内没有已建立的实际
混合标准库对象边；理由同时保留条件性风险：未来若出现同进程 C++ 对象交换，必须
重新评估。

## 6. 2 个“未定”包

- `gmp`：三架构 `libgmpxx.a` 各有 11 个全局 C++ 符号，`libgmpxx` 动态库直接
  依赖 libstdc++；只知道 `eigen`、`python-pycrypto` 有 BuildRequires，缺实际
  link command、link map 和最终 ELF 归档成员来源。
- `tensorflow2`：两组静态归档各有约一万至四万多个 C++ 符号并安装大量 C++
  头文件；只知道三个 Unified consumer 有 BuildRequires，缺实际静态吸收关系和
  最终 ELF 对象来源。

两者仍为“未定”。定案前不直接修改 spec，但按“可能需要改”预留构建和验证资源；
若实际静态链接成立却保持 libstdc++，可能把对象布局、异常或所有权语义复制进
libc++ consumer。闭合步骤详见 `INSUFFICIENT_REASONS.md`。

## 7. 前后对照与校验

- `reason_before_after.tsv` / `.md` 保存 254 条原理由和新理由，便于逐包抽查。
- 自动校验确认除理由外七列逐字段一致，判定一致 254/254。

## 8. 理由仍不充分的包

只有 R100 本来就标为“未定”的 `gmp`、`tensorflow2` 缺少完成最终判断所需证据。
没有发现其余 252 项既有判定缺少原规则所需证据。这里的“充分”受既有覆盖边界
约束，不表示已经补做其他架构的精确符号边或新 revision 验证。

## 9. 自行判断与尚存疑问

### 自行判断

1. 为避免新增未经验证的翻译含义，普通包用途保留仓库英文 `Summary` 原文；少数
   中文概括也同时附原文。
2. 把 29 个构建/非运行时载体按真实镜像归属逐包说明，没有沿用“仅构建期就一定
   不进设备”的错误等同。
3. 对 C++ ABI 耦合但布局未证明的边，只写 ABI 风险，不写成已发生布局错读。
4. `NOT_OBSERVED` 只用于既有覆盖之外的事实；已完成门禁的否定结果写成具体检查
   项为 0/NO，而不是模糊的“没看到”。

### 尚存疑问

1. 总部对外材料是否要求把 254 条仓库英文 Summary 全部人工翻译为中文？本轮保留
   原文以避免引入语义偏差。
2. 精确符号边目前仅有 armv7l；其他架构是否存在额外边为 `NOT_OBSERVED`。
3. 六份标准镜像之外的产品 profile、临时测试 rootfs 和人工安装状态为
   `NOT_OBSERVED`。
4. R100 快照之后的源码 revision 是否改变边界，需要在实际实施 revision 确定后
   重新核对；本任务不据此改变既有判定。
