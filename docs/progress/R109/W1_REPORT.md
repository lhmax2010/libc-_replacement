# W1 闸门事项全面验证

## 结论

`PARTIAL`。当前平台发布仓、R24 迁移重编集合和 R72 源码覆盖范围内的材料已经足以描述行为变化及主要影响；但外部产品/应用组件清单不可得，D03/D04 的内联消费面也不能由 ELF 动态符号清查闭合。因此本报告不把“已覆盖范围内未发现违规调用”扩大为“平台上不存在违规调用”，也不替人工作闸门决定。

## 1. 调用方与锁状态

### 1.1 源码调用

R72 的 371/371 个 source RPM 扫描中，13 个 source RPM（10 个去重包名）出现 `condition_variable`。本轮对这些源码先宽收集 403 条平台等待候选，并用 4 条同方法正向对照校准；再按 `std::condition_variable` 的直接声明和简单别名归因，得到 92 条可直接归因调用，分布于 54 个文件、6 个 source RPM：

| 源码范围 | 最终判断 | 调用处 | 文件 | source RPM |
|---|---|---:|---:|---:|
| 生产代码或会被交付的头文件 | 源码表明持锁 | 8 | 6 | 4 |
| 测试、示例或基准 | 源码表明持锁 | 82 | 47 | 5 |
| 测试、示例或基准 | 示例本身不可按当前标准接口编译 | 2 | 1 | 1 |

自动规则最初标出的 3 条“可能未持锁”均为控制流假阳性：解锁分支在进入等待前已经 `return`，实际等待分支继续持锁。19 条局部窗口无法判断的调用经逐组复核后，除 2 条把 `std::mutex` 直接传给标准接口的旧示例外，均能在外围函数、适配器或调用者看到持锁依据。生产范围的 8 条均未发现未持锁调用。

宽收集表中另有 311 条不能仅凭词法把对象归属于 `std::condition_variable` 的候选。这些行保留为 `UNRESOLVED_CANDIDATE`，不计入 92 条，也不据此推断其锁状态。源码结论是“直接可归因的现有调用未发现违规”，不是语义完备证明。

### 1.2 已发布 ELF 调用

对 R11 的 11,332 个包记录、39,166 个 ELF 逐个解析符号表，解析失败 0；正向对照同时命中 D01/D02 两个预期符号。平台侧得到：

- 612 条未定义符号记录；
- 601 个按“仓库、包、架构、ELF 路径”区分的消费记录；
- 若只按“架构、路径”去重则为 568 个；
- 131 个二进制包，映射到 80 个 source RPM。

601 个消费记录全部映射到 R24 的迁移重编计划，source RPM 下载状态全部为 `PASS`。因此，在当前发布仓清单内，D01/D02 的调用方属于“会随既定迁移重编”的一类。D03/D04 是头文件内联路径，动态符号表不能给出其完整实例化消费面；外部产品/应用组件不在 R11/R24 分母内，数量和重编策略均为 `NOT_AVAILABLE`。

## 2. 两条错误路径何时发生

当前 libc++ 源码在普通等待入口先检查 `unique_lock::owns_lock()`，不持锁时显式生成 `EPERM`；随后若 `pthread_cond_wait` 返回非零，再按该错误码生成 `system_error`。定时等待有同类检查和底层错误处理。

glibc 2.40 源码列出的底层非超时错误包括：递归互斥量不由调用线程持有时的 `EPERM`；健壮互斥量重新获取时的 `EOWNERDEAD`/`ENOTRECOVERABLE`；优先级保护互斥量的优先级变更错误。定时入口还会对非法纳秒值或不支持的 clock id 返回 `EINVAL`。

对标准、未被篡改的 `std::mutex` 与 libc++ 自身生成的定时时间值，本轮没有找到能自然产生这些底层错误的合规路径：标准接口不把 mutex 配置为 robust、recursive 或 priority-protect，libc++ 会规范化时间值并使用受支持时钟。它们仍可能在调用者通过 `native_handle()` 非标准地重建/篡改互斥量、对象损坏或底层故障时出现；当前发布物中是否存在这种行为未能从符号表判断，记 `NOT_OBSERVED`。实验中的 `EINVAL` 是受控故障注入，只证明错误传播形态，不证明平台会自然出现该错误。

线程取消通过 forced unwind 传播，不是 `pthread_cond_wait` 返回一个普通错误码；它与本节两条普通错误路径分开。

## 3. 行为实测

实验没有修改平台源码或四个补丁。移除规格格使用探针目录中的生成覆盖层：从同一份当前 `condition_variable.cpp` 和基线头文件精确移除 6 个头文件、2 个源文件异常规格，生成内容及工具均已做 SHA256 快照。底层错误格用独立动态拦截器令 `pthread_cond_wait` 返回 `EINVAL`；每格 5 次。

| 调用方/实现 | 未持锁 | 底层返回 `EINVAL` |
|---|---|---|
| 保留规格的 libc++ | `TERMINATE` 5/5 | `TERMINATE` 5/5，注入器 5/5 到达 |
| 移除规格后重新编译的 libc++ 调用方 | `system_error` 5/5 | `system_error` 5/5，注入器 5/5 到达 |
| 保留旧头文件编译、加载移除规格实现 | `TERMINATE` 5/5 | `TERMINATE` 5/5 |
| 系统 libstdc++ | 返回 5/5 | 返回 5/5 |

移除规格格的具体异常为：

- 未持锁：code 1、generic category，消息为 `condition_variable::wait: mutex not locked: Operation not permitted`；
- 底层错误：code 22、generic category，消息为 `condition_variable wait failed: Invalid argument`。

保留规格格另以默认终止处理器重复 5 次：两类均 5/5 收到 `SIGABRT`（子进程 return code `-6`）；stderr 分别报告未捕获的 `std::__1::system_error` 和上述具体消息。自定义终止处理器格则 10/10 到达终止处理器并以 86 退出，证明不是仅凭“崩溃/退出码”作判断。

libstdc++ 未持锁格虽然 5/5 正常返回，但返回后 `unique_lock::owns_lock()==false`，而 native mutex 的 `try_lock` 仍报告 busy；这是静默的所有权状态不一致，不能记为“没有问题”。底层注入格 5/5 返回且 `owns_lock()==true`，说明当前实现没有把该返回码转成异常。

旧调用方格说明不重编并不等于自动取得新行为：符号仍能绑定，但旧调用点保留 non-throwing 契约，异常穿越时仍终止。这是当前机器上的实际观察，不是仅由 ABI 名称推断。

## 4. 影响评估

对持锁正确、底层返回成功或正常超时的现有调用，实验没有观察到变化。变化集中在原本会终止的前置条件违反和底层异常错误：

- 重新编译的调用方会收到 `system_error`。若希望恢复或记录后继续，需要在能定义恢复策略的位置增加针对性处理；若异常最终逃出线程入口、析构函数或其他 non-throwing 边界，进程仍可能终止，只是问题现场和清理轨迹改变。
- `catch (...)`、通用任务执行器或未来值封装可能捕获并吞掉异常，使原先在错误现场终止的缺陷延后或被掩盖。这是可能变差的场景。
- 展开期间可运行局部清理、记录上下文、由上层决定重试或降级；对于可恢复的底层故障，这比无条件终止提供更多选择，是可能变好的场景。
- glibc 明确说明某些 priority-protect 错误返回时 mutex 已释放。因此异常处理代码不能笼统假定锁仍由调用方持有。受控 `EINVAL` 格中锁仍显示持有，只代表该注入格。
- 同一进程混用新旧调用点时，同一实现抛出的异常在新调用点可传播、在旧调用点终止，形成可观察的不一致。当前 R24 范围内 601 个发布消费记录都会重编，可消除此集合内的调用点差异；外部和预编译消费方是否存在、是否淘汰为 `NOT_AVAILABLE`。

## 5. 人工裁决所需事实边界

现有证据支持以下有限结论：当前已发布仓的 D01/D02 消费方都在重编计划内；直接可归因源码调用没有发现未持锁的产品路径；变化在故障路径上真实存在，且旧调用方不会自动获得新语义。证据不支持“平台上没有外部旧调用方”或“底层错误永不可能发生”。是否接受这项从现场终止到可传播异常的策略变化，留给人工裁决。
