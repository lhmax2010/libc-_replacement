=== R109 executive ===
# Base 层 libc++ 适配：一页汇总

## 判定结果

本轮对象是 `Tizen-Base-Toolchain` 的 254 个源码包。先用实际 C++ 构建记录、
运行时依赖、符号和头文件载体识别出 73 个 C++ 候选，再以“是否和将迁移的代码
跨边界交换 C++ 语义”为核心逐包核对。最终结果为：需要改 11 个、不需要改
237 个、当前不能改 6 个、未定 0 个。需要改的 11 个是：

`abseil-cpp`、`bcc-tools`、`boost`、`bpftrace`、`icu`、`jsoncpp`、
`libsigc++`、`llvm`、`pcre`、`taglib`、`tensorflow2`。

之所以不是所有 C++ 包都改，是因为共存本身并不构成问题；实际风险来自跨两套
标准库边界传递容器、字符串、智能指针、异常或其他 C++ ABI 语义。只在构建机
运行、对外只暴露 C 接口、只提供由消费方编译的头文件，或经实际链接核查没有
把 C++ 静态成员带入消费方的包，不需要仅因“含 C++”而切换。

## 为什么逐包启用，而不全局注入

逐包方案只触及上述 11 个已证实需要适配的包。全局注入会同时触及 55 个已经
判定不需要改的 C++ 包，并碰到 6 个当前明确走 GCC 路径的包。探针已实测：

- GCC 对 `-stdlib=libc++` 明确报错，不会静默忽略；这 6 个包会直接失败；
- Clang 接受该选项，并实际把标准库选择切到 libc++；因此那 55 个包会在没有
  边界需求的情况下被静默改变，而不是“多带一个无用选项”。

这里的“当前不能改”描述现有工具链配置/产品角色，不是永久技术结论。

## 当前实施进度

| 状态 | 数量 | 包 |
|---|---:|---|
| 已完成并推送 | 8 | `abseil-cpp`、`boost`、`icu`、`jsoncpp`、`libsigc++`、`pcre`、`taglib`、`tensorflow2` |
| 暂停 | 3 | `llvm`、`bcc-tools`、`bpftrace` |

八个已完成包的精确提交 SHA 见 `tables/implementation_status.tsv`。暂停三包必须
协调处理：LLVM 所用 MLGO/XLA 预编译 C++ 对象按 libstdc++ ABI 生成，与 libc++
代码链接时出现 `std::__cxx11` / `std::__1` 符号不匹配；同时
`bcc-tools → llvm` 有 584 个、`bpftrace → llvm` 有 201 个已证明布局敏感的
C++ 符号，不能只切换链条的一端。

## 与总部 step0 的关系

总部的 639/91 是 `Tizen-Base` 的二进制包口径；本轮 254/73/11 是
`Tizen-Base-Toolchain` 的源码包和边界判定口径。固定快照重算只能得到 Base
646/83；另一套 ELF 扫描虽得到 91，但方法不同，不能替代原口径。两仓源码集合
只差 Base 独有 `toybox` 和 Toolchain 独有四包；`toybox` 不含 C++、不依赖
libstdc++，不是漏掉的迁移对象。

## 未覆盖范围

- 判定锚定已归档的固定快照、已取得的构建记录、镜像清单和消费关系；后续新增
  包、revision 漂移或新的动态加载关系需要重新核对。
- 镜像归属只覆盖已有的六份 boot/headed/headless、aarch64/armv7l 精确清单，
  不代表所有产品 profile。
- LLVM/MLGO 资产尚未重建，三包协调验证尚未完成。
- Unified 包侧适配、MLGO AOT 资产生产和运行时专项验证属于其他工作线，不在
  本轮整理范围内。

# 总部 step0 与 Base Toolchain 判定的口径关系

## 1. 两组数字回答的不是同一个问题

总部 step0 统计的是 `Tizen-Base` 仓的**二进制包**：639 个二进制包中，
91 个依赖 `libstdc++`。本项目判定的是 `Tizen-Base-Toolchain` 仓的
**源码包**：254 个源码包中有 73 个 C++ 候选，最终只有 11 个被实证为需要
适配 libc++。两者仓不同，统计单位也不同；一个源码包还可能生成多个二进制
子包，所以 639/91 与 254/73/11 不能直接相除或一一对应。

“含 C++”也不等于“需要改”：只有会与迁移后的代码跨边界交换 C++ 语义的包
才进入 11 包清单。纯 C 接口、仅构建期使用或没有相关运行时边界的 C++ 包，
仍可不改变标准库选择。

## 2. 对 step0 数字的复现边界

R106 使用固定快照
`Tizen-Base/tizen-base_20260827.214809` 的 primary repodata 重算，得到：

- 646 个唯一二进制包名；
- 83 个二进制包在仓库依赖元数据中直接 `Requires` libstdc++。

该结果不能严格复现总部的 639/91。原因是总部数字取自未记录 revision、时间点
和 repodata 校验和的滚动仓，事后无法恢复同一输入。R106 另用 RPM payload 内
ELF 的 `DT_NEEDED` 扫描，在排除 noarch/riscv64 后可以得到 91 个实际依赖包名；
但这是另一套观测对象和算法，不能拿它冒充 step0 原始口径。

## 3. 两仓集合差异

R106 按源码包名对固定快照比较：

| 集合 | 数量 | 包名 |
|---|---:|---|
| 两仓共有 | 250 | 见 R106 完整表 |
| 仅 `Tizen-Base` | 1 | `toybox` |
| 仅 `Tizen-Base-Toolchain` | 4 | `binutils-armv7hl`、`gcc-armv7hl`、`libcxx-runtimes`、`tensorflow2` |

`toybox` 的已发布产物无 C++ runtime ELF，仓库依赖元数据也不要求 libstdc++；
源码包中统计到 236 个 `.c` 文件、常见 C++ 后缀为 0。因此它虽不在本轮 254
包分母中，却不构成 libc++ 迁移对象的遗漏。为什么两个项目的 manifest 对它
取舍不同，现有材料未给出政策说明，记为 `NOT_AVAILABLE`；这不影响其代码/产物
性质判断。

二进制包层面，固定快照共有 638 个包名；仅 Base 有 8 个 `toybox` 子包，仅
Base Toolchain 有 12 个工具链、libc++、TensorFlow 等子包。子包集合差异说明
项目选包和功能配置不同，不能据此把一边的包数量外推到另一边。
