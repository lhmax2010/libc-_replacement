# 拟发总部说明的核对报告

## 1. 总体结论

原稿语气得体，识别子句和传播行为的基本定义正确，八个核心数字的数值都能在
R110 表中找到对应值；但**当前版本不宜直接发送**。存在两项会改变读者理解的
严重失真：

1. 把旧启发式的 50 个“源码 RPM occurrence/token 行”与去重后的 104 个“逻辑
   站点”放入同一张 `Reported / Actual` 表，比较单位不一致；
2. 把只针对原表阳性 11 个源码 RPM 实例所做的严格复核，写成对同一冻结快照
   全部 371 个源码 RPM 的无限制重扫，扩大了 R110 实际覆盖范围。

此外，五步复现说明缺少输入身份、复核子集、排除规则和精确去重键，按原文不能
保证得到 104；现有附件也没有一份恰好 104 行的逻辑站点表。

## 2. 甲：事实准确性

### 2.1 定义

- “识别子句”定义准确：源码可见的 `catch`/`__catch` 捕获
  `abi::__forced_unwind` 或 `__cxxabiv1::__forced_unwind`。R110 的表达式还允许
  `const` 的两种位置以及跨行空白。
- “传播站点”的附加条件准确：handler 内观察到裸 `throw;` 或
  `__throw_exception_again;`。
- “源码 RPM 实例 + 包内路径 + 行号”只准确描述**源码 occurrence**。104 使用的
  逻辑键是“包名 + 规范化包内路径 + 行号 + 精确子句/传播形态”。原稿先把
  `site` 定义为前者、随后却把后者称作同一种 site，需拆成两个术语。

### 2.2 数字逐项核对

| 数字 | R110 核对结果 | 原稿是否可原样保留 |
|---:|---|---|
| 50 | 旧启发式筛出的 50 个 token 行；不是严格站点数 | 需改标签 |
| 4 | 50 行中的 4 个 `key-manager` 日志字符串误计 | 可以 |
| 126 | 宏重抛形式的源码 RPM occurrence 数；去重后为 63 | 必须注明单位 |
| 175 | 受限历史阳性集合中的识别子句 occurrence | 必须注明范围 |
| 172 | 同一集合中的传播子句 occurrence | 必须注明范围 |
| 46 | 裸 `throw;` 的 occurrence；去重后为 41 | 必须注明单位 |
| 104 | 172 行按逻辑键去重后的传播站点 | 可以，但不能与 50 同单位比较 |
| 10 / 8 | 传播集合覆盖 10 个源码 RPM 实例、8 个包名 | 需把 source packages 改成 source RPM instances |

为保持同单位，可同时给出两组对照：

- occurrence 口径：旧启发式 50 行，其中 46 行是真实识别子句；严格复核得到
  172 个传播 occurrence；
- 逻辑站点口径：旧 50 行去重为 45 行，其中真实识别子句为 41；严格复核得到
  104 个传播逻辑站点（41 个裸重抛、63 个宏重抛）。

175 个识别子句比 172 个传播子句多出的 3 个位于 `dali2-csharp-binder`，handler
没有继续传播。因此识别集合覆盖 11 个源码 RPM 实例、9 个包名；10/8 只描述
传播集合。原稿未明说这一差别，容易让读者把 175 也理解为 10/8。

### 2.3 两项缺陷

`key-manager` 的描述属实。四个日志行都位于真实 handler 内，上一行是目标 catch，
下一行是 `throw;`；旧窗口算法没有要求当前 token 行本身就是 catch，因而把 catch
行和日志行分别计数。“sat next to”没有造假，但改为 “inside the real handler,
between the catch clause and the bare throw” 更精确。

宏形式确实解释了新增的 126 个 occurrence。无扩展名头文件也是原输入过滤缺陷，
但它与宏漏项重叠：其中有 32 个源码 RPM occurrence、去重后 16 个逻辑站点，全部
属于宏形式；不能把它理解成“126 之外又漏了一批”。

R110 还登记了潜在盲区：类型别名、多层 token-pasting 宏、项目自定义函数间接
传播、条件编译失活代码、嵌套资产路径计数方式。这些不是已经量化出的额外漏项，
应与已观测的两项缺陷分开表述。

## 3. 乙：复现步骤

### 3.1 明确结论

**按原稿五步不能保证复现 104。**主要问题如下：

1. 没有给出冻结输入清单或哈希，也没写原扫描分母是 371 个成功解包的源码 RPM；
2. 更重要的是，R110 并未用严格规则完整重扫 371 个实例。脚本先从 R32 location
   表选出已有显式目标 catch 命中的 11 个源码 RPM 实例，再对这 11 个的所有文本
   文件严格扫描；
3. 没写文档路径被排除，而测试、示例和构建文件仍计入；
4. 没写条件编译失活分支仍按源码出现次数计入；
5. Step 4 的 “per file+line” 遗漏源码实例/包名，Step 5 的 “collapse those to
   package names” 容易被操作成只剩 8 个包；
6. 没写主源码归档前缀的路径规范化，以及架构化嵌套资产路径仍分别保留；
7. 没给出严格解析条件：允许跨行、定位平衡花括号 handler、分别识别两种传播。

可操作的复现说明必须先明确：此次是在“历史阳性子集”内复核，而不是全语料的
完备再扫描。建议替换全文见 `SUGGESTED_REPLACEMENT.md`。

## 4. 丙：数字差异来源

原稿列出的四项均成立，但不完整：

- 宏形式是否计入：成立；
- 是否扫描无扩展名头文件：成立，但与本次 126 宏 occurrence 有重叠；
- 是否排除字符串和注释：成立；R110 对最终行做了实际源码核对，但严格表达式本身
  不是完整 C++ 词法分析器；
- 是否去重 RPM Release 变体：成立。

还应列出：源码快照和源码包集合、是全量还是历史阳性子集、文档/测试/示例/构建
文件口径、条件编译失活分支、主归档与嵌套资产路径规范化、别名或宏生成的 catch、
项目自定义间接传播。这些因素都可能让对方的 CodeGrok 结果不同。

## 5. 丁：失真、范围与语气

### 5.1 推断写成事实或覆盖扩大

原稿的 “Re-counting the same frozen snapshot without those restrictions” 是主要
范围失真。事实是只对原表已识别出目标 catch 的 11 个历史源码 RPM 实例做了无
扩展名限制复核。尚未证明其余 360 个实例的无扩展名文件中没有目标子句。

原稿的 “Actual 104” 本身数值正确，但与 “Reported 50” 单位不同，缩短表述后反而
掩盖了旧算法既有误计又有漏计的真实结构。

### 5.2 应补充而未补充

应明确写出：

- 104 是历史冻结阳性子集的逻辑站点数；
- 当前全平台源码全集没有用严格方法复扫，为 `NOT_OBSERVED`；
- 当前只复核过历史阳性八包，得到 140，不能称为当前平台总数。为避免混淆历史
  问题回复，140 可以不放正文，但限制必须说明。

### 5.3 语气

开头直接承认原数字不准确、随后给方法和更正，语气合适；没有过度道歉，也没有
淡化问题。需要改的是技术口径，不需要加强道歉措辞。

## 6. 戊：附件

现有材料中：

1. `docs/progress/R110/tables/reported_50_audit.tsv` 最适合证明旧 50 行及 4 个误计；
2. `docs/progress/R110/tables/strict_rethrow_sites_original.tsv` 最适合证明严格复核的
   172 个 occurrence。它含包名、源码实例、包内相对路径、行号、实际代码、子句、
   上下文和传播类型；没有工作区绝对路径或内部任务编号；
3. `docs/progress/R110/STRICT_RETHROW_SITE_LIST.md` 是相同 172 行的可读版，也无内部
   任务编号，但长表更适合 TSV 核对。

R110 **没有直接产出 104 行的去重逻辑站点附件**。若原稿继续说 attached per-site
list 对应 104，附件与正文会不一致。发送前有两种不改变结论的做法：

- 附 172 行表，并明确说明附件是 occurrence 级，按公开的逻辑键去重得到 104；
- 另行从 172 行表导出并复核一份 104 行表，再作为逻辑站点附件。

如导出 104 行版，应保留包名、规范化包内路径、行号、实际代码、子句和传播类型；
源码实例可改为“合并的实例列表”，不能静默删除溯源信息。本任务按纪律未生成或
修改该附件。

## 7. 不一致清单（按严重程度）

### 必须修改

1. `50 → 104` 表混用 occurrence 与逻辑站点单位。
2. “same frozen snapshot without restrictions” 把 11 个阳性实例复核扩大成 371 个
   实例的全量重扫。
3. 五步复现缺少实际输入范围和精确去重键，无法保证得到 104。
4. `site` 单一定义同时承载 occurrence 和 logical site 两种不同对象。

### 应修改

5. 126 和 46 未注明是源码 RPM occurrence；去重后分别为 63 和 41。
6. 扩展名漏项与宏漏项重叠，当前文字可能被读成相加。
7. 10/8 仅属于传播集合；175 个识别子句实际是 11/9。
8. 未声明当前全平台严格复扫为 `NOT_OBSERVED`。
9. 现有附件没有 104 行版；附件名称和正文单位需对齐。

### 可优化

10. 补充快照、文件范围、条件编译、嵌套资产和别名/间接传播等差异来源。
11. 把 `key-manager` 的 “sat next to” 改成 handler 内 catch 与 throw 之间，描述更
    精确。

## 8. 自行判断与尚存疑问

本轮自行判断只有三项：把“能否复现”解释为第三方仅依据回复和附件可重复得到相同
计数；把不同计数单位列为实质问题而非排版问题；把附件行数与正文口径不一致列为
发送前问题。这些判断未改变 R110 的任何数据或结论。

尚存两个需人工确认的问题：

1. 总部当前要核对的是历史阳性子集的更正，还是希望得到完整 371 包/当前平台的
   全量严格计数？后者尚未执行，不能由 R110 的 104 代替。
2. 发件时采用 172 行 occurrence 表并说明去重，还是先另行产出 104 行逻辑站点表？

本轮未修改待审原稿、R110 材料、源码、配置或结论，未推送 Gerrit。
