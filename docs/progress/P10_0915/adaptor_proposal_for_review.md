# 跨标准库 adaptor：证据、部署变体与决策边界

待人工审阅。本文重组既有正式分析与三家评审意见，不新增实验，不批准实施，不排列方案优先级。实测、静态核查和推断分别标明；“未测”不等于失败，“样本通过”不等于普遍兼容。[分析底本](../ADAPTOR_0912/W4/adaptor_analysis_zh.md)

## 一、问题、范围与已经裁决的前提

libstdc++（GNU 的 C++ 标准库）与 libc++（LLVM 的 C++ 标准库）可能用不同内存布局表示字符串等对象。ABI（应用二进制接口）还包括符号、调用约定、异常类型身份和对象生命周期，不能只比较大小。`extern "C"` 统一入口名称，不会把参数里的 `std::string` 转成 C 数据。某些不匹配会在链接时暴露，另一些同名入口能链接成功、随后错读或错误销毁对象。

人工已裁决：`chromium-efl` 整体改用 libc++，不保留 GNU 构建的完整组件。本文的**方案 A 指选择性保留 GNU 组件，因组件方决定而排除**；不是证明它在技术上不成立。少量 GNU 编译的 adaptor 接口层仍允许；**方案 B 指同一 DSO（动态共享库）内的双 ABI 接口层及符号版本路由**，也允许。两家评审中的 A/B 字母含义不同，本文统一按上述含义使用，不按字母机械合并。

“应用零改动”在比较旧 Native C++ 客户端时，指无需改应用源码、重编、重链或调整其启动方式，且保留所需功能。头文件 inline（内联）封送只可能免源码修改，仍须重编。C#/JavaScript 应用若原本只跨 C/托管边界，平台内部共同迁移也可能无需改应用；不能把针对旧 C++ 二进制的比较推广到它们。

范围是已查到的接口和已有产物，不依赖新增 SDK 清单，也不宣称 SDK 全覆盖。此前逐项分析了 Dali/NUI 8 个包族、Web 3 个包族，Native 12 个包族仅快速确认，其余 4 个包族未展开；不是 27 个包族都完成深度分析。[范围原件](../P7_0909/stage2/REPORT.md)

## 二、机制与不能混淆的实现形态

### 2.1 两侧各认自己的对象，中间传数据

GNU 编译单元读取 GNU 对象，libc++ 编译单元构造 libc++ 对象；中间传指针、长度、整数、状态码等简单数据，以下称 POD 数据协议。各侧构造、销毁本侧对象。指针只在同一进程、规定的借用期内有效；它不是进程间协议。状态、异常、引用寿命也属于契约，不能只转换最终字段。

**事实链。**【实测】真实 Boost.Program_options 的两种方向和同侧对照共 4 格，每格 5 次，20 次运行、100 次输入比对；五种输入逐字节正确。两个分别编译的 `.o` 已链接进同一个 `.so`，映射、入口归属和绑定诊断可核。【限定】这个实验验证受控转换机制，不替代 EWK、真实浏览器回调或完整 Dali 对象实测。[机制、构建及原始索引](../API_0911/W2/REPORT.md)

**已排除的解释。**“两个 TU（编译单元）”不代表运行时完全隔离。GNU/C++ 符号命名空间有助区分部分符号，但该实验 shim 的 `__gxx_personality_v0` 实际绑定 LLVM libc++abi；不能说每个 TU 都独享自己的异常运行时。反向目标组件不可得时，换个包装名字也不算反向实测。

**反驳需要什么。**同样真实 provider、运行库、输入及约束下出现字节或销毁差异，即可反驳该样本结论。要升级为旧应用透明部署，还需证明原入口确实被路由、所有状态和生命周期契约被保留，而不仅是另写的测试程序能调用桥接入口。

### 2.2 对原来“不成立的做法”的修正

| 形态 | 事实链、排除边界与可反驳条件 |
| --- | --- |
| 自定义一个“兼容布局类型”替换 `std::string` | 【静态核查】普通类型替换不能让现有头文件里的真实 `std::string` 自动变成自定义类型。排除的是这一普通替换，不是穷尽所有手工 ABI 仿真；特别是 C 名称入口，若另行证明全部调用约定、布局、特殊成员、分配和生命周期兼容，可反驳更强的“不可能”主张。当前没有这种完整证明。 |
| 一个 TU 直接把同一个标准库对象当成两套布局 | 【机制限定】分别使用两套标准头的做法需要分侧编译；单个 TU 仍可通过 C 函数调用另一侧，最终 ELF 也可同时链接两套库。“一个 TU 只能链接一套库”表述不成立。排除的是无转换地解释对象；若存在经验证的转换层，已不是被排除形态。 |
| provider 同时导出两套接口 | 【实测与设计区分】同一 `.so` 容纳两套 `.o` 已做过，不应列为不成立。两个完整 provider 副本与“一个 libc++ 核心、两套薄接口层”不同；后者是允许的方案 B。版本节点只路由，不转换对象。下述三条生产行为契约未闭合，不能据机制样本宣称旧 EWK 入口已透明部署。 |

方案 B 的三条未闭合契约是：（1）同名弱符号、COMDAT（链接器选择同名定义的机制）在实际链接顺序、优化和 LTO 下不会合错；（2）`operator new/delete` 的动态符号抢占符合创建/释放契约；（3）异常运行时共存时，普通异常、取消和清理具有目标语义。第一条已有原型故障，尚未验证的是完整部署保证；后两条不能改写成“已经全部发生故障”。

### 3.2 EWK：三段原型历史与规范矩阵

**事实链。**【静态核查】真实 `ewk_parse_cookie` 接受输入后写 name/value；Domain/Path 只有属性存在才写，缺省保留旧值；拒绝分支在字段写入前返回。接受输入后才计算 expiry。实测沿革必须分开：[原始复用问题](../API_0911/W1_CONT/REPORT.md)、[后续原型记录](../ADAPTOR_0912/W2/REPORT.md)、[真实源码行号](../ADAPTOR_0912/W1/raw/008_targeted.stdout)。

【直接调用实测】在所测 x86_64 配置中，GNU/libc++ 的 string 为 32/24 字节，EWK 输出结构为 136/104 字节。未经转换的 libc++→GNU 调用在 x86_64 原生和 armv7l 物理板各 5/5 观测 SIGSEGV；GNU 同侧各 5/5 字段正确。ARM 探针记录信号后退出 139，不冒充默认 core dump。这些结果不证明反方向也会出现同一故障。[原始直接调用矩阵](../API_0911/W1_CONT/MATRIX.md)

1. 早期仅传输入和最终输出的原型，固定输入通过，复用输出时 5/5 成功返回但应保留的字段改变。这不是“四字段每个都必错”。
2. 后续首次引入状态协议时，两侧都生成 `EWKCookieContents` 临时对象。同名 WEAK HIDDEN 析构被合并，GNU 对象进入错误析构释放；两个 adaptor 模式各 5 次 SIGSEGV。同侧对照通过。此失败不混入后面的规范矩阵。
3. 再修订 front 为独立的四个本侧字符串，避免两侧生成同名包装类析构；得到下表。故意关闭旧状态复制的负向模式仍调用真实 provider，不是模拟件。[符号证据](../ADAPTOR_0912/W2/raw/007_object_symbols.stdout)、[故障回溯](../ADAPTOR_0912/W2/raw/006_debug_state.stdout)

| 环境 | GNU 同侧对照 | 修订 adaptor：libc++→GNU | 故意丢旧状态 |
| --- | --- | --- | --- |
| x86_64 原生 | 60/60 场景正确 | 60/60 正确 | 20/60 正确，40/60 错值 |
| armv7l 物理板 | 60/60 场景正确 | 60/60 正确 | 20/60 正确，40/60 错值 |

每格 5 个进程，每进程 12 场景；合计 6 格、30 次运行、360 次场景观察，其中修订 adaptor 120、同侧 120、负向 120。**不是 360 次 adaptor 成功，也不是 360 个独立进程。**每架构每路径的 60 次场景均完成消费侧作用域销毁，负向模式仍错值。规范运行均保存 `/proc/self/maps`，四字符串以长度和十六进制字节核对；时间值按同次调用时钟区间断言。[矩阵](../ADAPTOR_0912/W2/MATRIX.md)、[原生索引](../ADAPTOR_0912/W2/v2native_matrix.json)、[物理板索引](../ADAPTOR_0912/W2/board_matrix.json)

这 12 场景覆盖完整输入、缺省/单个属性、空 Domain、三种拒绝、长字符串、固定 Expires、Max-Age=60 和连续成功复用。修订原型仍未覆盖两项关键可观察行为：

- 【静态核查】公开结构中的 `expiry_date_utc` 无默认成员初始化。调用方写 `EWKCookieContents c;` 时，原函数可在成功路径只写它；原型却在调用前无条件读取旧 expiry。既有探针初始化了旧对象，未覆盖这种不确定值读取；不能把其潜在未定义行为说成实测崩溃。[公开结构](../P7_0909/stage2/snapshots/evidence/chromium-efl/55f75e1f273b_ewk_cookie_parser.h)、[front 第 10–11 行](../ADAPTOR_0912/W2/frontend.cpp)
- 【静态核查＋推断】原函数在缺 Domain 时不修改该字符串；原型成功后无条件 swap 四字段。此前借出的长字符串 `c_str()` 指针可能在临时对象销毁后失效，即使字段字节相同。地址/引用有效期没有运行验证，不能以值相等证明未修改字段行为相同。[front 第 20 行](../ADAPTOR_0912/W2/frontend.cpp)

其他待测分支包括：Max-Age=0（该源码取当前时间，不是 session 0）；Max-Age 与 Expires 同时出现时的优先关系；非法、空、负数、尾随非数字 Max-Age 不回退 Expires；空 Path；重复属性选择；非 UTF-8、嵌入 NUL 与长度边界；成功后接拒绝的同一对象序列。这里区分解析源码规则与运行结果，不能用 Boost 的 NUL 样本代替 EWK 实测。

**已排除的方案。**不传旧状态、只加 hidden、把两个同名包装对象分别放进两个 TU，都不能满足上述已测情形。实验 catch-all 转状态再抛本地 `runtime_error` 也不保持原异常类型、部分写入或取消契约。不能原样作为生产错误处理。

**反驳需要什么。**同身份、同输入及旧状态下出现字段差异，即反驳限定的字段修复结论。要反驳“尚未证明透明部署”，需补齐上述状态、引用、错误和旧入口路由，以及真实 **GNU 消费方→libc++ EWK provider** 的矩阵；该实际迁移方向仍为 `NOT_OBSERVED`，已有尝试未获得真实 libc++ EWK 产物。[构建缺口](../ADAPTOR_0912/W1/REPORT.md)

## 四、实现规模、维护和自动生成

既有 EWK 转换代码 56 行（协议头 8、backend 26、front 22，含空行注释），探针另 49 行；不是生产报价。两份 Dali wrapper 文件的 61、38 个导出起始行也不是待转换边数。完整人时 `NOT_AVAILABLE`：尚无完整接口契约、目标反向产物和生产集成设计。[计数依据](../ADAPTOR_0912/W3/raw/002_workload.stdout)

| 范围 | 谁要做什么；规模边界 |
| --- | --- |
| EWK | 接口维护者定义字段更新/错误契约；adaptor 维护者写两侧转换和定位入口；构建方维护 ABI flavor、导出与版本；测试方保留双向差分与复用矩阵。不是只维护四字段的四个赋值。 |
| 二进制回复 | 一对字节转换之外，引擎/插件方处理接口表版本、instance 生命周期及回复时序；借用数据若需跨回调留存，应按协议复制，不能保存悬空指针。 |
| Dali | 标量需要成功标记及保持旧值；字符串需要编码/长度；Array/Map 需要递归协议；整对象另有代理、虚调用、所有权、线程和回调，不能报“每接口几十行”覆盖全部。 |
| Native 所选 C 边 | 不需重复新增标准库转换；原句柄、回调和异常约束仍存在。 |

【静态】当前 EWK 不止一次复制：输入及旧字段入 provider，本侧结果再回传构造，最后 swap；存在临时分配。生产延迟、峰值内存、完整分配次数 `NOT_OBSERVED`。这是“尚未测”，不是“不可测”；可按既有交替顺序/重复计时经验设计专项基准，但既有锁微基准数值不能当 adaptor 开销。

【设计，未实现】生成器可分三层：从两套真实编译配置的 AST/DWARF 等信息生成签名/转换骨架；生成 sizeof/offsetof/导出版本漂移检查；生成真实 provider 差分和复用测试。布局哨兵不是兼容性证明。更新/失败/引用/所有权语义需人工维护的规则，不能仅从头文件自动推出。版本节点减少寻址歧义，不免除上游语义变更、编译器/优化/LTO 和 ABI flavor 变化后的复核。

【待验证设计】EWK 可共享解析核心，让它报告哪些字段实际写入（update mask），只提交这些字段；Domain/Path 的存在性应来自真实解析结果，不能按空值或新旧相等猜测。这可能避免读取旧 expiry 和无条件改写保留字段；仍需证明部分写入、分配失败、异常和取消等行为。本文不修改原型，也不把设计写成已修复。

## 五、一般判据与部署契约

**事实链。**纯数据若可完整编码、各侧负责生命周期，已有样本证明可以转换；含状态的接口还需编码未写入/失败/部分更新。所有权、内部引用、虚调用及异常并不是“指针长度”自动解决的，但也不能一律宣称任何代理都不可能。

| 类型 | 可讨论的设计，不是已实现支持 | 尚缺的透明性证明 |
| --- | --- | --- |
| 已知异常 | 本侧捕获，传类型标记与数据，在另一侧本地重抛 | 任意用户类型身份、原 catch 行为、部分状态和取消；catch-all 不能吞强制展开。 |
| 智能指针/所有权 | 对象留原侧，本侧代理控制块经回调释放 | use_count、weak_ptr、别名所有权、异常安全、线程与释放时机。 |
| 多态对象 | 旧 ABI 门面/代理逐方法转成句柄操作 | 直接字段访问、已内联代码、任意派生类、RTTI、身份及回调语义。 |
| future/promise | 本侧对象配远端结果/错误协议 | deferred、线程退出通知、broken_promise、等待与析构语义。 |
| 迭代器/内部引用 | 远端操作代理，或约定只读快照 | 旧内联解引用、实时别名、失效规则；快照不等于原引用。 |

**已排除的概括。**两库共存不等于“两套独立堆”，也不能据此断言必然堆损坏。既有特定 new/delete 绑定诊断不能外推任意第三方库/内存调试器组合。相反，普通异常确有反例：真实 GNU 插件抛共享 `BoundaryError`，libc++ 主程序在 x86_64 原生和 armv7l 物理板均只进入 catch-all、退出 12；同轮受控 POSIX 取消链却能跨两侧，守卫各执行一次、join 得到取消值。普通异常与强制展开必须分开。[异常与取消原始记录](../R78/REPORT.md)

typeinfo（运行时类型信息）的未合一，与不该合并的同名实现被合并，是不同机制。另一次强制展开对照显示，类型信息是否导出到 `.dynsym` 会改变 handler 命中；仅加 `--export-dynamic` 并未使最终重抛正常，仍退出 134。它不是上述 `BoundaryError` 失败成因的直接实验。不能将“静态归档再隐藏符号”当成无条件安全修复。[类型信息对照](../R39/R39_report.md)

既有源码核对另指出，相关 libc++abi personality 的普通 typed catch 对 foreign（非本运行时）异常不进入该类型匹配路径。因此名字深比较建议仍是待验证假设，不能仅因两侧类型名相同就承诺宏开关能修复。特定绑定轨迹中 new/delete 的 GNU 与 LLVM 版本分别绑定到本侧；这不证明全部加载组合安全，也没有证明 `<stdexcept>` 所有九个类都已发生错误。[异常与分配核对](../P4_0909/FINDINGS.md)、[实际绑定轨迹](../API_0911/W2/raw/008_binding_trace.stderr)

**反驳需要什么。**针对确定的接口协议证明完整代理语义，便可反驳“简单字节桥不能覆盖该契约”的更强解释；但某个代理样本不能证明任意对象可透明跨库。需要逐项核对：

- 旧 ELF 最终解析哪个入口，版本/SONAME/插件发现是否一致；新旧入口是否误绑定、递归或旁路 adaptor。同名 C 入口无法凭参数自动判断 ABI，实验专用 configure 调用不能冒充旧应用已有的路由。
- 同名隐式成员、弱符号和 inline/template 的处理。既有 30 次 COMDAT 对照在指定 GNU/ELF/lld 环境显示先出现定义胜出，不是通用链接器保证。`_LIBCPP_HIDE_FROM_ABI` 的标记受 hardening、断言、异常开关及版本共同影响。[链接对照](../R112/REPORT.md)
- 符号版本保护的是最终 ELF 的版本需求，不是所有旧 `.o/.a`。四种绑定情形已有每格 5 次对照；旧对象重链可选新默认节点，新头编译但链接旧库仍可记录旧节点。后来已实施的兼容包装与早期机制探索要分时点，不能引用历史报告断言“现在没有 wrapper”。[绑定对照](../R113/REPORT.md)
- 并行产物不能仅换文件目录。已适配的 aarch64 Boost 候选产物上，30 条旧边全部仍至少有一个同修饰名符号交集，15 条全部旧符号保留；这是符号核查，不是 30 条运行失败。必须明确匹配规则，不能假设旧客户端自动拒绝新库。[交集原件](../R111/ITEM2_BOOST_TRANSITION_REPORT.md)
- inline 静态变量、模板静态状态等可能产生分裂身份；这是待核查风险，不是已发现某个产品故障。动态导出边图也看不到全部内联、模板和运行时弱绑定。
- 目标 libc++ 的 ABI flavor 必须按真实产物核对：上游 Chromium 的私有 `__Cr`/ABI version 2 与 Tizen 已查 GNU 构建不是同一配置。旧快照中 42 个被查 ELF 使用 GNU，不能据上游配置推断迁移后第三套 flavor 已存在；未来产物未观测。[上游配置](../R116/REPORT_ZH.md)、[Tizen 配置入口](../ADAPTOR_0912/W1/REPORT.md)、[42 个 ELF 的身份与范围](../R19b/R19b_report.md)

## 六、方案对比：保留全部选项，不把条件变化写成技术不可能

### 6.1 恢复既有五方案

下表保留既有背景材料的全部五种机制及成本；历史表讨论 Boost 边界，不把其边数当成本轮 EWK 的接口数。[五方案原表](../R110/DECISION_BACKGROUND.md)

| 原有方案 | 避免什么；保留什么成本 | 本次前提下的适用性 |
| --- | --- | --- |
| provider 与所有 C++ 消费方共同重编为同一运行库 | 消除所覆盖边的跨库布局/销毁问题；组件方要闭合依赖、构建/部署顺序、插件及外部旧对象覆盖。 | 平台内部共同迁移仍可讨论；C#/JS 外层应用可能不改。旧 Native C++ 客户端若也必须重编，不属旧二进制零改动。 |
| provider 保留 libstdc++，边界改 C ABI/不透明句柄并同侧创建销毁 | 对象不跨 ABI 解释/释放；平台定义数据、错误及生命周期，调用方接入新约定，验证成本仍有。 | 保留完整 GNU Chromium 部分被组件方决定排除；C 数据/句柄这一机制仍可用于新的 libc++ 核心，不能把整行技术上删除。 |
| 为两套 ABI 提供隔离的并行产物 | 调用方匹配本侧 provider，保留较多原 C++ API；发布方承担符号/SONAME/插件发现隔离及双发布、更新矩阵。 | 完整 GNU Chromium 副本被当前决定排除；不是声称并行机制不成立。两个薄接口层不是两份完整组件，见方案 B。 |
| 使用进程边界隔离并经 IPC 序列化 | 标准库对象、异常、分配器留本进程；协议、复制、恢复、部署、延迟改变由两端维护者承担。 | 需重设调用路径；保留 GNU 完整组件的变体不符当前决定。旧 ABI 前端加 IPC 可讨论，但仍需兼容门面，不是旧对象天然可跨进程。 |
| 接受现有混合边界 | 无需改接口；不消除既有错值、终止、销毁故障及未测风险。 | 不等于支持声明或恢复功能。若改为限制支持组合，应明确撤去哪些混合调用承诺，由业务裁决。 |

### 6.2 追加部署变体与改约方式

| 方案 | 机制和应用影响 | 当前状态及承担者 |
| --- | --- | --- |
| 方案 A：选择性不迁移 | 把相关完整组件及 C++ 依赖继续放在 GNU 一侧，原 GNU 客户端不跨库；隔离仍需核查。 | **因组件方决定而排除**。既有 GNU 构建证明历史构建形态存在，不证明任意未来版本都能维持。条件改变可重审机制。 |
| 分离 DSO 的 adaptor | 两套薄接口层经 POD 转换，可能保留旧 Native 二进制入口。 | 机制有样本；旧入口部署、反方向和契约未闭合。平台承担两个构建侧与路由维护。 |
| 方案 B：同 DSO 双版本＋符号版本路由 | 同一 libc++ 核心外放 GNU/LLVM 两套接口层，选择明确入口后转换；不是新机制，是 adaptor 部署变体。 | 允许，但不等于已实现目标双版本。三条未测生产契约见 2.2；旧无版本 ELF、旧对象重链、导出策略还需目标实测。 |
| 改 C 数据接口 | 新接口显式传字节/长度/句柄；直接改用它的应用要改源码。 | 已有具体设计见 6.3，尚未实施。平台与应用共同定义错误、缓冲和并存契约。 |
| 头文件 inline 封送 | 保留源码层调用形态，在应用本侧编译转换包装，调用新 C 入口。 | 改 C 接口的变体，应用源码可不改、**必须重编/重链**；不保护已发布旧 ELF，需验证旧调用语义。 |
| 应用及依赖迁移 libc++ | 双方同库且依赖配套时移除混用前提。 | 需源码、构建和依赖迁移条件；外部应用是否具备条件不可得，不能承诺全体可做。 |
| 接受限制并声明 | 只支持经确认的运行库/版本/接口组合。 | 平台说明边界，业务/应用接受限制；不是技术上修复原混合接口。 |
| 预加载拦截入口 | 另一个装载路由变体，不替代转换或状态契约。 | 若需修改应用启动环境，不符合本文严格零改动定义；解析顺序、句柄范围和生产装载未验证，不作为已通过部署法。 |

在方案 A 因组件方决定排除后，adaptor 是剩余方案中唯一应用零改动的——**这句话仅限本表内“保留原功能、原入口的旧 Native C++ 二进制”目标，并把方案 B 和旧 ABI 兼容门面计入 adaptor 家族**；不是所有未来机制的唯一性定理，也不是部署成功保证。平台内部统一迁移、外层 C#/JS 应用无需变化，是另一种不应删去的情形。

## 七、未覆盖范围与评审建议，待后续评估

### 7.1 不能遗漏的范围限制

真实 libc++ EWK 反向、真实 browser receiver、完整 Dali 对象/虚调用、生产旧 ELF 装载、异常/取消与部分写入、并发重入、内部引用寿命、完整分配和性能、LTO/其他工具链仍未验证。aarch64 **adaptor** 无实测，不能拿 aarch64 的其他 Boost 对照填补。SDK 资格、外部应用分母和全部跨库接口不可得；没有把它们写成“不存在”。

静态盘点中还有 bundle 的 `GetString/GetKeys`、Web 引擎 `EvaluateJavaScript` 的 string/function、图表标签 vector、cion 的 vector/shared_ptr、组件工厂 map/unique_ptr/虚调用等候选。它们提示待查面，不是已证明对 SDK 开放或已测失败。[候选接口原件](../P7_0909/stage2/REPORT.md)。动态符号图的盲区包括内联、模板、重复静态状态和运行时绑定；本文不声称“四处就是平台全部问题”。

## 八、供评审与业务裁决的问题

1. 双 TU 机制的有限样本结论是否恰当？从它升级到生产契约还缺哪些可反驳的验证？
2. EWK 已有 12 场景之外，未初始化字段、未写字段引用寿命和错误分支是否还有遗漏？
3. 自定义布局、单 TU 和同 DSO 双版本的适用边界是否表述准确，是否混淆编译与运行时绑定？
4. **在方案 A 排除后，adaptor 与方案 B 之间如何选？**这里是分离 DSO 部署与同 DSO 部署的选择，不是两种互不相关的转换机制。
5. 生成器能减少哪些重复劳动，哪些语义仍需接口维护者负责？是否需要共享核心和字段更新标记？
6. 复杂对象的句柄/代理需要保持哪些具体契约；哪些旧内联调用无法由新增门面拦截？
7. 哪些目标 flavor、依赖和 SDK/应用范围需要业务确认，哪些已有证据尚未纳入？
8. 哪些措辞仍可能把静态规则写成实测、把有限通过写成普遍兼容？
9. 如何验收旧 ELF 路由、弱符号、分配释放、异常/取消、真实回调和部署更新，避免“能加载”替代“正确”？
10. **adaptor 的 libstdc++ 接口层如何跟随 libstdc++ 的 ABI 变化？**谁维护 `_GLIBCXX_USE_CXX11_ABI`、导出版本、工具链、旧二进制组合及再验证记录；哪些变化需要新增门面而不能替换旧入口？

本稿只提出事实、边界和可检验的选项；不以“机制可行”替代业务决定，也不把“尚未验证”判成“永远不可行”。
