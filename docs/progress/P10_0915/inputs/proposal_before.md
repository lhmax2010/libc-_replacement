# 第三方应用零改动的跨标准库兼容方案：adaptor 层

- 日期：2026-09-15
- 状态：**方案草案，待评审**
- 工作线：运行时验证（`codex/runtime-validation`）
- 本文用途：供多方评审判断方案可行性，以及是否存在更优方案

---

## 一、要解决的问题

平台正在把 C++ 标准库从 libstdc++ 迁到 libc++。**第三方应用不会跟着迁** ——
它们继续用 libstdc++ 编译，继续调用平台的接口。

**已实测确认**：当接口跨越两套标准库的边界传递 C++ 对象时，会静默出错。

```cpp
// 提供方（libstdc++ 构建）
std::deque<int>* make_payload() {
    return new std::deque<int>{11, 22, 33, 44};   // 报告长度 4
}

// 消费方（libc++ 构建）
auto* p = make_payload();
p->size();                                       // 读到 106884723786536
```

**链接成功、加载成功、进程正常退出，但数据是错的。**
原因：同一类型在两套库中布局不同（`deque` 一侧 80 字节、另一侧 48 字节），
而符号名不携带足够信息让链接器发现这一点。
证据：`docs/progress/R80/`。

**平台上有哪些接口会这样传？** 我们盘点了 960 个头文件提供方、
深入了 27 个包族，找到四处：

| 接口 | 形态 | 应用是否直接接触 |
|---|---|---|
| `ewk_parse_cookie` | `extern "C"` 内传 `std::string`，输出结构含四个 `std::string` | 是 |
| `SetSyncBinaryReply` | 引擎与插件间传 `std::vector<uint8_t>` | 否（内部边界） |
| `dali2-csharp-binder` ↔ Dali | binder 导出 C 名称，内部依赖 Dali C++ ABI | 否（C# 应用经 C 边界） |
| Native 四族的内联包装 | 后经核查**不传标准库对象**，无需处理 | — |

证据：`docs/progress/P7_0909/`、`docs/progress/API_0911/`。

**本文讨论的方案，是让这些接口在应用不改代码的前提下继续工作。**

## 二、方案：在平台侧加 adaptor 层

### 2.1 机制

```
应用                  平台侧
(libstdc++)          ┌─────────────────────────────────────────┐
                     │  接口层 (libstdc++ 编译单元)             │
  调用接口  ───────► │    接收 libstdc++ 的 std::string        │
  接口签名不变        │    取出 (const char*, size_t)            │
                     │         │                                │
                     │         ▼  纯 C 边界，只传指针与长度      │
                     │  实现层 (libc++ 编译单元)                │
                     │    用指针与长度构造 libc++ 的 std::string │
                     │    调用真正的实现                         │
                     │    结果同样以指针与长度传回               │
                     └─────────────────────────────────────────┘
```

**核心原则**：
- 两个编译单元各链自己的标准库；
- **标准库对象不穿过中间边界**，只传 POD（指针、长度、整数）；
- 每一侧自己构造、自己销毁自己的对象；
- 应用看到的接口签名与现在完全一致。

### 2.2 为什么下列更简单的做法不成立

评审时请勿重复提出这些 —— 我们已论证过：

| 做法 | 为什么不成立 |
|---|---|
| 自定义一个兼容布局的 `string` 类型 | 接口签名里写的是 `std::string`，编译器用的是当前编译单元里真正的那个；自定义类型签名对不上 |
| 单一编译单元的 shim | 该编译单元只能链一套标准库，问题只是从一条边移到另一条边 |
| provider 同时导出两套版本（仿 libstdc++ 的 `_GLIBCXX_USE_CXX11_ABI`） | 那是 libstdc++ 自己两套实现的机制；我们的两套分属不同项目，同时编进去会冲突。**此项未做穷尽证明，评审可挑战** |

证据：`docs/progress/ADAPTOR_0912/W3/REPORT.md`。

## 三、已验证的内容

### 3.1 机制可行 —— 真实 Boost 组件

用真实的平台 `libboost_program_options`（libstdc++ 构建）作 provider：

| 方向 | 路径 | 结果 |
|---|---|---|
| libstdc++ 消费方 → libc++ provider | 双编译单元 adaptor | **5/5** |
| libc++ 消费方 → libstdc++ provider | 双编译单元 adaptor | **5/5** |
| 同侧对照（两组） | 直接调用 | 5/5 |

五种输入：空串、ASCII、中文含补充平面字符、**内嵌 NUL**、257 字符长串。
**逐字节比对**，每次用 `/proc/self/maps` 确认两套库与 provider 同时加载。

证据：`docs/progress/API_0911/W2/`。

### 3.2 真实接口可行 —— `ewk_parse_cookie`

**第一版 adaptor 失败了**：固定样本通过，但复用输出结构时 5/5 字段静默改变。

**原因从源码里找到了**（`ewk_cookie_parser.cc:32-49`）：

```cpp
cookie.name = new_cookie.Name();
cookie.value = new_cookie.Value();
auto domain = new_cookie.Domain();
if (domain.has_value()) {          // 只在 cookie 带 Domain 时才覆盖
    ...                            // 否则保留输出结构里的旧值
```

**这是一条从头文件看不出来的隐含约定。** 第一版 adaptor 没复刻它。

**第二版复刻了这条约定**，设计 12 个场景覆盖全部语义：

| 场景 | 覆盖 |
|---|---|
| 0 | 空输出，完整 Domain/Path |
| 1 | 复用输出，缺 Domain/Path —— **保留旧值** |
| 2、3 | 只给 Domain 或只给 Path —— 只覆盖所给字段 |
| 4 | 显式空 Domain —— 清空而非保留 |
| 5–7 | 空输入、HttpOnly、Secure —— 返回 false，五字段不变 |
| 8 | 160/161/1024 字节长值 —— 逐字节且销毁完成 |
| 9、10 | Expires 固定日期、Max-Age 区间 |
| 11 | 同一输出连续两次写 |

**结果**：x86_64 原生与 armv7l 物理板，每场景 5/5，共 360 次场景观察。

**负向对照**：不复刻语义的版本只有 4/12 场景正确 —— 证明"复刻语义"是必要的。

证据：`docs/progress/ADAPTOR_0912/W2/REPORT.md`。

### 3.3 逐接口判定

| 接口 | 判定 | 依据 |
|---|---|---|
| `ewk_parse_cookie` 字段协议 | **可行**，限已测方向与场景 | 3.2 |
| `ewk_parse_cookie` 完整透明部署 | 需进一步验证 | 反方向、异常、并发未测 |
| `SetSyncBinaryReply` | 数据转换可表达；**真实回调路径未跑** | 缺浏览器实例 |
| Dali `Property::Value` 的 POD 重载 | 条件性可表达 | 属性子集双向通过 |
| Dali `Property::Value` 的 String/Array/Map 重载 | 需进一步验证 | — |
| **Dali 完整对象、Control、虚调用** | **不适用** | 那不是数据，是行为；不能把对象内存当字节复制 |
| Native 四族 | **无需 adaptor** | 所选边不传标准库对象 |

证据：`docs/progress/ADAPTOR_0912/W3/REPORT.md`。

## 四、方案的代价

| 项 | 内容 |
|---|---|
| **一次性** | 每个接口一对转换函数；**必须读实现，把隐含约定复刻进去** |
| **每次调用** | 一次数据复制 |
| **跟进上游时** | 多检查一处：实现逻辑变了，adaptor 要同步。（这不是额外负担 —— 我们本来就打包这些组件，上游改了本来就要跟进） |
| **验证** | **不能只测"不崩"** —— 出错表现是静默错值。每个接口要专门设计覆盖语义的场景（EWK 用了 12 个） |

**最大的实际成本是最后一条。**

---

## 五、adaptor 不能覆盖的

| 类别 | 原因 |
|---|---|
| 异常穿越边界 | 异常在飞的时候没有转换时机；两套 RTTI 独立 |
| 迭代器 | 指向容器内部结构，转过去是野指针 |
| 所有权转移（智能指针） | 谁释放要显式定义，adaptor 不能替代 |
| 多态对象与虚调用 | 那是行为不是数据 |
| 有状态对象（`future`/`promise`） | 不能复制内存，要转接"提交/等待/取消"协议 |

这些不是 adaptor 的缺陷，是任何"格式转换"方案的边界。
**对这些接口只能改设计。**

---

## 六、与其他方案的对比

| 方案 | 应用是否改代码 | 平台侧代价 | 覆盖范围 |
|---|---|---|---|
| **adaptor 层** | **否** | 每接口一对转换 + 语义复刻 + 验证 | 数据类接口 |
| 改成 C 接口 | **是** | 改接口 + 保留旧接口一段时间 | 全部 |
| 应用改用 libc++ | **是**（重编） | 无 | 全部，但要应用有源码 |
| 接受限制并声明 | 否 | 无 | 声明哪些接口不支持跨库 |

**adaptor 是唯一"应用零改动"且"平台侧可实施"的方案。**
但它不覆盖第五节那些类别。

## 七、本文未覆盖的

- 真实浏览器/插件实例的运行路径（`SetSyncBinaryReply` 的回调）；
- 反方向的 EWK 实测（libstdc++ 应用 → libc++ 平台，这是迁移后的实际方向）；
- Dali 完整初始化下的行为；
- 正式 SDK 暴露清单（devel 头文件可见不等于 SDK 承诺）；
- aarch64 的运行时验证（无物理板）；
- 性能数据（复制开销只有结构分析，无实测耗时）。
