# 跨标准库 adaptor：已验证范围与实施条件

待人工审阅。本材料不选择方案、不排列优先级，不构成未测接口的兼容性承诺。

本次已证明：**把调用前状态也纳入转换，能够修复 EWK cookie 解析 adaptor 在复用输出时丢字段的问题**。证明范围是 libc++ 调用方→真实 GNU provider 的正常返回字段语义，覆盖 x86_64 原生与 armv7l 物理板。**迁移后的实际反方向——旧 GNU 调用方→libc++ EWK——仍未实测**；完整透明部署不能据此批准。[运行矩阵](../W2/MATRIX.md)、[原型与限定](../W2/REPORT.md)

## 机制：两侧各认自己的对象，中间传可解释的数据

两套 C++ 标准库可能用不同方式存储同一个“字符串”。编译链接通过，只能说明找到了入口，不能保证入口把对象内存解释正确。`extern "C"` 可以统一导出名称，但不会把参数里的 C++ 字符串变成 C 字节数组。

adaptor 在调用方一侧读取本侧字符串，在 provider 一侧重新构造其标准库的字符串。两个编译单元分别按不同标准库编译，中间只传指针、字节长度、整数、状态码等简单数据（POD）。返回时反向复制；每侧只销毁本侧构造的对象。这里的指针只在**同一进程、约定借用期限内**有效，不是跨进程序列化协议。

这套机制已有真实 Boost.Program_options 固定样本的双向验证：4 格、每格 5 次，共 20 次；不替代 EWK、浏览器回调或 Dali 的目标实测。[机制实验记录](../../API_0911/W2/REPORT.md)

两个编译单元只是起点，还要确保入口找对、输出旧状态不丢、所有权不串、同名辅助函数不被链接器合并。本次同时发现并修复了最后一种问题。

## EWK cookie：字段协议已验证，完整部署仍有限定

**事实链。**【静态核查】真实 `ewk_parse_cookie` 在接受输入后覆盖 name/value；Domain/Path 属性存在才写对应字段，不存在则保留输出对象的旧字段；空输入、HttpOnly、Secure 的拒绝分支位于字段写入之前。【实测】原先不传旧状态的协议在复用输出时丢字段。修订协议把原有四字段和 expiry 先送到 GNU 侧，再让真实函数处理；两架构的同侧对照和修订 adaptor 均在每场景 5 次中得到正确字段及完成销毁。[带行号实际源码](../W1/raw/008_targeted.stdout)、[逐场景记录](../W2/REPORT.md)

规范实验包括 12 个场景：完整输入、字段缺省、仅一个属性、显式空属性、拒绝输入、长字符串、固定 Expires、基于本次时钟范围的 Max-Age，以及同一输出连续复用。每次记录 maps，确认两个运行库、入口和真实 provider；四字符串记录长度与十六进制字节。Max-Age 不要求不同进程生成相同绝对时间。

| 环境 | GNU 同侧对照 | 修订 adaptor：libc++→GNU | 故意丢旧状态的负向模式 |
| --- | --- | --- | --- |
| x86_64 原生 | 5 次，60/60 场景正确 | 5 次，60/60 正确 | 5 次，20/60 正确、40/60 错值 |
| armv7l 物理板 | 5 次，60/60 场景正确 | 5 次，60/60 正确 | 5 次，20/60 正确、40/60 错值 |

每行每路径是 5 个进程，每进程 12 个场景；合计 6 格、30 次运行、360 次场景观察，不是 360 次独立运行。三种路径每侧都完成 60/60 场景的消费侧作用域销毁，**负向模式照样产生错值**。销毁完成不代表状态正确。[原生原始索引](../W2/v2native_matrix.json)、[物理板原始索引](../W2/board_matrix.json)

**已排除的方案。**只搬输入和最终输出、不带旧状态的方案被上述负向样本排除；仅把 `EWKCookieContents` 临时对象放在两个 TU 的做法也实际失败：两侧隐式析构的修饰名相同，WEAK HIDDEN 定义被合并，GNU 对象在错误析构中释放并触发 SIGSEGV。修订 front 使用本地四个字符串，不再在两侧生成这个外部类的析构。隐式成员冲突是“标准库命名空间隔离”之外还需检查的一层。[两个对象文件的符号](../W2/raw/007_object_symbols.stdout)、[故障回溯](../W2/raw/006_debug_state.stdout)

**反驳需要什么。**若相同 provider/运行库身份、输入及旧状态下，正常返回字段仍与同侧控制不同，限定的状态修复结论即不成立。要证明更强的“可部署”，还需真实 libc++ EWK 反向矩阵、旧调用方路由、产品构建/打包、异常与取消、内部引用/地址稳定性等证据。实验 catch-all/本地 runtime_error 策略没有保持原异常类型、部分写入或取消语义，**不能原样作为生产错误契约**。

## 浏览器二进制回复：数据可转换，真实回调尚未验证

**事实链。**【静态核查】插件通过接口表调用 `SetSyncBinaryReply(instance, const std::vector<uint8_t>&)`；方向是插件回调进入引擎。真实引擎先查有效 instance，再把 vector 赋值到内部回复，随后同步返回路径取出该回复。【既有实测】两套 vector 的所选 x86_64 表示样本都是 24 字节、三指针；这只说明那些表示观察一致，未验证真实回调、异常、allocator 或销毁契约。[注册、实例与接收路径](../W1/REPORT.md)、[函数状态清单](../W2/STATE_SCOPE.tsv)

**已排除的方案。**不能用两个 sizeof 相等代替回调实测，也不能把 Node/service 中“不支持”的空操作当正向对照；只在调用前复制 vector 也不能补齐真实接口表/instance 注册。【推断】字节元素可在接收侧按指针与长度重建 vector，因此数据转换本身可表达，但真实宿主是否可部署仍需验证。实际组件编译缺 base 头和生成依赖；尚未启动可用 receiver，不能说“必须整个浏览器”或“无需浏览器已跑通”。

**反驳需要什么。**真实双方组件在有效注册及实例上下文中，两方向反复断言长度/每字节/回复顺序/销毁，并确认实际加载身份，才能把本接口从“需进一步验证”提升为实测可行。若副本不能保持某个既定的引用、异常或所有权契约，简单字节 adaptor 不适用于该契约。

## Dali：属性值不等于完整对象行为

**事实链。**【静态核查】C# 应用经 C 名称导出的绑定入口；但绑定层内部仍调用 Dali C++ API。`Control::New` 返回对象，绑定层再创建 Control 句柄，由配对入口 delete；对象、虚调用和生命周期不等于一串可复制字节。【既有实测】真实属性包装子集双向的精确值/销毁通过；完整 GNU binder 链只替换 libc++ core 时，两架构均缺 GNU vector 修饰名。【本次实测】物理板存在离屏 API；第一次初始化缺 GLES 搜索路径，找到已安装 `/hal/lib/driver` 后，在 30 秒期限内仍未完成 New，修正路径后重复 5 次相同。因此 Control/虚调用仍未测。[依赖和离屏记录](../W1/REPORT.md)、[真实 Control 构造/销毁源码](../W3/raw/002_workload.stdout)

**已排除的方案。**只换 core 不能使既有完整 GNU 依赖链直接加载；不能将属性子集通过当成整个 Dali 通过，也不能把一个带虚表或内部引用的对象的原始内存当成 POD 复制。后一个是对“原样字节复制”的结构性判断，**不排除把对象留在原侧、另做句柄/操作代理**；该代理尚未验证。现有离屏超时不是板子不支持图形的证明。

**反驳需要什么。**完整双方组件在正确初始化后，逐项验证对象身份、具体属性、虚调用、引用计数/销毁、线程与回调契约，才能扩展支持范围；若证明某条实际边仅传稳定标量/借用数据，则不应把它并入整对象障碍。C# 侧没有直接接触 C++ ABI，也不免除平台内 binder→Dali 边界的核查。

## Native 包装与新增的条件输出

**事实链。**【静态核查与编译链接】app_control.hpp 的所选操作、app_common.hpp 的 GetId、service_app.hpp/app.hpp 的所选 Run，在两库下共 8 个 ELF 的平台导入为 C 入口；字符串转换留在应用侧。它们无需重复加标准库 adaptor，但还不是四族全部运行安全证明。【静态核查】另复核 Dali 六个 Get 输出重载：bool、float、int32、Dali::String、Array、Map；类型不匹配时返回 false 而不写输出。[Native 原始范围](../../API_0911/W1/REPORT.md)、[Get 实现行号](../W2/raw/005_get_state.stdout)

**已排除的方案。**不能把本地存在 C++ 符号当作平台边一定传 C++ 对象，也不能把 C 名称当安全充分条件。Get 若用零初始化临时值并在失败时无条件拷回，会改变“失败保持旧值”规则；这是源码推导，不是本轮六个 Get 的运行结果。Array/Map 的嵌套值与所有权不能从外层容器签名单独推出。

**反驳需要什么。**若发现所选 Native 实例化路径还把 C++ 对象/异常穿过平台入口，就需重新归类；对 Get，需以匹配/不匹配类型和非空旧值实际验证状态、类型编码及生命周期。现有 11 定义的定界清单中，有 7 个条件保留输出，另有 2 个回调/缓存序列候选；**不是全平台计数**，清单之外总量不可得。

## 判断一个新接口时，逐项确认什么

不能只看签名是否有 string。逐项确认：数据能否完整编码；调用前状态/失败/部分更新；创建与释放归属；异常和取消契约；内部引用/迭代器的寿命；虚调用/对象身份；回调注册与线程顺序；同名辅助符号；两方向真实组件及旧调用方部署。缺少一项就保留对应限定，而不是用其他项的成功补齐。[逐接口判据与表](../W3/REPORT.md)

## 规模与方案对照

已写 EWK 实验转换部分 **56 行**（协议头 8、backend 26、front 22，包括注释与空行），探针另 49 行；不含构建/证据编排与生产集成。这个实测代码量不是生产报价。另一方向需对应分侧构建及独立验证；异常策略未定，因此完整生产人时不可得。[计数原文](../W3/raw/002_workload.stdout)

| 范围 | 需要谁完成什么 |
| --- | --- |
| EWK | 平台 adaptor 维护者维护两侧转换、初始状态协议、入口寻址和符号隔离；接口方定错误契约；测试方维持两方向与复用矩阵 |
| 二进制回复 | 一对字节转换操作之外，平台引擎/插件维护者还需接口表适配、instance 映射/注销及同步回复序列验证 |
| Dali 标量 Get | 至少三组成功标记操作；对象身份协议可共用。字符串另需编码与长度，Array/Map 另需递归类型协议 |
| Dali 整对象 | API/绑定维护者需对象代理、操作集、所有权/回调/线程契约；总规模不可得。两份被查看的 wrapper 文件有 61、38 个导出起始行，不是需转换的边数 |
| Native 所选 C 边 | 不需新增标准库转换入口；应用与平台仍须验证原句柄、回调及异常约束 |

EWK 每次把输入及旧字段复制到 provider 侧，再把返回字段复制到调用侧；最终提交使用 swap。vector 数据协议至少复制输入字节。生产延迟、峰值内存及完整分配次数未测。上游改变字段、类型、缺省规则、接口表、库版本或编译/LTO 设置，都要求重新核对。头文件可帮助生成签名/复制骨架，不能自动推导保留旧值、生命周期或失败行为。

| 方案 | 能消除什么 / 保留什么成本 | 承担者 |
| --- | --- | --- |
| adaptor | 可能保留调用侧接口形态；增加转换、状态/生命周期、符号及版本维护 | 平台接口、构建、测试维护方 |
| 改 C 数据/句柄接口 | 避开直接跨标准库对象；仍需定义字段、错误、创建释放、旧接口并存 | 平台新增接口；应用开发者接入新协议 |
| 应用及依赖迁移 libc++ | 在双方及依赖配套时移除标准库混用前提；需要源码和迁移条件 | 应用及组件维护者；外部组件是否具备条件未判断 |
| 接受限制并声明 | 不承担未承诺的混用；限制可用标准库/版本/接口与部署组合 | 平台维护支持清单，业务与应用方确认约束可接受性 |

不存在本材料替业务决定的最优方案。
