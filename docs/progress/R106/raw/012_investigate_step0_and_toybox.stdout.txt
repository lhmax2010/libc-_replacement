### 13-3 Environment

Validation runs on an armv7l development board (Tizen 11.0), reachable over SDB. Six writable and executable paths on the board have been confirmed for staging test binaries; test binaries are cross-compiled on the build host, as the board carries no compiler. Coverage for aarch64 and x86_64 uses user-mode emulation on the build host, which is available and in use for the packaging gates.

### 13-4 Sequencing

On-device validation runs alongside the first migration wave, whose board testing uses the same hardware. Board availability is therefore a scheduling constraint on both.

## Appendix B: Analysis Method **[UPDATED]**

The original's method description is accurate for what it covers. Two additions for reproducibility:

**Snapshot pinning**: the original cites rolling reference-repository URLs whose content changes daily, with no snapshot ID or checksum recorded — the figures cannot be re-derived later. Measurements in this revision are pinned: for example, the chromium-efl analysis used Unified repository revision `1785904307`, repomd SHA256 `e425b6a9…`, with each analyzed RPM's SHA256 verified three ways (on-disk recomputation, our own ledger, and the repodata checksum).

**Method limits acknowledged in the original are correct**: name-based heuristics for categorisation, and repodata dependencies for coverage. This revision adds that neither supports migration *ordering*, which requires the ABI coupling graph (§3-3, §9-5).
