实施源码为 `sandbox/lhmax2025/libcxx-noexcept-relief`，提交

但原 FAIL 记录保留。ARM 官方套件沿用此前有效结果，缺 3,554 项；本包补测尚待完成，旧残留已清理并释放板子，

## 本次改动是什么

**允许等待中的取消穿过，并恢复共享锁写者状态。** 取消线程时，底层运行时会沿调用链退回，
执行沿途的资源清理；这称为“强制展开”。`noexcept` 表示函数不允许异常越过的契约，
原先会在目标等待边界触发终止。本次解除普通等待及三种定时等待的相应契约，并给
`shared_mutex` 普通写者和 `shared_timed_mutex` 定时写者增加回滚：等待中途退出时，
清除该写者设置的标记并通知排队者，而不抹掉仍合法持锁的读者状态。
验证依据：[实施差异与构建](../../IMPL_0908/W1/REPORT.md)、[两架构状态和值断言](../../IMPL_0908/W3/REPORT.md)。

**为已链接旧程序保留旧入口。** 同一个库同时保留旧契约和新契约，用“符号版本”区分。
它只为普通等待和 system-clock 定时等待这两个库内函数保留旧 `LLVM_22` 入口，
新链接的默认入口为 `LLVM_22_TIZEN_1`。它不重新编译旧程序，也不修复旧程序内部缺少的清理代码。
验证依据：[双版本设计](../../IMPL_0908/W2/REPORT.md)、[两架构最终版本核验](../../IMPL_0908/W3/raw/035_alias_verification.stdout)、
[定时入口逐轮实测](../../IMPL_0908/W3/timed_versions.tsv)。

**转换缓冲对象析构时不再自动刷新。** `wbuffer_convert` 是把宽字符转换后写入底层缓冲的设施。
本次移除其现代头文件析构中的自动同步调用，保留资源释放，以及显式 `pubsync()` 同步路径。
需要输出完整时，不能再把析构当作最后一次刷新。这里的刷新是把转换缓冲交给下层，不承诺物理介质持久化。
验证依据：[源码调用与资源核查](../../R111/ITEM1_WBUFFER_CLOSE_REPORT.md)、[新旧输出值对照](../../IMPL_0908/W3/REPORT.md)。

**Boost 与消费方使用兼容的 C++ 对象约定。** ABI 是二进制间对函数调用、对象表示和所有权的约定。
既定处理是让相关 Boost 提供方与迁移后的消费方统一到 libc++，避免跨 libstdc++／libc++ 解释同一对象。
既有适配已覆盖 Clang toolchain 条件下的 Boost 提供方；本轮没有重新实施 Boost 迁移，
也没有取得全部 13 个消费方已重建、同批部署的证据。计划范围不等于实际完成。
验证依据：[90 条边、13 个消费方与适配条件核查](../../R111/ITEM2_BOOST_TRANSITION_REPORT.md)。

## 承诺的适用前提

下表是草稿中的**有限承诺**，并非任意 C++ 程序的取消安全保证。前提为：使用本次验证的
配套 libc++／libc++abi 和 GNU 展开器配置；启用 Linux `__1` 命名空间的共享库双版本开关
`LIBCXX_ENABLE_TIZEN_CONDVAR_VERSIONS`；相关调用链对象用一致的新头重编并链接双版本库；
启用 C++ 异常及相应清理信息；使用**延迟取消**（在线程到达取消点时处理请求），不是异步取消。
调用链不得另有阻止展开的 `noexcept` 帧，调用方不得吞掉强制展开；正常 API 的锁所有权等前置条件仍适用。
实测线程用裸 `pthread_create` 创建，其他线程封装与此测法的等同性未在本轮证明。
配置与测法依据：[构建设计](../../IMPL_0908/W2/REPORT.md)、[最终实测与限定](../../IMPL_0908/W3/REPORT.md)。

| 承诺（含验证依据） | 已知限制（及为什么） |
|---|---|

## 未重编对象：四种绑定情形

ELF 是 Linux 可执行文件和共享库采用的二进制文件格式；`.o` 是编译后的目标文件，
`.a` 是目标文件归档。**编译决定调用点和清理代码，链接决定使用的符号版本。两步不能互相替代。**

以下旧 ELF 特指已经记录 `LLVM_22` 等待引用的对象；不是对任意无版本旧文件或任意动态查找方式的保证。
每行普通等待已在原生和实板各测 5 次，旧／新 system-clock 入口另各测 5 次；依据为
[两架构最终矩阵](../../IMPL_0908/W3/REPORT.md)、[版本表与具体行为](../../IMPL_0908/W2/REPORT.md)、[定时补测](../../IMPL_0908/W3/timed_versions.tsv)。

| 编译与链接情形 | 运行时入口 | 取消结局与边界 |
|---|---|---|
| 已链接旧程序，等待引用已记录旧节点 | `LLVM_22` | 保留旧不抛契约，进入终止处理。探针用标记处理器退出 86；86 不是默认系统信号的名称。 |
| 旧 `.o`／`.a` 中的对象不重编，只重新链接双版本库 | 新默认 `LLVM_22_TIZEN_1` | **依赖旧机器码和异常清理表布局**：可能执行清理，也可能线程已回收而锁滞留。本轮 quiet 帧实测清理/解锁为 0，竞争者无法取得锁；不在干净退出承诺内。 |
| 新头重编对象，并链接双版本库 | 新默认 `LLVM_22_TIZEN_1` | 在前述调用链前提下，清理和解锁各为 1，竞争者可取得锁，线程干净回收。 |
| 新头重编对象，但先链接旧单版本库，之后运行时才换新库 | `LLVM_22` | 已记录的旧版本需求仍保留，进入旧终止路径；仅更新运行时库不会重选链接时已记录的版本。 |

旧对象重新链接为何不能预测为统一结局：旧编译器按“不抛出”假设，可以不为该调用点生成清理区域。
附近是否存在其他可抛调用、编译选项及优化会影响清理表覆盖的机器码范围；重新链接不补生成这些代码。
先前同源旧头“邻近可抛调用”与 quiet 两种形态，已在 x86_64 原生、armv7l 实板分别观察到
“执行清理”和“锁滞留”。这不是随机概率，也不是说每个旧对象都必然滞留；这里的“布局”
指**调用点与清理表覆盖布局**，与 Boost 的 C++ 对象内存布局问题不同。
验证依据：[旧调用方两种形态及底层锁状态](../../R115/W3/REPORT.md)。

## 三处头文件实现不能靠动态库升级修正

“内联”在此指实现已随头文件编入消费方，而非必须在最终汇编中消失。单独更新动态库
无法改写旧对象中已有的这些实现；可靠生效需要重编所有相关翻译单元（一次源文件编译的单位）。

| 头文件实现 | 为什么旧对象必须重编 |
|---|---|
| steady-clock 定时等待 | 不抛契约和相应调用点信息已编入消费方，库端双版本没有对应的可靠修补位置。 |
| 自定义 Clock 定时等待模板 | 模板实例在消费方生成；换库不重新实例化旧代码。 |
| `wbuffer_convert` 析构 | 旧析构中的自动同步调用已经编入消费方；新库不能把那段旧代码删掉。 |

共享锁**定时写者的回滚守卫**也在头文件内，相关对象同样必须重编。
不得把新旧头生成的实现混合后偶然选中某个副本当作兼容保证；先前已观察到同名模板副本合并时的
链接顺序影响。静态及实验依据：[内联与混合对象核查](../../R112/REPORT.md)、[本次版本边界](../../IMPL_0908/W2/REPORT.md)。

## 外部可观察的行为变化

转换缓冲样本写入 `abcdef`：显式同步时，新旧两组都输出 6 字节；不显式同步时，旧组输出
6 字节，新组只输出 `a`，**本样本未输出 5 字节**，不是普遍固定损失量。
官方 `overflow.pass.cpp` 依赖析构刷新，在两架构新库均失败，而匹配旧基线单项均通过。
这不是 `noexcept` 假设测试；本包按用户明确的三方对照标准，将它列为已接受行为变化，仍保留原 FAIL。验证依据：[具体输出与官方对照](../../IMPL_0908/W3/REPORT.md)。

普通错误在**新入口**可以抛出 `system_error`（携带系统错误信息的异常），旧入口仍因不抛契约终止。
这不把“调用时未持有锁”等不满足前置条件的用法变成受支持的正常 API。
**无人捕获普通异常时，最终仍会终止进程，清理也不保证执行。** 既有 x86_64 实测中，
两种构建默认处理器均为 SIGABRT、诊断相同、局部清理均为 0；区别是终止发生的边界与传播路径。
不能把取消清理通过写成普通错误一定改善。验证依据：[无人捕获错误的回溯、信号与清理对照](../../R111/ITEM3_CONDVAR_UNWIND_REPORT.md)。

## 部署顺序约束与发布边界

要落入“新头、新节点”的承诺格，**新头必须先于相关对象重编，双版本库必须先于最终链接可用**。
运行时再替换库不能改写此前已经记录的旧版本需求，也不能补回旧对象清理代码。
还须部署配套的、包含既有运行时补丁的 libc++／libc++abi；不能只部署本次其中一个入口改动。
验证依据：[四种真实绑定及加载身份](../../IMPL_0908/W2/REPORT.md)、[两架构复核](../../IMPL_0908/W3/REPORT.md)。

Boost 的提供方和消费方须在实际对象边界上采用兼容 ABI，才有统一对象约定的前提。
只替换 Boost，而让旧消费方继续使用 libstdc++，可能形成混用窗口；构建完成与进入同一产品镜像
不是同一事件。本声明未证明全部 13 个消费方已迁移，也未证明发布系统支持原子切换或回滚。
依据：[迁移范围、构建条件与过渡期证据](../../R111/ITEM2_BOOST_TRANSITION_REPORT.md)。

发布验收仍须正视：已接受析构变化的对外说明、ARM 全量缺口、外部组件材料，
以及产品实际打包/部署身份。本轮没有进行产品 GBS/RPM 验收；历史 `SOURCE_PROVENANCE` 文件
不构成本次 sandbox 的新发布认证。本文不替代这些未完成的核验。

## 三方析构对照与本包官方套件状态

原生三方文件流样本输入三个宽字符，目标完整编码为九字节。不显式同步：新 libc++ 三字节、
旧 libc++ 九字节、libstdc++ 零字节，各 5/5；显式 pubsync 则三者均九字节，各 5/5。
按用户“libstdc++ 同样不能满足原析构输出断言就接受”的标准维持析构不同步。
**新 libc++ 与 libstdc++ 的字节数不相同**；一致的是不能把析构当最终同步保证，不能对外宣称完全等同。
N4861 D.21.2 的析构条款规定释放转换对象，没有要求析构刷新。具体证据与限制见
