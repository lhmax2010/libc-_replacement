# 第一阶段交人工确认的问题

第二阶段状态：`NOT_STARTED_WAITING_FOR_USER`。本阶段仅作范围建议，没有开始逐接口支持判定。

1. **是否按建议的 27 个源码包族开展第二阶段？**
   其中 26 族来自 40 个开发候选包版本组（27 个源码 RPM 版本记录），另加 `csapi-tizenfx` 托管侧。
   完整逐项清单在 tables/STAGE2_RECOMMENDED.tsv；ICU 两个发布版本不合并成一份架构实测证据。
2. **目标产品/profile/SDK 及应用来源是什么？**
   当前只界定冻结 Base/Unified 仓；public rootstrap 配方能提供候选证据，但不是最终 SDK 头文件白名单。
   需要业务/SDK 集成方提供目标产品、版本、profile、对应用实际开放的头文件/库/程序集清单，
   以及是否允许直接使用 DALi 原生 C++、Node/V8 与 LWE 原生接口。
3. **如何处理配方与名字所暗示的边界不一致？**
   public Chromium 配方明确列入 `_internal` 头和 Node/V8；Dali/LWE 在此次配方 RPM accept 中零命中，
   但已发布对应 devel 头文件。不能自行据此判“全公开”或“禁止应用使用”。
   建议第二阶段保留这些分层差异、标明待业务确认，而不是删掉其中任何一侧的证据。
4. **其余 C++ 候选是否有实际应用使用清单？**
   尚有 231 个包版本组在非内部候选头中有 C++ 信号，但无本轮 public 必要路径匹配依据；
   先提供应用依赖名单即可缩小集合。不能据此把它们判为“应用不接触”。
   另有两份 glibc-devel 版本组的 C++ 条件声明，暂不重复展开成新的标准库兼容性课题。
5. **公开配方的条件与缺口如何补齐？**
   部分配方涉及 i686/riscv32，代表头文件扫描并未覆盖这些架构；4 份 public 配方没有本轮头文件交集，
   2 条 internal 的 gstreamer-plugins-base-devel 名称记录未映射到冻结仓。
   需要相匹配的实际 SDK 生成结果；本轮不替换名称、不推断等价包。

原生 C 形态项可以暂缓 C++ 接口深查，但生命周期、异常/取消、回调与 ABI 前提仍保留。
本文件的建议仅针对分析范围，不是对接口改造或产品支持策略的处置建议。
