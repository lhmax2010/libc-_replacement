# 本批尚存疑问及需要人工/业务确认的材料

本批静态分类已完成，未继续其余四族，也未实施任何改造。

1. **最终 SDK 开放清单仍不可得。** 需要目标产品、版本/profile，以及提供给应用的头、库、程序集与 Web API/权限清单。
   已试冻结 public/internal rootstrap 配方、安装头及 pkg-config、源码公开/内部标记。
   Dali/LWE 原生入口缺少 public 配方相交依据不等于被禁止；Chromium 配方包含 internal/Node 头也不等于全对外开放。
2. **原生 Dali 的第三方使用资格。** 头、.pc 与 ELF 已证明可直接链接的技术入口；实际 SDK 是否包含并允许应用使用，需业务/SDK 集成方确认。
   NUI 所追踪 C# 路径不能替代该原生路径的 ABI 判断。
3. **EWK parser 与原生 Node/V8 是否在交付 SDK 中开放？** `ewk_parse_cookie` 明确传 std::string；不能仅因 extern "C" 归入纯 C。
   若实际未开放，只应从应用清单中排除，不改变该头本身的事实。
4. **Native 十一个例外是否进入下一批深入范围？** 本批已分开四族头内 C++ 便利封装与外置 C++ 对象/虚接口候选。
   需要先用最终 SDK 清单排除带入的内部/集成材料，不能直接把 11 族算成 11 族不兼容应用 API。
5. **其余四族是否分析？** glib2（通用基础库）、harfbuzz（字形塑形）、icu（Unicode/国际化）、vulkan-headers（图形 API 开发头）。
   本轮仅说明用途，不自行扩大范围。
6. **如需“可支持”的运行保证，还缺哪些材料？** 目标产品可执行环境、明确调用者与提供方的标准库/编译 ABI、
   实际 API 子集及所有权/异常/回调契约。本轮只有静态核查，不把既有 ICU 等固定样本通过转移给这批新接口。

另外记录两项事实限制，不作处置建议：

- binder 异常宏捕获 forced_unwind 后返回，且部分分配在所见 try/catch 范围外；
  没有据此重验或推断取消发生率、产品失败形态，也没有修改代码。
- webapi-plugins 内部同步二进制回复传 std::vector，尽管 Web 应用只传脚本/字节数据；
  这属于解释调用链所需的内部边界，未把它扩大为新的平台内部接口全量盘点。

自行判断已逐项写在 REPORT.md：路径标记分层、代表签名选取、按既有框架分类、明确标记的 C 化难点推断。
没有自行决定 SDK 资格、迁移顺序或实施方案。
