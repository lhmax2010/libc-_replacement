# 线程取消问题：解决方案定义

- 日期：2026-08-15
- 状态：**待裁决** —— 本文的目的是确定方案边界，不涉及实现排期
- 需要决定的事项：第五节三条

---

## 一、问题与约束

### 1-1 问题

POSIX 线程取消（`pthread_cancel`）在 glibc 上以强制展开实现，与 C++ 异常共用同一套底层机制。因此 `catch (...)` 会捕获线程取消；若不重新抛出，glibc 以 `FATAL: exception not rethrown` 终止进程。

libstdc++ 提供 `abi::__forced_unwind` 类型供代码识别并重抛；**libc++ 不提供该类型**。

### 1-2 约束（这些是既定条件，不在本次讨论范围）

| 约束 | 说明 |
|---|---|
| 标准库迁移到 libc++ | 项目目标 |
| glibc 保留由 GCC 构建 | LLVM 无法编译 glibc |
| 展开器采用 libgcc_s | 已定案；引入第二个展开器实测会崩溃 |
| 不修改消费者代码 | 76 个基础库双版本方案成立的前提 |
| armv7l 为先导架构 | 且其 EHABI 路径与 64 位不同 |

### 1-3 已排除的六个方向

均有实测依据，本次评审复核后结论不变：

| 方向 | 排除理由 |
|---|---|
| 改捕获具体类型 | 50 处逐处检查，无一处能确认保持原语义 |
| 线程入口禁用取消 | 同上，且改变取消语义 |
| 无条件重抛 | 真实异常的处理行为被改变 |
| 外来异常检测后重抛 | 消费侧无法完成正确重抛——重抛路径在运行时库内。（原表述为"无更可靠的区分手段"，经复核有误：`exception_class == 0` 可区分，但不改变结论） |
| 修改 personality 使 catch-all 跳过强制展开 | 会破坏 `pthread_exit`（走同一机制但需正常执行到 catch 块） |
| 逐包定制 | 50 处均无法确认保持原语义 |

**上游无现成方案。** 其他以 libc++ 为默认标准库的平台均为回避而非解决：Android/bionic 不实现 `pthread_cancel`，FreeBSD 用 libcxxrt，musl 的取消不做栈展开。Tizen 很可能是第一个「libc++ 默认 + glibc 线程取消 + libgcc_s」的组合。

## 二、问题实际有两层

这是本轮实测的核心发现，也是本文需要裁决的原因。

### 2-1 运行时层：libc++abi 没有可识别的类型

已由 R42 处理，四处改动，三个文件。详见第三节。

### 2-2 标准库层：libc++ 头文件自身没有防护

**libstdc++ 在其自身头文件与库中有 65 处防护，分布 16 个文件**（实测复核）。典型形态：

```cpp
__catch(__cxxabiv1::__forced_unwind&)
  { this->_M_setstate(ios_base::badbit); __throw_exception_again; }
__catch(...)
  { this->_M_setstate(ios_base::badbit); }
```

**libc++ 侧对应位置为裸 catch-all，`forced_unwind` 检索零命中。**

**运行时实测确认（两架构一致）**：

| 场景 | libstdc++ | libc++ | 打 R42 补丁后的 libc++ |
|---|---|---|---|
| `std::cout << x` 时被取消 | 正常取消 | **134 / abort** | **134 / abort（无变化）** |
| `std::getline` 阻塞时被取消 | 正常取消 | **134 / abort** | **134 / abort（无变化）** |
| `std::packaged_task` 内被取消 | 正常取消 | **134 / abort** | **134 / abort（无变化）** |

> **R42 的补丁对这些场景完全无效**——补丁提供的是"可识别的类型"，而 libc++ 头文件里根本没有捕获该类型的子句。

**消费面**（近似，头文件内联进消费者，源码扫描无法精确定位）：

| 口径 | 数量 |
|---|---|
| 371 个源码包中使用相关标准库设施的 | **329** |
| 其中同时存在线程/取消迹象的 | **147** |

对比应用代码层的口径（10 个包 / 50 处），**差一个数量级**。

### 2-3 两层的依赖关系

```
libc++abi 提供可识别的类型
        ↓
libc++ 头文件用该类型写防护
        ↓
应用代码的防护子句才能正常工作
```

**第二层缺失，第一层的价值为零** —— 这已由 2-2 的实测证实。

## 三、运行时层的当前状态

### 3-1 四处改动

| # | 位置 | 内容 | 状态 |
|---|---|---|---|
| 1 | `cxxabi.h` | 定义 `__cxxabiv1::__forced_unwind`，以 out-of-line key function 使 typeinfo 成为库内唯一强定义 | 正确，但**类形态需改回 libstdc++ 的抽象类形态**（私有析构 + 纯虚函数），否则允许按值捕获，与 libstdc++ 源码不兼容 |
| 2 | `cxa_personality.cpp` | 外来异常在强制展开时映射为该类型 | 正确 |
| 3 | `cxa_exception.cpp` | `__cxa_rethrow` 对外来异常改用 `_Unwind_Resume_or_Rethrow` | 正确，与 libstdc++ 逐字一致 |
| 4 | `cxa_personality.cpp` | EHABI 下为强制展开的 catching handler 走 handler 路径而非 cleanup 路径 | 方向正确，**门控条件过窄，引入回归**（见 3-2） |

### 3-2 待修的回归

第 (4) 处的门控只对"我们新加的类型"放行，未覆盖 `catch (...)`。后果：`catch (...) { ...; throw; }` 这一写法在 armv7l 上会 `std::terminate`。

**由上游自带测试直接证实**：

| 组合 | `libcxxabi/test/forced_unwind1.pass.cpp` |
|---|---|
| armv7l + 未打补丁 | 通过 |
| armv7l + libstdc++ | 通过 |
| **armv7l + R42 补丁** | **退出 134** |

**这是我们引入的回归**，且只在先导架构上出现（x86_64 的 Itanium 路径无此机制）。

修法：门控从「是不是新加的类型」改为「是不是 catching handler」，与 libstdc++ 的判据一致，约三行，改后可删去一个中间字段。

### 3-3 运行时层的验证状态

28 格矩阵（两架构 × 七类场景 × libc++/libstdc++）全部通过，另有未打补丁对照复现原始故障。但该矩阵**结构性地未覆盖 catch-all 重抛形态**——三个 catch-all 分支均不重抛。上游测试补上了这个缺口。

## 四、方案的完整形态

综合两层，方案应包含：

### 4-1 运行时层（libc++abi）

| 项 | 说明 |
|---|---|
| 类型定义 | 与 libstdc++ 逐字兼容的抽象类 + key function |
| personality 类型映射 | 强制展开的外来异常映射为该类型 |
| 重抛路径修正 | 外来异常用 `_Unwind_Resume_or_Rethrow` |
| EHABI handler 帧路径 | 按 catching handler 处理，不走 cleanup 登记 |

**性质**：其中重抛路径与 EHABI 路径两项属**纯缺陷修复**（后者是上游 2021 年一次改动留下的后续问题），上游接受概率较高；类型定义与映射两项属 **GNU 扩展语义**，上游态度未知。

### 4-2 标准库层（libc++ 头文件）

在 libc++ 的 65 处对应位置补上等价防护。

**性质**：属 GNU 扩展语义的移植，上游大概率不接受，**长期自维护的主体在这一层**。

**已知形态特征**：65 处的写法高度重复，libstdc++ 自身使用宏（`__catch` / `__throw_exception_again`）实现。是否可用同类手段统一处理，尚未评估。

## 五、需要裁决的三条

### 决策一：方案是否包含标准库层？

| 选项 | 后果 |
|---|---|
| **包含** | 方案完整。自维护补丁从 3 个文件扩展至约 20 个文件 |
| **不包含** | 需**书面接受**：147 个包在标准库 I/O 中被取消时会 abort，且故障堆栈落在标准库内部、应用代码中找不到任何 catch，现场归因困难 |

> 参考事实：不包含时，运行时层的四处改动只对应用代码中已有防护子句的 10 个包（约 46 处独立站点）有效。

### 决策二：若包含，覆盖范围？

**本条待决策一确定后再议，当前信息不足以裁决。**

若决策一为"包含"，默认覆盖范围应为**全部 65 处**——与 libstdc++ 语义完全对齐。缩小范围需要理由，而唯一可能的理由是工作量。

但工作量目前无法评估：65 处的写法高度重复，libstdc++ 自身以宏（`__catch` / `__throw_exception_again`）实现，**若可用同类手段统一处理，补 65 处与补一个子集的成本差别可能很小**。此外，按设施划分子集也需要先查清每处防护所属的设施、对应的 libc++ 位置、以及各设施的调用路径上是否真的存在取消点——这些均未测量。

因此本条的正确顺序是：决策一确定 → 摸清能否统一处理 → 届时再判断是否需要缩小范围。

### 决策三：上游提交的范围与时机？

已确认的前提：材料已归档，**待产品验证完成后再提交**（此为既定决定）。需确定的是：

| 选项 | 说明 |
|---|---|
| 全部提交 | 含 GNU 扩展语义部分，被拒概率高 |
| 仅提交缺陷修复部分 | 重抛路径 + EHABI 路径两项，接受概率高，可显著降低长期 rebase 成本 |
| 分两笔提交 | 缺陷修复先行，扩展语义另议 |
