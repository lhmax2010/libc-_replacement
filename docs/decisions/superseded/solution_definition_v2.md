## 一、问题与约束

### 1-1 问题

POSIX 线程取消（`pthread_cancel`）在 glibc 上以强制展开实现，与 C++ 异常共用同一套底层机制。因此 `catch (...)` 会捕获线程取消；若不重新抛出，glibc 以 `FATAL: exception not rethrown` 终止进程。

libstdc++ 提供 `abi::__forced_unwind` 类型供代码识别并重抛；**libc++ 不提供该类型**。

### 1-2 既定约束

| 约束 | 说明 |
|---|---|
| 标准库迁移到 libc++ | 项目目标 |
| glibc 保留由 GCC 构建 | LLVM 无法编译 glibc |
| 展开器采用 libgcc_s | 已定案；引入第二个展开器实测会崩溃 |
| 不修改消费者源码 | 76 个基础库双版本方案成立的前提 |
| armv7l 为先导架构 | 其 EHABI 路径与 64 位不同 |

### 1-3 已排除的六个方向

均有实测依据，评审复核后结论不变：

| 方向 | 排除理由 |
|---|---|
| 改捕获具体类型 | 逐处检查，无一处能确认保持原语义 |
| 线程入口禁用取消 | 同上，且改变取消语义 |
| 无条件重抛 | 真实异常的处理行为被改变 |
| 外来异常检测后重抛 | **消费侧无法完成正确重抛——重抛路径在运行时库内**（原表述"无更可靠的区分手段"有误：`exception_class == 0` 可区分，但不改变结论） |
| 修改 personality 使 catch-all 跳过强制展开 | 会破坏 `pthread_exit`（走同一机制但需正常执行到 catch 块） |
| 逐包定制 | 同第一项 |

**上游无现成方案。** 其他以 libc++ 为默认标准库的平台均为回避而非解决：Android/bionic 不实现 `pthread_cancel`，FreeBSD 用 libcxxrt，musl 的取消不做栈展开。Tizen 很可能是第一个「libc++ 默认 + glibc 线程取消 + libgcc_s」的组合。

## 二、问题分三层

### 2-1 层 A：展开机制缺陷（与本方案的范围裁决无关）

libc++abi 中两处与 `__forced_unwind` 类型无关的缺陷：

| 缺陷 | 表现 |
|---|---|
| `__cxa_rethrow` 对外来异常使用 `_Unwind_RaiseException` | 应为 `_Unwind_Resume_or_Rethrow`（libstdc++ 用的正是后者）。前者把强制展开当普通异常重抛，glibc 的 stop 函数不再被调用 |
| EHABI 下 catching handler 被登记为 cleanup | 上游 2021 年一次改动（EHABI 增加强制展开支持）留下的后续问题。`__cxa_begin_cleanup` 压栈无配对出栈，重抛续跑后遇下一个 cleanup 帧即终止 |

**这两处属纯缺陷修复，其价值不依赖标准库层。** 修复后，`catch (...) { …; throw; }` 这一在 libstdc++ 下正常工作的写法，在 libc++ 下也能正常工作。

**验证**：上游自带测试 `libcxxabi/test/forced_unwind{1,2,3,4}` 与 `unwind_0{1..6}`，两架构 20/20 通过。

### 2-2 层 B：识别类型缺失

libc++abi 不提供 `abi::__forced_unwind`，代码无法识别强制展开。

补齐需两处：类型定义（与 libstdc++ 逐字对应的抽象类 + out-of-line key function，使 typeinfo 成为库内唯一强定义），以及 personality 在强制展开时将外来异常映射为该类型。

**属 GNU 扩展语义的移植。**

### 2-3 层 C：标准库自身缺少防护

libstdc++ 在其头文件与库中有 65 处防护；libc++ 侧对应位置为裸 catch-all。

**实测（两架构一致）**：

| 场景 | libstdc++ | libc++ | libc++ + 层 A/B |
|---|---|---|---|
| `std::cout << x` 时被取消 | 正常取消 | 134 / abort | **134 / abort（无变化）** |
| `std::getline` 阻塞时被取消 | 正常取消 | 134 / abort | **134 / abort（无变化）** |
| `std::packaged_task` 内被取消 | 正常取消 | 134 / abort | **134 / abort（无变化）** |

> 层 A/B 对这些场景无效——它们提供的是"可识别的类型"，而 libc++ 头文件里没有捕获该类型的子句。

**消费面**（近似上界；头文件内联进消费者，源码扫描无法精确定位）：

| 口径 | 数量 |
|---|---|
| 371 个源码包中使用相关标准库设施的 | 329 |
| 其中同时存在线程/取消迹象的 | **147** |

对比应用代码层的口径（10 个包 / 约 46 处独立站点），差一个数量级。

### 2-4 三层的关系

- **层 A 独立成立**：不依赖 B、C，修复后即消除一类真实缺陷；
- **层 B 是层 C 的前提**：没有可识别的类型，头文件里无从写防护；
- **层 C 决定实际覆盖面**：只做 A+B，147 个包在标准库 I/O 中被取消时仍会 abort。

## 三、层 A 与层 B 的当前状态

四处改动，三个文件，**已完成并验证**：

| # | 层 | 位置 | 内容 |
|---|---|---|---|
| 1 | B | `cxxabi.h` | 定义 `__forced_unwind`（私有虚析构 + 纯虚函数，与 libstdc++ 同形态，不可实例化、不能按值捕获），out-of-line key function 使 typeinfo 成为库内唯一强定义 |
| 2 | B | `cxa_personality.cpp` | 外来异常在强制展开时映射为该类型 |
| 3 | A | `cxa_exception.cpp` | `__cxa_rethrow` 对外来异常改用 `_Unwind_Resume_or_Rethrow` |
| 4 | A | `cxa_personality.cpp` | EHABI 下按 catching handler 处理（判据 `ttypeIndex != 0`，与 libstdc++ 的 `found_cleanup` 门一致），不走 cleanup 登记 |

**验证结果**：

| 项 | 结果 |
|---|---|
| 上游自带测试 | 两架构 20/20 通过 |
| 回归矩阵 | 两架构 18/18 场景退出 0，与 libstdc++ 的退出码及 join 结果一致 |
| 消费者链接选项 | 无需 `--export-dynamic` |
| 按值捕获 | 两套标准库均拒绝（与 libstdc++ 语义一致） |

## 四、层 C 的成本结构（已实测）

### 4-1 站点分布

libc++ 侧共 **50 处 catch-all / 7 个头文件**（口径已核实准确）：

| 分类 | 数量 | 修改后消费者是否需重编 |
|---|---|---|
| **汇聚到 `src/ios.cpp` 的两个 out-of-line 函数** | **16**（15 处 badbit、1 处 failbit） | **否** —— 库内改动 |
| 位于消费者头文件 | **34** | **是** —— 内联进每个消费者 |
| 无对应物 | 8 | 不适用 |

> 第 1 版所写"65 处 / 约 20 个文件"是 **libstdc++ 侧**的分布，被误用于估算 libc++ 侧工作量，已更正。

### 4-2 汇聚点方案已验证可行

只修改 `ios.cpp` 的汇聚函数（配合层 B 的类型），重跑取消测试：

| 架构 | 结果 |
|---|---|
| x86_64 | 取消成功，`join=PTHREAD_CANCELED`，与 libstdc++ 对照一致 |
| armv7l | 取消成功（**需先修复层 A 的 EHABI 缺陷**；在其修复前该格失败） |

**这同时补上了此前缺失的正向证据**：此前只证明了"libc++ 会吞掉强制展开"，未证明"补上防护就能修好"。

### 4-3 但汇聚点不能覆盖全部

`getline` 场景走的是**头文件本地的 catch-all**，不经过 badbit 汇聚函数——只改汇聚点对它无效（实测仍 134）。

**因此那 34 处头文件站点绕不过去**，成本没有数量级下降：16 处便宜（库内、不重编消费者），34 处贵（头文件、要重编消费者），而 34 处是必需的。

### 4-4 一处已更正的误读

第 1 版称"libstdc++ 用宏（`__catch` / `__throw_exception_again`）实现，故层 C 可能可归并"。实际这两个是 `-fno-exceptions` 兼容宏，**不做任何归并**，libstdc++ 的 65 处全部长手写。归并机会在 libc++ 一侧的 `ios.cpp` 汇聚点，理由与宏无关。

## 五、消费者重编的含义

这是层 C 成本的主要构成，需要单独说明：

- 修改 `ios.cpp`（16 处）：**库内改动**，重新发布 libc++ 即可，消费者不动；
- 修改头文件（34 处）：**内联进消费者**，所有使用相关设施的包必须重新编译。

**但这一项与迁移本身重合**——迁移到 libc++ 本就要求全部 C++ 包重新编译。若层 C 的头文件改动与迁移同批完成，则**不产生额外的重编成本**；若在迁移完成之后才做，则需要第二次全量重编。

**这构成一个时序约束**：层 C 的头文件部分应与迁移同期落地。

## 六、需要裁决的事项

### 决策一：方案是否包含层 C？

| 选项 | 后果 |
|---|---|
| **包含** | 方案完整。改动范围：`ios.cpp` 两个函数 + 7 个头文件的 34 处 |
| **不包含** | 需**书面接受**：147 个包（近似上界）在标准库 I/O 中被取消时会 abort，故障堆栈落在标准库内部、应用代码中找不到任何 catch，现场归因困难 |

**技术层面的参考意见**：三方独立评审一致认为应当包含，主要依据是——消费侧无法自救（库内的 catch-all 先于任何应用 handler 吞掉展开，而消费者源码不可修改是既定约束），"不包含"等于永久接受一类应用无法规避的 abort。

**唯一可能翻转该结论的信息**：若平台生产运行路径上实际不调用 `pthread_cancel`，则整个问题（含层 A、B）退化为编译兼容问题。已有的局部调查指向这一方向——对首批两个包的 44 个消费者仓搜索，结论均为"生产代码中未观察到取消调用，仅测试中触发"。但该结论**不能由源码扫描推广到全平台**（外部取消与厂商二进制包均不可见），需要在产品镜像上做动态探针才能确认。

### 决策二：层 C 的覆盖范围？

若决策一为"包含"，默认应覆盖全部 50 处。缩小范围的唯一理由是成本，而成本结构已明确（16 处库内 + 34 处头文件，后者与迁移重编重合）。

**建议按站点性质分批**，而非按设施裁剪：

| 批次 | 内容 | 性质 |
|---|---|---|
| 优先 | `ios.cpp` 的 16 处 | 库内改动，不重编消费者，可独立发布 |
| 与迁移同批 | 头文件 34 处 | 借迁移的全量重编落地，不产生额外重编成本 |
| 另议 | 无对应物的 8 处 | 需先确认其在 libc++ 中的等价位置 |

### 决策三：上游提交的范围与时机？

已定：材料已归档，**待产品验证完成后再提交**。需确定范围：

| 选项 | 说明 |
|---|---|
| 仅提交层 A（两处缺陷修复） | 属纯缺陷修复，其中 EHABI 一处是上游 2021 年改动的后续问题，且有上游自带测试作证；**接受概率较高，可显著降低长期 rebase 成本** |
| 层 A + 层 B | 层 B 属 GNU 扩展语义，上游态度未知 |
| 全部（含层 C） | 层 C 是对 libc++ 头文件的大范围改动，上游大概率不接受 |

**前置条件**：层 A 的两处修复应作为同一系列提交（EHABI 那处依赖重抛那处才能完整生效）。
