## 一、问题与约束

### 1-1 问题

POSIX 线程取消（`pthread_cancel`）在 glibc 上以强制展开实现，与 C++ 异常共用同一套底层机制。因此 `catch (...)` 会捕获线程取消；若不重新抛出，glibc 以 `FATAL: exception not rethrown` 终止进程。

libstdc++ 提供 `abi::__forced_unwind` 类型供代码识别并重抛；**libc++ 不提供该类型**。

### 1-2 既定约束

| 约束 | 说明 |
|---|---|
| 标准库迁移到 libc++ | 项目目标 |
| glibc 保留由 GCC 构建 | LLVM 无法编译 glibc |
| 展开器采用 libgcc_s | 已定案；引入第二个展开器实测会崩溃 |
| 不修改消费者源码 | 76 个基础库双版本方案成立的前提 |
| armv7l 为先导架构 | 其 EHABI 路径与 64 位不同 |

### 1-3 已排除的六个方向

均有实测依据，评审复核后结论不变：

| 方向 | 排除理由 |
|---|---|
| 改捕获具体类型 | 逐处检查，无一处能确认保持原语义 |
| 线程入口禁用取消 | 同上，且改变取消语义 |
| 无条件重抛 | 真实异常的处理行为被改变 |
| 外来异常检测后重抛 | **消费侧无法完成正确重抛——重抛路径在运行时库内**（原表述"无更可靠的区分手段"有误：`exception_class == 0` 可区分，但不改变结论） |
| 修改 personality 使 catch-all 跳过强制展开 | 会破坏 `pthread_exit`（走同一机制但需正常执行到 catch 块） |
| 逐包定制 | 同第一项 |

**上游无现成方案。** 其他以 libc++ 为默认标准库的平台均为回避而非解决：Android/bionic 不实现 `pthread_cancel`，FreeBSD 用 libcxxrt，musl 的取消不做栈展开。Tizen 很可能是第一个「libc++ 默认 + glibc 线程取消 + libgcc_s」的组合。

## 二、问题分三层

### 2-1 层 A：展开机制缺陷（与本方案的范围裁决无关）

libc++abi 中两处与 `__forced_unwind` 类型无关的缺陷：

| 缺陷 | 表现 |
|---|---|
| `__cxa_rethrow` 对外来异常使用 `_Unwind_RaiseException` | 应为 `_Unwind_Resume_or_Rethrow`（libstdc++ 用的正是后者）。前者把强制展开当普通异常重抛，glibc 的 stop 函数不再被调用 |
| EHABI 下 catching handler 被登记为 cleanup | 上游 2021 年一次改动（EHABI 增加强制展开支持）留下的后续问题。`__cxa_begin_cleanup` 压栈无配对出栈，重抛续跑后遇下一个 cleanup 帧即终止 |

**这两处在代码路径上与层 B、层 C 解耦**：其触发条件不要求进入 libc++ 标准库层。修复后，`catch (...) { …; throw; }` 这一在 libstdc++ 下正常工作的写法，在 libc++ 下也能正常工作。

**验证**：新增的 catch-all 重抛场景（`pthread_cancel` 与 `pthread_exit` 各一格，两架构）——修复前失败、修复后退出 0 且与 libstdc++ 的 join 结果一致。

> **证据强度的边界**：上游自带测试 `forced_unwind{1,2,3,4}` 与 `unwind_0{1..6}` 在修复后两架构 20/20 通过，**但该矩阵不能用于证明层 A 的独立价值**——未打补丁版本同样 20/20，且被测对象是层 A+B 的组合而非层 A 单独。`forced_unwind1` 虽含 catch-all 重抛，但未验证重抛后 stop callback 是否继续被调用，故错误路径也能通过。层 A 目前**尚无 A-only 的隔离验证矩阵**。

### 2-2 层 B：识别类型缺失

libc++abi 不提供 `abi::__forced_unwind`，代码无法识别强制展开。

补齐需两处：类型定义（与 libstdc++ 逐字对应的抽象类 + out-of-line key function，使 typeinfo 成为库内唯一强定义），以及 personality 在强制展开时将外来异常映射为该类型。

**属 GNU 扩展语义的移植。**

### 2-3 层 C：标准库自身缺少防护

libstdc++ 在其头文件与库中有 65 处防护；libc++ 侧对应位置为裸 catch-all。

**实测（两架构一致）**：

| 场景 | libstdc++ | libc++ | libc++ + 层 A/B |
|---|---|---|---|
| `std::cout << x` 时被取消 | 正常取消 | 134 / abort | **134 / abort（无变化）** |
| `std::getline` 阻塞时被取消 | 正常取消 | 134 / abort | **134 / abort（无变化）** |
| `std::packaged_task` 内被取消 | 正常取消 | 134 / abort | **134 / abort（无变化）** |

> 层 A/B 对这些场景无效——它们提供的是"可识别的类型"，而 libc++ 头文件里没有捕获该类型的子句。

**消费面**（近似上界；头文件内联进消费者，源码扫描无法精确定位）：

| 口径 | 数量 |
|---|---|
| 371 个源码包中使用相关标准库设施的 | 329 |
| 其中同时存在线程/取消迹象的 | **147** |

对比应用代码层的口径（10 个包 / 约 46 处独立站点），差一个数量级。

### 2-4 三层的关系

- **层 A 不依赖 B、C**：其修复独立消除一类真实缺陷；
- **层 B 是层 C 的前提**：没有可识别的类型，头文件里无从写防护；
- **层 C 依赖层 A（至少在 armv7l 上）**：层 C 的防护以重抛实现，而重抛在 EHABI 下会命中层 A 的缺陷——实测中，层 A 未修复时层 C 的验证在 armv7l 上失败；
- **层 C 决定实际覆盖面**：只做 A+B，标准库 I/O 中的取消场景仍会 abort（实测：`cout`、`getline`、`packaged_task` 三个场景，层 A+B 后行为无变化）。

## 四、层 C 的成本结构（已实测）

### 4-1 站点分布

libc++ 侧共 **50 处 catch-all**（分布于 4 个头文件），按"修改后消费者是否需要重新编译"分为两类。该分类已按符号级实测确定（下详）：

| 分类 | 数量 | 构成 |
|---|---|---|
| **库内可交付**（不需重编消费者） | **34** | 汇聚到 `src/ios.cpp` 两个函数的 **16 处**；`basic_istream<char>` 显式实例化成员等 **18 处** |
| **需重编消费者** | **16** | istream 自由函数 6、future 9、string 1 |
| **合计** | **50** | |

另有 **8 处**属"libstdc++ 侧有防护但 libc++ 中无直接对应物"——**这是另一口径，不是上述 50 的子集**，需先确认其在 libc++ 中的等价位置才能判断处置方式。

> **该分类相对前版发生对调。** 第 3 版记为"16 处库内 / 34 处需重编"，其中"34 处需重编"是**静态判定加两处抽样**的结果，而两个抽样恰好都取自"必然需重编"的一侧。符号级核查表明其中 18 处实为库内符号。

> 第 1 版所写"65 处 / 约 20 个文件"是 **libstdc++ 侧**的分布，被误用于估算 libc++ 侧工作量，已更正。

### 4-1a 分类的符号级核查依据

对 34 处逐一做**二维判定**——库侧是否导出、消费者侧引用形态——并在 `-O0` 与 `-O2` 两种优化级下各测一次：

| 类别 | 数量 | 判据 |
|---|---|---|
| 库侧导出（弱符号，带版本节点）× 消费者侧为未定义引用 | 16 | `basic_istream<char>` 的 15 个显式实例化成员 + `basic_ostream<char>::sentry` 析构 |
| 未导出，但经导出载体成员编入库内 | 2 | istream 的算术输入 helper，其载体是十余个导出的 `operator>>` 重载 |
| 未导出 × 消费者持本地副本 | 16 | istream 自由函数 6、future 9、string 1 |

**`-O0` 与 `-O2` 逐站点结论一致，无分歧；不可判定 0 处。**

**该分类的成立条件**（超出下述条件时需重新判定）：

| 条件 | 说明 |
|---|---|
| 标准 `char` / `wchar_t` + `std::char_traits` 的显式实例化 | 非标准特化不在显式实例化范围内 |
| 动态链接 libc++ | 静态链接或内嵌 libc++ 的消费者不适用 |
| 默认的 extern-template 行为 | 关闭该行为则消费者自带副本 |
| 无 LTO | LTO 可能跨模块内联，使消费者不再引用库内定义 |
| 无同名符号插入 | 这些符号为弱符号（vague linkage），若消费者持有同名定义且解析顺序在前，库内定义不生效 |

**架构口径**：上述分类与下节的对偶实验**均在 x86_64 上取得**。armv7l 的消费者/DSO 级符号核查尚未进行（列入实施前置项，见附录）。

**已记录的残余边界**：弱符号插入与 LTO/激进内联两条路径均未实测（`NOT_OBSERVED`）；两者若发生，会使对应站点从"库内可交付"变为"需重编消费者"。

**判定基准**：三个参照库（平台 GBS 构建版、重链版、**平台发布 RPM 版**）的动态导出名集**零差异**（各 1970 个符号），故不存在"构建版与产品形态不一致"的风险。

**future 的 9 处无法库内化**，理由是**签名集无界，且相关成员标注了 `_LIBCPP_HIDE_FROM_ABI`**——不可能为消费者的任意可调用类型预先实例化，且该标注本身就要求内联进消费者。

> 前版将理由写为"模板参数含消费者自身的类型"，对其中 4 处不成立——`packaged_task` 是类型擦除的。结论不变，理由已更正。

### 4-2 两类站点均已取得正向证据

**16 处汇聚点**（修改 `ios.cpp` 的两个函数，配合层 B 的类型）：

| 架构 | 结果 |
|---|---|
| x86_64 | 取消成功，`join=PTHREAD_CANCELED`，与 libstdc++ 对照一致 |
| armv7l | 取消成功（**需先修复层 A 的 EHABI 缺陷**；在其修复前该格失败） |

其中 badbit 与 failbit 两个函数**分别验证**：只补 badbit 时 failbit 场景仍失败，两者都补后才通过。**限定条件**：failbit 路径的修复在实测中是在 badbit 防护已就位的前提下取得的，两者的独立性未单独验证。

**需重编消费者的一类**（抽样 2 处：`istream/getline` 自由函数与 `future/packaged_task`，两架构）：

| 组合 | 结果 |
|---|---|
| 未打任何补丁 | 134 |
| 层 A+B，头文件未改 | 134 |
| 只重编 libc++、不重编消费者 | 134 |
| **头文件补防护 + 重编消费者** | **0，`join=PTHREAD_CANCELED`** |
| libstdc++ 对照 | 0，`join=PTHREAD_CANCELED` |

**库内可交付的一类**（抽样 2 处：`basic_istream<char>` 的 `getline` 与 `read` 成员，x86_64）——**该组做了双向对偶验证**：

| 组合 | 结果 |
|---|---|
| 未打任何补丁 / 仅层 A+B | 134 |
| **补防护 + 只重编 libc++，消费者不动**（`-O0`/`-O2` 各一） | **0，`PTHREAD_CANCELED`** |
| **镜像格：补丁头重编消费者 + 旧库** | **134** |
| 补丁库 + 补丁头消费者 / libstdc++ 对照 | 0，`PTHREAD_CANCELED` |

> 镜像格与关键格构成对偶：**只换库即可修复，只换消费者不行**——直接证明这类站点的防护只能由库交付。关键格附换入库的 SHA256 与运行时加载原文双重佐证。

> **抽样局限**：两类各抽 2 处，结果不外推至同类其余站点；符号级分类覆盖全部 34 处。

**这补上了此前缺失的正向证据**：此前只证明了"libc++ 会吞掉强制展开"，未证明"补上防护就能修好"。现两类站点均有正向证据。

### 4-3 但汇聚点不能覆盖全部

`getline` 自由函数场景走的是**头文件本地的 catch-all**，不经过 badbit 汇聚函数——只改汇聚点对它无效（实测仍 134）。因此汇聚点之外的站点绕不过去。

**但成本结构与第 3 版所述相反**：符号级核查表明 50 处中 **34 处可由库内交付**（16 汇聚点 + 18 库内符号），**16 处需重编消费者**（istream 自由函数 6、future 9、string 1）。第 3 版的"16 便宜 / 34 贵"应更正为"**34 便宜 / 16 贵**"。

### 4-4 一处已更正的误读

第 1 版称"libstdc++ 用宏（`__catch` / `__throw_exception_again`）实现，故层 C 可能可归并"。实际这两个是 `-fno-exceptions` 兼容宏，**不做任何归并**，libstdc++ 的 65 处全部长手写。归并机会在 libc++ 一侧的 `ios.cpp` 汇聚点，理由与宏无关。

## 五、消费者重编的含义

这是层 C 成本的主要构成，需要单独说明：

- **库内批（34 处）**：改动只进 libc++ 包，重新发布即可，消费者不动。含 `ios.cpp` 的 16 处汇聚点与 18 处库内符号站点；
- **头文件批（16 处）**：改动内联进消费者，所有使用相关设施的包必须重新编译。含 istream 自由函数 6、future 9、string 1。

**这一项与迁移本身重合**——迁移到 libc++ 本就要求全部 C++ 包重新编译。若层 C 的头文件改动在迁移编译之前就位，则**不产生第二轮重编**；否则需要对已迁移的包再编一次。

**实测确认**：对**需重编消费者的那一类**站点，只替换/重链 libc++ 而不重编消费者，行为不变——消费者中已内联的 catch 不会因库的更新而改变。**对库内可交付的那一类则相反**：只换库即生效，消费者不动。

> 第 3 版曾引用一格实验作为"只重编 libc++ 无效"的证据，但该格实际换入的是汇聚点补丁版的库，而非补了对应头文件站点的库，**承担不了该含义**，已更换为上述两类各自的对照结果。

**因此时序约束应精确表述为**：

> **层 C 中"需重编消费者"的那 16 处，必须在第一批消费者迁移编译之前进入 libc++ 包。**

其余 34 处由库内交付，不受该时序约束——它们可以在迁移的任何阶段随 libc++ 包更新发布。

这一约束还牵出三项需在实施时处理的事项：

| 事项 | 说明 |
|---|---|
| **三级发布顺序** | 层 C 的产物会引入对层 B 类型符号的未定义引用（已实证）。因此发布顺序必须是：**libc++abi（层 A+B）→ libc++（层 C）→ 消费者**。任一环节颠倒，装机即出现未解析符号 |
| **包依赖** | libc++ 包须对 libc++abi 声明**按 release 显式书写**的依赖。**ELF/RPM 的自动依赖在此不设防**——层 B 新增的符号仍挂在既有的 `LLVM_22` 版本节点上，而旧版 libc++abi 同样提供该节点（已实测 verdef 相同），故自动生成的依赖无法区分新旧。**重编后的消费者同样需要该显式依赖** |
| **不可单独回滚** | 基于同一原因，层 C 的 libc++ 不能在层 A+B 的 libc++abi 被回滚后单独留存；回滚须按相反顺序整体进行 |
| 构建顺序 | libc++ 包本身须先于任何消费者完成构建与发布 |
| 已迁移的包 | 若层 C 就绪时已有包完成迁移，这些包需重新编译一次 |
| 不可重编的二进制 | 厂商预编译包等无法重编者，无法获得层 C 的防护——须单独登记为已知缺口 |

## 六、需要裁决的事项

### 决策一：方案是否包含层 C？

| 选项 | 后果 |
|---|---|
| **包含** | 方案完整。改动范围：`ios.cpp` 两个函数 + 4 个头文件中的 48 处站点 |
| **不包含** | 需**书面接受**：处于风险范围的包在标准库 I/O 中被取消时会 abort，故障堆栈落在标准库内部、应用代码中找不到任何 catch，现场归因困难。风险范围的**近似上界为 147 个包**（该数为候选集上界，非实际受影响集合——实际受影响者取决于运行期是否真的发生取消） |

**技术层面的参考意见**：三方独立评审一致认为应当包含，主要依据是——消费侧无法自救（库内的 catch-all 先于任何应用 handler 吞掉展开，而消费者源码不可修改是既定约束），"不包含"等于永久接受一类应用无法规避的 abort。

**唯一可能翻转该结论的信息**：若平台生产运行路径上实际不存在任何强制展开入口（`pthread_cancel`、`pthread_exit` 等），则整个问题（含层 A、B）退化为编译兼容问题。已有的局部调查指向这一方向，但其广度**远小于第 2 版所述**：实际范围是**首批 2 个包、3 个代码仓、44 条 include 传播位置**（第 2 版误写为"44 个消费者仓"，把证据广度放大约 15 倍）。在该范围内，生产代码中未观察到取消调用，仅测试中触发。

该结论**不能由源码扫描推广到全平台**——外部发起的取消与厂商二进制包均不可见。需要在产品镜像上做动态探针才能确认。

**探针应挂在 `libgcc_s` 的 `_Unwind_ForcedUnwind` 上，而非两个 POSIX API。** 该函数是强制展开的汇聚点：一个挂点即可覆盖 `pthread_cancel`、`pthread_exit`、glibc 内部路径、第三方组件的直接调用，以及框架封装（如 GLib/ecore 的线程退出），并补上"厂商二进制不可见"的盲区。

**实现约束**：**不能用 `LD_PRELOAD`**——glibc 的取消路径经 `dlopen` + `dlsym` 解析 `libgcc_s.so.1`，预加载的同名符号拦不住它。须以 uprobe 或调试器断点挂在 **`libgcc_s.so.1` 本体**上。

**且翻转条件不止 `pthread_cancel`**：`pthread_exit` 走同一强制展开机制，同样会触发本问题。因此翻转条件应表述为"生产路径上不存在任何强制展开入口"，而非仅无 `pthread_cancel` 调用。

### 决策二：层 C 的覆盖范围与分批？

若决策一为"包含"，默认应覆盖全部 50 处。成本结构现已由符号级实测确定：

| 批次 | 内容 | 数量 | 性质与时序 |
|---|---|---|---|
| **库内批** | 库内可交付站点（16 处汇聚点 + 18 处库内符号） | **34** | 只进 libc++ 包，库侧单点验证，标准配置下不触碰消费者构建；**不受迁移时序约束**，可在任意阶段随 libc++ 更新发布 |
| **头文件批** | 需重编消费者的站点 | **16** | **必须最先就位**——须赶在第一批消费者开始迁移编译之前进入 libc++ 包；借迁移的全量重编落地，不产生额外重编成本 |
| 另议 | 无对应物的 8 处 | 8 | 需先确认其在 libc++ 中的等价位置 |

> **命名说明**：两批以站点性质命名而非序号，因为时间顺序与直觉相反——**头文件批反而必须先就位**，库内批则不受时序约束。

> **例外形态的处置**：满足 §4-1a 所列成立条件之外的消费者（静态链接 libc++、启用 LTO、存在同名符号插入等），其对应站点应按**头文件批**处理。此类消费者的审计列入实施前置项。

**头文件批的 16 处中，future 的 9 处无法库内化**（签名集无界 + 成员标注 `_LIBCPP_HIDE_FROM_ABI`），是硬约束，不存在把它们移入库内批的做法。

> 该分批依据符号形态而非设施类别，因为决定成本的是"改动能否由库交付"，与站点属于哪个设施无关。

### 决策三：上游提交的范围与时机？

已定：材料已归档，**待产品验证完成后再提交**。需确定范围：

| 选项 | 说明 |
|---|---|
| 仅提交层 A（两处缺陷修复） | 属纯缺陷修复，其中 EHABI 一处是上游 2021 年改动的后续问题，且有上游自带测试作证；**接受概率较高，可显著降低长期 rebase 成本** |
| 层 A + 层 B | 层 B 属 GNU 扩展语义，上游态度未知 |
| 全部（含层 C） | 层 C 是对 libc++ 头文件的大范围改动，上游大概率不接受 |

**依赖关系**：层 A 的两处修复应作为同一系列提交。原因是**重抛那处的修复会使 EHABI 缺陷显现**——在重抛仍走旧 API 时，EHABI 的 handler/cleanup 登记错误不会暴露；修正重抛后，该缺陷才成为必现故障。因此单独提交重抛修复而不带 EHABI 修复，会在 ARM 平台上引入回归。
