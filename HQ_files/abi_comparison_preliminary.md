# libstdc++ 与 libc++ 的 ABI 差异（初步版）

- 日期：2026-09-09
- 修订：P5，2026-09-11；证据以本次核对的既有记录为界，不代表当日重新进行产品验证。
- 本报告不是全部产品验收结论；支持范围以配套候审声明为准。
- 状态：**初步版** —— 成员级的内部实现比对尚未完成，见第五节
- 大小／对齐探针：x86_64；GNU 侧宿主 GCC 13.3.0；LLVM 侧 Clang 21.1.1 与缓存的平台 libc++／libc++abi。libc++ 头版本宏 220108 即 22.1.8，不是编译器版本。GCC 14.2 平台源码及基线符号清单是另一个输入。

## 一、哪些层一致、哪些层不同

这一点是理解全部差异的前提。

| 层 | 两套库 | 后果 |
|---|---|---|
| 名字修饰规则 | 同属 Itanium C++ ABI，实际名称仍受命名空间、ABI tag 等影响 | 本例可匹配，不代表所有接口可链接 |
| 函数调用约定 | 须核对目标 ABI、完整定义及编译选项 | 一致是兼容的前提，不是完整安全性证明 |
| 内置类型与 POD 的布局 | 满足同一目标 ABI 等条件时可设计兼容边界 | Engine／Rect 对应跨库调用实测为 NOT_OBSERVED；隐式 this、生命周期和异常路径也须核对 |
| **标准库类型的表示** | 已测部分大小／对齐不同，其余尚未证明完整等价 | 有静默错值反例，不是每个类型必然以同一方式失败 |
| 内联命名空间 | 不同（`__cxx11` / `__1`） | 部分符号名不同，链接会失败 |
| 异常与 RTTI | 实际运行时、personality 及符号绑定影响匹配 | 所测 GNU 插件→libc++ 的 BoundaryError 未进 typed catch；不能概括为所有类型信息丢失 |
| 分配器与内部状态 | 需核对实际分配器、析构、对齐及生命周期契约 | 加载两套库不等于两套独立堆；new[]／free 不配对即使同库也错误 |

**链接成功不足以保证正确。** 接口数据、生命周期、异常／取消路径及实际 ABI 配置共同决定
兼容条件。固定 C 接口样本通过不代表任意 C 接口安全；未统一 ABI 的标准对象、异常和
所有权直接跨界不在当前支持承诺内。部分组合链接即失败，部分可运行但产生错值。

## 二、对象布局的差异

固定 x86_64 探针的 33 个具体类型实例中，10 个 sizeof 或 alignof 不同，23 个两项均相同；
没有完成成员偏移、节点、控制块及操作语义等价性验证。

### 2.1 大小或对齐不同的类型

| 类型 | libstdc++ | libc++ | 差值 |
|---|---:|---:|---:|
| `std::any` | 16 | **32** | +16 |
| `std::function<void()>` | 32 | **48** | +16 |
| `std::deque<int>` | **80** | 48 | −32 |
| `std::map<int,int>` | **48** | 24 | −24 |
| `std::set<int>` | **48** | 24 | −24 |
| `std::unordered_map<int,int>` | **56** | 40 | −16 |
| `std::unordered_set<int>` | **56** | 40 | −16 |
| `std::string` | **32** | 24 | −8 |
| `std::future<int>` | **16** | 8 | −8 |
| `std::promise<int>` | **24** | 8 | −16 |

**注意方向不一致** —— 有的 libc++ 更大，有的更小。这说明两套库的设计取舍
不同，不是简单的"新版本更紧凑"。

表中数值和差值单位为字节，差值为 libc++ 减 libstdc++。std::function<void()> 的对齐亦不同：GNU／LLVM 为 8／16 字节。

### 2.2 大小与对齐相同的类型

其余 23 个（`std::array`、`std::pair`、`std::vector`、`std::unique_ptr`、
`std::shared_ptr` 等）大小与对齐相同。

**但大小相同不等于可以跨边界传递** —— 内部字段的含义与不变式仍可能不同。
本轮只比对了大小与对齐，**成员级比对未做**（见第五节）。

### 2.3 实测的后果

以下为原实验核心片段，提供方和消费方是不同翻译单元；省略头文件、打印及辅助函数定义。

```cpp
// 提供方（libstdc++ 构建）
std::deque<int>* make_payload() {
    return new std::deque<int>{11, 22, 33, 44};
}

// 消费方（libc++ 构建）
int main() {
    auto* payload = make_payload();
    const auto producer_view = provider_size(payload);
    const auto consumer_view = payload->size();
    destroy_payload(payload);       // 由提供方 delete
    return producer_view == consumer_view ? 0 : 42;
}
```

**链接和加载成功，无信号崩溃，但主动退出 42 标记错值。** provider／consumer 的 sizeof
为 80／48，长度视图为 4／106884723786536，并由 provider 的 destroy_payload 释放对象。
错误长度是当次输出，不是每次运行的固定值。

**为什么本例可链接**：普通非模板函数 make_payload 的返回类型未直接编码进 Itanium 名字
`_Z12make_payloadv`。`_Z9make_datav` 正确编码 make_data，但不是原实验符号。
模板函数、函数类型规则不同，ABI tag 也可能改变名字；原 string 版本就因 abi:cxx11 tag 链接失败。

## 三、导出符号的差异

| 项 | libstdc++ | libc++ |
|---|---:|---:|
| 去版本、按符号名去重的输入条目数 | 6,057（GCC x86_64 基线清单） | 1,969（缓存平台 libc++ 已定义导出记录） |
| **忽略版本的精确同名交集** | **17** | |

6,057＝4,546 FUNC＋1,511 OBJECT；不是全部公共 C++ API 数，也不是两份现场库用同一命令
得到的直接规模比较。构造／析构 ABI 变体各计符号名。17 项在 GNU 为 GLIBCXX_*／CXXABI_*，
在 LLVM 为 LLVM_22，版本契约不同。

**17 个同名符号已逐项静态核对标准层用途；在各自正确配对运行时中，分组行为探针输出一致。**
未证明错误配对、符号抢占／dlsym、双运行时 TLS、异常对象跨 provider 复制析构等组合可互换；
不能由同名同用途推出任意混用安全。

**差异的来源**：

1. **内联命名空间** —— libstdc++ 用 `std::__cxx11`、libc++ 用 `std::__1`，
   因此大量同名类型的修饰名不同；
2. **实现策略** —— libc++ 大量使用头文件内联（`_LIBCPP_HIDE_FROM_ABI`），
   代码编进使用方而非导出；libstdc++ 更多编在库中；

**第 2 点的后果**：libc++ 的很多实现**随使用方编译进其二进制**，
更新库改变不了已编译的那些副本。

## 四、线程取消相关的差异

本表对照固定未打本地补丁的源码，不代表已修补运行库的当前状态。GNU 为 GCC 14.2
源码 49c50605… 的 include/src/libsupc++，LLVM 为 5ed6c772… 的 libcxx/include、src。
typed-catch 句法点包含扩展、兼容源码及未求值条件分支，不代表编译后实例、可达取消点或问题数。
LLVM 统计不含 libcxxabi 自身的识别逻辑；原始零命中已有正向对照。

| 项 | libstdc++ | libc++ |
|---|---|---|
| 识别强制展开的标记类型 | **提供**（`abi::__forced_unwind`） | **不提供** |
| 所述源码目录内显式 typed-catch 识别句法点 | 65 处／16 文件 | 0 处（原始未补丁 libcxx） |
| `condition_variable::wait` 的异常规格 | **无**（GCC 为支持取消移除过） | **有 `noexcept`** |
| `wbuffer_convert` 析构 | `= default`，不同步 | 调用同步 |
| `shared_mutex` 的实现 | 所核配置使用 pthread_rwlock；宏可选择 CV fallback | 自己的状态机 |

**最后一行的边界**：glibc 2.40 的 pthread 读写锁具有用户态状态、原子操作与 futex；其获取
路径不提供延迟取消点，不能称为“取消后由内核自动恢复”。libstdc++ 后端受
_GLIBCXX_USE_PTHREAD_RWLOCK_T 等宏控制，不能由架构名推广所有构建。
原 libc++ 写者预占写者位后等待，若取消展开能穿过等待而无回滚，会留下状态；保留规格时
可能先终止。本批已加入相应回滚。两种后端均不能据此宣称任意异步取消安全。

## 五、本版未覆盖的内容

**以下项目尚未完成；工期与工作安排需由人工另行确认：**

1. **成员级的布局比对** —— 本版只比对了大小与对齐。要说清"内部实现差距"
   需要逐个类型比对：
   - 数据成员的类型、顺序、填充；
   - 虚表结构与虚函数顺序；
   - 内部辅助类型（节点、控制块、迭代器表示）；
   - 分配策略与增长策略；

2. **大小相同的 23 个类型是否真的等价** —— 大小相同不代表字段含义相同；

3. **同名 17 个符号的混用可互换性** —— 用途核查与正确配对探针已有，缺的是第三节所列混用组合；

4. **全部异常／RTTI 组合** —— 已测 GNU 插件抛 BoundaryError{77}：x86_64 原生及 armv7l 实板
   均进 catch-all、退出 12。相关 libc++abi personality 的 typed catch 先要求 native_exception，
   foreign 路径不匹配；不是所有 RTTI 丢失。任意类型、方向及符号绑定仍未覆盖；

5. **架构覆盖** —— 33 类型全表及 deque 仅 x86_64；ICU 单入口仅 armv7l 实板；受控 C ABI
   和上述异常有 x86_64 原生／armv7l 实板记录。Boost 另有原生 x86_64、armv7l QEMU、aarch64 QEMU
   代表边；aarch64 新增 22 条、累计代表组 49/90，不是全边覆盖。aarch64 完整取消／本批官方套件仍未完成。

其他未覆盖范围包括任意旧调用方、额外 noexcept／无异常帧、任意模板／回调、异步取消、
自定义分配器、任意插件加载组合、全量成员布局和第三方实际接口；外部组件分母不可得。

### 旧／新绑定与头文件限制

编译决定清理代码，链接决定符号版本。旧 ELF 在此特指已记录旧等待节点的二进制。

| 编译／链接形态 | 等待入口 | 已测边界 |
|---|---|---|
| 已链接旧 ELF | LLVM_22 | 保留旧终止契约 |
| 旧 .o／.a 不重编，只重新链接双版本库 | LLVM_22_TIZEN_1（新默认） | 依赖调用点与清理表布局；quiet 样本线程回收但锁滞留，不保证干净退出 |
| 新头重编并链接双版本库 | LLVM_22_TIZEN_1 | 被测前提下清理、解锁与后续进展通过 |
| 新头对象先链接旧单版本库，再更新运行库 | LLVM_22 | 仍走链接时记录的旧节点 |

双版本只覆盖普通等待和 system-clock 定时等待两个库内入口。steady-clock、自定义 Clock 等待、
wbuffer_convert 析构，以及定时写者回滚均有头文件实现；旧对象中的副本不能靠更新动态库修正，须重编相关翻译单元。

## 六、哪些差异需要保持一致

**本节陈述本项目已采用的处理原则，不是标准强制要求，也不是两套库全部行为等价的实测结论。**
以下只描述已裁决项目的具体对齐目标及边界；“标准不要求”不能推出“技术上绝无可能”。

| 差异 | 是否需要一致 | 我们的处理 |
|---|---|---|
| 线程取消的识别机制 | 已定目标 | 第一批补丁补标记类型；覆盖 50 站点＝20 头侧＋30 库侧，实际新增 36 typed handler＝20＋14＋2；两处汇聚 handler 覆盖库侧 16 站点 |
| `condition_variable` 的异常规格 | **需要** | 解除，与 libstdc++ 一致 |
| `wbuffer_convert` 析构行为 | 已定目标 | 不再自动刷新；不是全部输出字节数一致 |
| `shared_mutex` 的取消安全性 | 已定目标 | 两写者路径加状态回滚；GNU pthread 后端获取不提供延迟取消点，不等于自动回滚 |
| **对象布局** | 不在本轮追求互换范围 | 通过接口边界管理，不作技术不可能性断言 |
| 导出符号集合 | 不需要 | 实现策略不同，属正常差异 |
| 内联命名空间 | 不需要 | 它反而提供了部分保护（符号不撞名） |

等待取消展开、普通错误处理、读写锁取消响应及析构输出必须分别看。libc++ 仍保留错误检查；
未捕获普通错误仍可终止，清理不保证执行。wbuffer_convert 对齐的是析构不再自动刷新：
新／旧／GNU 探针输出 3／9／0 字节，缓冲算法未改；GNU 与 libc++ 的缓冲策略原已不同，
旧 libc++ 9 字节变为新库 3 字节则是移除析构刷新的结果。对象布局与符号集合不在本轮追求互换的范围内。
