## 3. Patch0 自动生成证实

平台 SRPM 中：

- Source0 流式 SHA256 实测为 `16a932e1bad4e1ed68938b48aa9fe5613992426584a75dd17dacabf2151d122e`；
- Patch0 SHA256 为 `509ae752761a32765df63036f1034f94229c3f47d8883e5bccdc469018d7870c`；
- 导出后的 spec 明写 `# Patches auto-generated by git-buildpackage:`、`Patch0: 0001-Apply-Tizen-toolchain-compatibility-fixes.patch` 和 `%patch0 -p1`（`generated/srpm/llvm.spec:48-49,158-161`）。

平台 VCS 锚 `c12cbe…` 相对上游 tag 有五个提交；四个只改 `packaging/`，唯一含源码改动的是 `bdfb133d… Apply Tizen toolchain compatibility fixes`，改 10 个源码文件并另改一个 `packaging/llvm.spec`。GBS 明确传 `--git-patch-export-ignore-path=^(packaging/.*|.gbs.conf)`（`gitbuildsys/cmd_export.py:178-184`），所以该提交导出时恰剩 10 个目标文件。

按任务要求生成该提交的 source-only `git format-patch`。与 SRPM Patch0 的 raw diff 只有两个头部差异：标准 git mbox 多一行 `From <commit> Mon Sep…`，Subject 多 `[PATCH]`；正文零差异。GBP 的实际 `write_patch_file` 本来就用 `unixfrom=False` 且直接写原 Subject（`gbp/scripts/common/pq.py:194-243`）。按这两项实际序列化差异归一化后，两文件均为 7,693 字节、SHA256 均为 `509ae752…`，`cmp` 退出 0（`commands/02_patch_origin_proof.log:264-306`）。

结论：

`PATCH_AUTOGENERATED_CONFIRMED`

同时确认：匹配提交是平台 `c12cbe…` 的祖先，但不是当前本地 `tizen_base` 的祖先；它只存在于所抓取的其他远端线中。原文见 `commands/02_patch_origin_proof.log:234-243`。

## 4. 编号分配与多提交行为

本机实际版本为 `gbs 2.0.8`、`gbs-export 2.0.8`、`git-buildpackage-rpm 0.9.36+tizen20240605`。实现链如下：

1. GBS 在非native路径强制打开 `--git-patch-export`，设置 `100k` 压缩阈值，并排除 `packaging/` 和 `.gbs.conf`（`gitbuildsys/cmd_export.py:163-184`）。
2. GBP 对提交按时间正序逐个 `format_patch`；过滤后无路径则不生成文件（`gbp/scripts/pq_rpm.py:152-164`）。当前配置没有 squash，当前本地范围也无真实 merge commit。
3. 文件名前缀为 `len(series)+1` 的四位数，即 `0001-`、`0002-`……；basename 总长按 63 字符截断（`gbp/scripts/common/pq.py:246-278`）。
4. spec patch 编号从 0 起；第一个文件写 `Patch0` 与 `%patch0 -p1`，依次递增（`gbp/rpm/__init__.py:688-701`）。

由此对两个不同历史分别作确定回答：

- 对平台 SRPM 的实际历史 `ca7933e… -> c12cbe…`，现有一个源码 patch。若把 EHABI backport 作为下一线性提交，结果是 `0002-libcxxabi-declare-__gnu_unwind_frame-in-cxa_personal.patch`、`Patch1`、`%patch1 -p1`；不会并入 Patch0。EHABI source-only diff 实测 611 字节，低于 100k 阈值。
- 对当前检出的本地 `tizen_base`，`c12cbe…` 不是其祖先。该分支从上游 tag 起有八个线性提交，其中两个仅改 packaging、六个改源码；因此已经位于 HEAD 的 EHABI 是第六个 patch：`0006-libcxxabi-declare-__gnu_unwind_frame-in-cxa_personal.patch`、`Patch5`、`%patch5 -p1`。完整逐提交映射见 `commands/03_gbs_implementation_evidence.log:916-925`。

这两个编号结论分别对应两条不同历史，不能相互替代。

## 5. R6 与平台机制的关系

R6 最终工作目录、完整 build 命令、depanneur 命令和内层 export 命令见 `commands/04_r6_and_gcc_comparison.log:2-37`。三个层次都保留了 `--no-patch-export`。该开关的 CLI 原文为“不创建 upstream 与 export tree 之间的 patches，并从 export tree 而非 upstream branch 创建 tarball”（`/usr/bin/gbs:129-132`）。

因此 R6 的实际行为不是“上游 Source0 + 下游 patches”，而是把 disposable worktree HEAD `3d3e3da…` 整体打成 Source0。其 SHA 实测为 `7d7f2105f1c745754e1318b3d73b632a642e426883fb2d6fa6a5b46f55b5d314`，与平台的 `16a932e1…` 不同（`commands/04_r6_and_gcc_comparison.log:49-65`）。逐项差异见 `build_method_delta.tsv`。

### 5.1 第 4b 推理链

完整逐步链见 `reasoning_chain_4b.tsv`。结论限定为：若 `libcxx-runtimes.spec` 位于 `platform/upstream/llvm` 的 `packaging/` 下，由 `--spec libcxx-runtimes.spec` 选择，并使用平台同一标准非native导出、同一 VCS 锚和配置，则：

- Source0 取 `upstream/22.1.8` 对应上游树；现有平台成品实测其 SHA 为 `16a932e1…`；
- export revision 相对上游树的非packaging源码提交按提交生成 patch 并注入导出后的 spec；
- `packaging/` 下的 spec、map、manifest、provenance 等由 GBP 复制，不进入源码 patch。

结论记：

`PLATFORM_STYLE_PATCH_EXPORT_DETERMINED`

边界：平台构建服务器当次完整 export 命令行/外部 profile 覆盖记录在已搜索范围内 `NOT_FOUND`；上述结论由仓配置、同版本本机实现与平台 SRPM 成品字节结果互证，不补全未见参数。
